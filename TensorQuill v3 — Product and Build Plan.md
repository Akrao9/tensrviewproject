# TensorQuill v3 — Product and Build Plan

Nov 13, 2026 · @Ak B

TensorQuill lets ML engineers and their coding agents see inside a PyTorch training run, so a failing run is caught and explained before it wastes days of GPU time. It was called TensorLens until Nov 14, 2026, when the name TensorQuill was chosen (see Decisions); the dated review reports in this folder still use the old name. This version replaces the larger v2 plan.

## Product

TensorQuill owns the capture SDK, detectors, the evidence they produce, and (decided Nov 14, 2026) its own Rust viewer app built on Rune. Until that app covers the needed views, stock Rerun displays the evidence, and the team's coding agent uses it to investigate incidents.

- **Who it is for:** teams training large models on their own clusters with MLflow or W&B. Start with RL, robotics and mixture-of-experts teams, whose important signals are not loss curves.
- **The pitch:** add one line to your PyTorch script and see inside a failing run (activations, attention, MoE routing), with evidence an agent can read.
- **Against trackers:** MLflow and W&B show scalar curves, and their MCP servers let coding agents query those runs. This shows what happens inside the layers.
- **Against CoreWeave ARIA:** ARIA is an agent inside W&B that analyses experiments, proposes next runs and launches them with approval (public preview June 2026). It reasons over what W&B logged, mostly scalars, and is tied to W&B and CoreWeave. This captures layer internals and works with whichever tracker, agent and cloud the team already has.
- **Against Trainy Pluto:** Pluto is a Neptune replacement built for responsiveness with many runs, and its experimental MCP server lets an agent read per-layer panels in one call. It displays what the user logs; no capture SDK or failure detectors turned up. This captures the internals cheaply under `torch.compile` and FSDP and detects known failures.
- **Against debugging agents:** free add-ons and research agents such as RunSleuth read logs, loss curves and gradient norms. None found inspects activations, attention or MoE routing. This gives those agents a picture and the numbers behind it.

**The gap.** A search on Nov 13, 2026 found no product that captures layer internals (activations, attention, MoE routing, cross-GPU drift) and hands an agent the evidence to explain a failure. Public requests for such a tool were not found either, so demand is unproven; the closest signal is that CoreWeave and Trainy are both building agent access to training runs.

**Why now.** OpenAI bought Neptune, whose product logged thousands of per-layer metrics to debug unstable runs, and the hosted service shut down in March 2026. Teams that relied on it said the hard requirement was a tool that stays responsive with thousands of runs and heavy logging.

## How it works

Capture signals inside the training script, write them to an append-only local file on each rank first, and optionally stream them from that file's byte offset over Arrow Flight to a self-hosted Rust ingest server that stores partitioned Parquet. Detectors run in Python on either the local files or the server's Parquet files while the run is in progress, exporting JSON evidence for coding agents and an `.rrd` recording and blueprint for engineers to explore in Rerun.

Scalars keep going to the tracker the team already uses. Tensor summaries take their own path, so a slow tensor pipeline or network stall never blocks metric logging or drops training steps.

## Capture SDK

Inside the compiled graph, hooks compute only cheap statistics of fixed size. Copies to the CPU, JSONL writing, Arrow Flight encoding, and probe passes happen outside the compiled step.

**Setup:** `python -m pip install -e 'sdk[rerun]'` and `tensorquill.init(model)`, with the team's MLflow or W&B configuration left unchanged. `init` tags the tensor stream with the tracker's run ID, and the SDK records its own global step with every batch.

- **Run ID.** Takes an explicit `run_id=` first, then `MLFLOW_RUN_ID`, `mlflow.active_run()`, or `wandb.run.id`. Without any of those, it uses the launcher's job ID (`TORCHELASTIC_RUN_ID` unless `"none"`, or `SLURM_JOB_ID` and `SLURM_STEP_ID`), and otherwise generates a unique `run-<UTC YYYYMMDD-HHMMSS>-<hex6>` ID, broadcast from rank 0 when `torch.distributed` is initialized, so separate runs never append to the same file and every rank shares one name (Nov 14, 2026). Because `mlflow.active_run()` is thread-local and `None` when a run was created through `MlflowClient` (as PyTorch Lightning's `MLFlowLogger` does on rank 0 via `@rank_zero_experiment`), the Lightning callback (`tensorquill.lightning.TensorQuillCallback`, Nov 14, 2026) reads the logger's run ID on rank 0 and broadcasts it with `trainer.strategy.broadcast`.
- **Step.** An MLflow run has no current step; the step is passed with each `log_metric` call. By default (`auto_step=True`), TensorQuill counts training iterations through `register_optimizer_step_post_hook` (imported from `torch.optim.optimizer`), or takes `step=` from `session.step(step=...)` / `trainer.global_step` when `auto_step=False`. With multiple optimizers on one model (such as Muon plus AdamW), the first optimizer to step becomes the lead optimizer and commits the iteration's step; other optimizers in the same iteration are deduplicated by parameter gradient `(id(p.grad), p.grad._version)` signatures (`sdk/src/tensorquill/capture.py`). When `torch.amp.GradScaler` skips `optimizer.step()` on gradient overflow, neither optimizer hook fires; use `auto_step=False` and call `session.step(lr=...)` once per iteration, or attach `scaler=` (planned in Step 10b) to record skipped overflow steps.

Do not ship a tracking-store plugin with its own URI scheme (`tensorquill+https://…`). MLflow selects the plugin by scheme, but its proxied artifact store (`mlflow-artifacts:`) accepts only `http` and `https` tracking URIs, so `log_artifact` would fail for teams that use it. The model registry would also need its own plugin.

**Rules (matching `sdk/src/tensorquill/capture.py` and `probe.py` at `ffdbabd`)**

- **Static compiled hooks.** Register forward hooks **before** `torch.compile` and keep them attached after `session.close()`. With default PyTorch settings, hooks added to a module that had none when compiled are silently ignored (`skip_nnmodule_hook_guards`); on a module that already had hooks, Dynamo guards the hook dictionary, so adding or removing a hook triggers a recompile. `init()` rejects an outer `torch.compile(model)` wrapper (`_orig_mod`).
- **Fixed-shape on-device hook bodies.** Hook bodies compute mean, std, absolute max, and zero fraction per watched module (or router expert counts via compare-and-sum into an `int64` buffer) and write into preallocated on-device buffers marked with `torch._dynamo.mark_static_address`. No histograms, `.cpu()`, `bincount`, `nonzero`, numpy, or I/O run inside a compiled hook. Across microbatches (gradient accumulation), hooks keep the largest `abs_max`, sum router counts, and keep the last microbatch's `mean`, `std`, and `zero_frac`; recomputed forward passes during activation checkpointing backward are skipped.
- **Gradient norms without backward hooks.** Read `p.grad` norms in `register_optimizer_step_pre_hook` (before the lead optimizer's `step()` or `zero_grad()`, or after `step(closure)` when a closure is used) with `torch._foreach_norm(..., dtype=torch.float32)`, grouped by `(device, dtype)` after unwrapping `DTensor.to_local()`, falling back to chunked `torch.linalg.vector_norm` when `_foreach_norm` is unavailable. Because the pre-hook runs after user gradient clipping, TensorQuill also wraps `torch.nn.utils.clip_grad_norm_` while the session is open (and keeps the wrapper callable after `close()`) to record the pre-clipping total norm (`clip_grad_norm`) at zero extra cost; callers can also call `session.record_grad_norm(norm)` or `session.record_grads()` before manual clipping.
- **Ring buffer and bounded writer queue.** On each step, outside the compiled graph, hook buffers copy into slot `_slot` of an on-device ring buffer of length `every` (`every=50` by default). Every `every` steps (and on `close()`), the float32 ring buffer, int64 router counts, clip-norm ring, replica-spread ring, and logged-scalar ring move to the CPU and are enqueued to a background writer thread with a bounded queue (`WRITER_QUEUE = 8` blocks of `every` steps). If the sink stalls, training blocks on `queue.put` with a one-time `RuntimeWarning` rather than growing host memory or dropping steps.
- **Tier 2 probe pass (`probe=`, `probe_every=1000`).** Requires PyTorch 2.6+ (`torch.compiler.set_stance("force_eager")`). Runs after the step's ring-buffer copy and clears the capture hook buffers afterwards so probe activations never pollute training statistics. Snapshots and restores each submodule's `training` flag, turns off deterministic algorithms for `histc` / `index_add_`, and restores CPU/CUDA RNG states. Temporarily switches Hugging Face `flash_attention_2` and `flash_attention_3` modules to `sdpa` and wraps `F.scaled_dot_product_attention` so the fused kernel still produces the forward output while the wrapper recomputes `softmax(QKᵀ)` in query blocks of at most $2^{26}$ scores (256 MB), repeating `key` heads to match `query` heads under grouped-query attention (`enable_gqa`). Each query row's entropy is normalized by the log of that row's visible key count (`entropy_share`), excluding all-masked and non-finite rows. If a probe raises an exception, `probe.error` is recorded with a `RuntimeWarning` and the step record is preserved.
- **Per-rank files.** Every rank writes its own file, `tensorquill-out/<run_id>.rank<rank>.jsonl`, reading the rank from `torch.distributed` or `RANK` / `LOCAL_RANK`.
- **Compiler gate.** Verified in-process via Dynamo counters: [test_compile.py](sdk/tests/test_compile.py) and [test_probe.py](sdk/tests/test_probe.py) run on CPU with `error_on_recompile=True` and check `counters["graph_break"]` is empty; [gpu_check.py](sdk/examples/gpu_check.py) also checks `counters["inductor"]["cudagraph_skips"]` on CUDA, with `TORCH_LOGS="graph_breaks,recompiles,cudagraphs"` enabled for diagnostic logs.

**Data tiers**

| Tier | Data | Computed how | When | Approx. size |
| --- | --- | --- | --- | --- |
| 0 | Logged scalars (`session.log`), learning rate, `clip_grad_norm`, per-parameter `grad_norms`, per-block activation `mean`, `std`, `abs_max`, `zero_frac`, and 50-step float64 `weight_norms` / `weights_unchanged` | Forward hooks into static buffers; `_foreach_norm` in optimizer pre-hook | Computed every step (weights every 50), flushed to CPU every `every=50` steps | ~26 KB JSON per step on Granite full capture |
| 1 | MoE expert load counts (`moe`), router entropy, diversity `exp(H)/N`, dead-expert fraction (`moe_stats`), and `moe_top_k` | On-device compare-and-sum per router in forward hook; entropy and diversity computed on CPU flush | Accumulated every step, flushed every `every=50` steps | ~4 KB JSON per step for 24 routers × 32 experts |
| 1 | Cross-GPU spread (`replica_spread`): float64 L2 norm, sum and seeded projection per replicated parameter | Per-rank float64 norm, sum and projection after `optimizer.step()`, one `all_gather` on `replica_group` | Every `replica_every=50` steps where `(step + 1) % replica_every == 0` | 24 bytes per parameter tensor per rank on the wire |
| 2 | Activation histograms (64 bins) per repeated block; per-head attention `max_logit`, `entropy`, `entropy_share`, `masked_rows`, `invalid_rows`, and 64×64 pooled attention map | Eager probe pass (`force_eager`, `no_grad`) on a fixed batch | Every `probe_every=1000` steps | ~0.5–2 MB JSON per probe step on Granite (24 layers) |
| 3 | Full activations for flagged layers (replay) | Postponed from v1 | — | — |

Attention requires the Tier 2 probe pass because FlashAttention and fused SDPA never materialize the attention matrix during training. The probe uses a fixed batch so distributions and attention maps compare cleanly across steps.

## W&B support

Support W&B from inside the customer's own training script. Hold off on anything that uses a customer's W&B key until a lawyer has read W&B's terms.

| Route | What it does | State and risk |
| --- | --- | --- |
| Read the active run in the script | `tensorquill.init(model)` reads `wandb.run.id` once when a run is active (after `run_id=`, `MLFLOW_RUN_ID`, and `mlflow.active_run()`) and tags the tensor stream with it | **Built.** Low risk: uses the MIT-licensed client on the user's machine and touches no W&B server |
| Wrap `wandb.log` | Keeps TensorQuill steps aligned with the steps W&B records | **Not built.** Low legal risk, but leans on client internals (`commit=False`, explicit `step=`, `define_metric`) |
| Viewer reads W&B history with the customer's key, on their machine | Pulls scalars into the viewer next to the tensor views | **Not built.** Needs legal review; terms restrict accessing the service to build a competing product |
| Hosted service holds the customer's W&B key | Cloud service pulls their W&B data | **Not built.** Highest risk; terms also restrict sharing access credentials with a third party |

Do not read `wandb.run.step` per training step. It waits on a round trip to the W&B background process, with a 30-second timeout, and raises an error in `mode="shared"` runs. It is also W&B's own log counter, not the training step: PyTorch Lightning's `WandbLogger` records the step as a `trainer/global_step` metric. Use the SDK's own global step.

The W&B Python client is MIT-licensed. The W&B server is proprietary, and its free local licence is for personal projects only, so never bundle it. If TensorQuill ever ships a default metadata server, use MLflow, whose client and server are both Apache 2.0. The terms were read through a third-party summary, not the original text.

## Cross-GPU detector

This detector checks that weights meant to be identical copies on several GPUs stay identical, and fires on the first step they drift apart.

**Why it is in the plan.** In the BLOOM-176B run, gradient clipping was applied on only one worker in each tensor-parallel group. LayerNorm weights that should have matched drifted apart while the loss curve looked healthy. It was found 13 days into the run, by a test that compared the weights across ranks, and the bug predated the run (TrainCheck's write-ups say ten or fifteen days). A separate study of faulty hardware found the same pattern: parameters on an unhealthy node drift while the loss stays close to normal.

**How it works (`sdk/src/tensorquill/distributed.py`)**

1. Every `replica_every` steps (`50` by default), where `(step + 1) % replica_every == 0` after `optimizer.step()`, each rank computes three fingerprints per parameter tensor, all in float64: its L2 norm, its sum, and a dot product with fixed pseudo-random weights derived from the element index (no random number generator is used, so training's random streams are untouched; decided Nov 15, 2026). The projection catches changes that keep the norm and sum, such as two elements swapping places; it is a screen, not proof of equality. Scheduling from the shared step number rather than a rank-local call counter guarantees every rank enters the collective on the exact same step.
2. The ranks that hold copies of the same weights share their `[n_params, 3]` fingerprints with the same single `dist.all_gather` on `replica_group` (24 bytes per parameter tensor per rank). `replica_projection=False` sends two columns.
3. Every rank in `replica_group` computes each fingerprint's spread divided by `max(mean_norm, 1e-12)` per parameter and records it in its own step record as `replica_spread`; a NaN or Inf weight on any rank makes that parameter's spread non-finite.
4. The detector (`sdk/src/tensorquill/evidence.py`) fires when the largest of `norm_spread`, `sum_spread` and `projection_spread`, each normalized by the parameter's mean L2 norm across ranks, exceeds `drift_tolerance` (`build_evidence(..., drift_tolerance=1e-6)` by default, one relative tolerance for both spread components) or is not finite; non-finite parameters carry `"non_finite": true` in the `replica_drift` incident.

It runs outside the compiled step and needs no hooks. See the implementation in [distributed.py](sdk/src/tensorquill/distributed.py) and the two-process test script in [replica_check.py](sdk/examples/replica_check.py), which also handle empty parameter shards, Apple MPS fallback (where float64 is unavailable), missing `_foreach_norm`, and non-finite weights.

The sum is paired with the L2 norm because a norm cannot see a sign flip: `[1, -1]` and `[1, 1]` have the same norm and different sums. Both fingerprints are float64 because a norm or sum in bf16 or fp16 is too coarse to show small drift. On CUDA, `torch._foreach_norm(ts, 2, dtype=torch.float64)` reads bf16 and fp16 tensors directly in one fused kernel per `(device, dtype)` group; sums and non-fast-path norms split flat tensors into `1 << 24`-element chunks (at most 128 MB temporary float64 memory). A float64 norm pass over Granite's 2.6 GB of bf16 weights measured ~3.7 ms per check on the RTX PRO 6000 (~0.07 ms/step amortized at `replica_every=50`); the two-GPU `all_gather` cost over NCCL is not yet measured.

**Where it applies**

| Setup | What is checked | Note |
| --- | --- | --- |
| DDP (data parallel) | Every trainable parameter | Pass `replica_group=dist.group.WORLD`; each rank holds a full copy |
| Tensor parallelism | Only weights replicated across TP ranks, such as LayerNorm | Pass `replica_params=` (Nov 14, 2026): a `(name, param) -> bool` filter, or the parameters or their names. With Megatron, `lambda name, p: not getattr(p, "tensor_model_parallel", False)` selects the replicated weights. Without it, every trainable parameter is compared, which reports false drift under tensor parallelism |
| Hybrid FSDP (sharded inside a node, replicated across nodes) | Each rank's local shard, compared across the inter-node replication group | Pass the replication process group as `replica_group=`. `distributed.py` unwraps FSDP2 `DTensor`s via `.to_local()`; FSDP1 flat parameters are not supported |
| Fully sharded (FSDP full shard, ZeRO-3) | Nothing | Each rank holds a different shard, so there are no copies to compare |

**Limits**

- A swap of two values inside a tensor changes neither the norm nor the sum. A weighted sum with fixed pseudo-random weights would catch it, for one extra pass over the tensor. Add a full hash at checkpoint time if that matters.
- Buffers such as BatchNorm running statistics differ per rank by design and are left out.
- It does not catch faults that hit every rank alike, slow nodes, or crashes.
- Verified on two CPU processes with Gloo ([replica_check.py](sdk/examples/replica_check.py)); the two-GPU NCCL run and the `1e-6` tolerance on healthy multi-GPU training are pending Gate 2.

## Ingest server and local-first streaming

Multi-node runs need a single store that collects every rank's stream and runs detectors before the job ends. The ingest pipeline combines three patterns from the reference codebases:

- **Local log first and offset-based flow control (from W&B):** W&B writes every record to its local `.wandb` transaction log first and keeps at most 32 records in memory (`InMemorySize: 32`), collapsing any network backlog into a 24-byte file-offset range (`FlowControlBufferSavedChunk` in `wandb/core/internal/stream/flowcontrolbuffer.go`) and seeking back to `lastReadOffset` when a trailing record is incomplete (`ResetLastRead` in `wandb/core/internal/runsync/runreader.go`). By contrast, MLflow's `AsyncLoggingQueue` buffers in an unbounded Python `Queue()` with no disk log (`mlflow/utils/async_logging/async_logging_queue.py`), and Rerun's `re_grpc_client` drops queued messages if its 5-second flush times out (`re_grpc_client/src/write.rs`).
- **Single-binary self-hosted Rust server with bounded byte quota (from Rerun):** Rerun ships an open-source Rust server (`re_server` on port `51234`, `re_grpc_server` on port `9876`) using `tonic`, `arrow`, `parquet`, `object_store`, `tcp_nodelay(true)`, `http2_adaptive_window(true)`, a Bearer token `Authenticator` interceptor (`re_auth`), and a byte-bounded input channel (`CHANNEL_SIZE_BYTES = 128 MiB` in `re_quota_channel`).
- **Composite-key deduplication on retry (from W&B and MLflow):** W&B deduplicates `file_stream` retries by virtual line offset (`HistoryLineNum` in `filestreamstate.go`), and MLflow deduplicates `LogBatch` retries by upserting on `(run_uuid, key, step, timestamp)` (`sqlalchemy_store_upsert_utils.py`).

### Specification

1. **Local append-only file (`sdk/src/tensorquill/sink.py`):**
   - The SDK always writes `tensorquill-out/<run_id>.rank<rank>.jsonl` first via the bounded 8-block `JsonlSink` queue (`WRITER_QUEUE = 8`). Each JSON line carries `"schema_version": 1`, `"run_id"`, `"rank"`, `"step"`, `"ts"` (Unix seconds when the step ended) and the captured metrics.
   - Local files use JSON Lines rather than Parquet because Parquet writes its footer only on close; a killed or preempted training process would leave an unreadable Parquet file.
2. **Opt-in Flight sender (`sdk/src/tensorquill/flight.py`):**
   - Enabled only when `endpoint=` or `TENSORQUILL_ENDPOINT` (`grpc://host:port` or `grpcs://host:port`) is set; default local runs open zero sockets.
   - A background daemon thread tails `tensorquill-out/<run_id>.rank<rank>.jsonl` from the byte offset saved in `tensorquill-out/<run_id>.rank<rank>.offset` (updated via atomic write-and-rename of `.offset.tmp` after each server `PutResult` ack). It holds one `DoPut` stream open per rank; the server acknowledges an offset only once those rows are in a stored Parquet part (see Decisions).
   - **Torn-line recovery:** only complete lines ending in `\n` that parse as JSON and match `run_id` are batched. If EOF is reached mid-line (or a crashed prior process left a truncated line before the next newline), the sender does not advance past the incomplete tail until `\n` arrives.
   - **Batching and backoff:** sends a `pyarrow.RecordBatch` over Arrow Flight `DoPut` every **50 steps or 2 seconds** (whichever comes first, capped at **4 MiB** uncompressed). Holds at most one batch in RAM; on disconnect or `Status::resource_exhausted`, sleeps with full-jitter exponential backoff (`100 ms` base, `30 s` cap) and re-reads from the saved `.offset` on reconnect. On `session.close()`, flushes remaining complete lines with a 5-second timeout and prints the local `.jsonl` path if unacked bytes remain.
3. **Arrow Flight `DoPut` contract and schema (`server/src/ingest.rs`):**
   - Crate versions: `arrow-flight = "60.1.0"`, `arrow = "60.1.0"`, `parquet = "60.1.0"`, `object_store = "0.14.2"`, `tonic = "0.14"`, `tokio = "1"`.
   - `FlightDescriptor`: path `["runs", "<run_id>", "rank=<rank>"]`.
   - `FlightData.app_metadata`: UTF-8 JSON `{"schema_version": 1, "run_id": "<id>", "rank": 0, "min_step": 0, "max_step": 49, "end_byte_offset": 128450}`.
   - **Arrow schema (one row per step):**
     - Scalar/vector columns: `schema_version: Int32`, `run_id: Utf8`, `rank: Int32`, `attempt: Int64`, `step: Int64`, `ts: Float64`, `lr: List<Float64>`, `grad_norm: Float64` (nullable), `clip_grad_norm: Float64` (nullable), `weight_norm: Float64` (nullable), `weights_unchanged: List<Utf8>` (nullable), `step_skipped: Boolean` (nullable), `grad_scale: Float64` (nullable).
     - Map columns: `scalars: Map<Utf8, Float64>`, `grad_norms: Map<Utf8, Float64>`, `weight_norms: Map<Utf8, Float64>`, `moe_top_k: Map<Utf8, Int32>`, `moe_counts: Map<Utf8, List<Int64>>`, `replica_spread: Map<Utf8, List<Float64>>`.
     - Canonical JSON-string columns for nested objects whose keys vary by model: `layers_json: Utf8` (nullable), `moe_stats_json: Utf8` (nullable), `probe_json: Utf8` (nullable), and `extra_json: Utf8` (nullable) for any key or value the columns above cannot hold. Storing these three nested structures as UTF-8 JSON strings inside Parquet preserves 100% lossless round-tripping back to the dict format `evidence.py` expects (`IM2`).
4. **Deduplication, backpressure, auth, and Parquet layout (`server/src/storage.rs`):**
   - **Watermark deduplication:** the server tracks the last kept step per `(run_id, rank, attempt)`, initialized when an attempt's first batch arrives by reading the `max(step)` row-group statistics from the newest existing Parquet footer under `{store_root}/runs/{run_id}/rank={rank}/attempt={attempt}/`. `attempt` is a column of every row (the writing session's start time, Unix milliseconds); a batch that spans two attempts is split. On each `DoPut` batch, rows with `step <= last_acked_step[(run_id, rank, attempt)]` are filtered out before buffering, making client retries idempotent.
   - **Memory cap:** total buffered Arrow bytes across all open streams are bounded at **128 MiB**. When full, `DoPut` returns `tonic::Status::resource_exhausted("ingest buffer full")` so senders pause on their local `.jsonl` file.
   - **Parquet flushing:** because S3 and GCS do not support in-place append, each `(run_id, rank)` buffer flushes an immutable Zstd-compressed Parquet part file every **500 steps or 10 seconds** (and on stream EOF or `SIGTERM`) via `object_store::ObjectStore::put` to:
     `{store_root}/runs/{run_id}/rank={rank}/attempt={attempt}/part-{min_step:08}-{max_step:08}.parquet`
     and replies with `PutResult{app_metadata: {"end_byte_offset": N}}` after the flush succeeds.
   - **Authentication and TLS:** `tensorquill-server --listen 127.0.0.1:50051 --store file:///var/lib/tensorquill` binds to loopback by default. Binding to a non-loopback address requires either `TENSORQUILL_TOKEN` (checked by a `tonic` interceptor against `Authorization: Bearer <token>` in constant time) or `--allow-unauthenticated`, with optional TLS via `--tls-cert` and `--tls-key`.
5. **Live detection and the Python-vs-Rust detector benchmark:**
   - For v1, `python -m tensorquill --watch {store_root}/runs/{run_id}` polls newly written `part-*.parquet` (or local `.jsonl`) files every 2 seconds, reconstructs step dicts losslessly from the Parquet columns, and writes `{run_id}.evidence.json` (`schema_version: 1`) atomically via rename.
   - **Benchmark protocol before porting detectors to Rust:** run a 64-rank, 1,000-step synthetic MoE stream (50-step flushes) and measure (a) Python `evidence.py` reading new Parquet parts via `pyarrow.parquet` vs. (b) an in-server Rust detector pass over incoming `RecordBatch`es. Keep detectors in Python unless the Python worker exceeds **250 ms** per 50-step flush across 64 ranks or **1 CPU core** steady-state.

## Viewer and agent evidence

Use stock Rerun 0.43.2 as the interim viewer, until TensorQuill's own Rune app covers the views below (decided Nov 14, 2026: Rerun is temporary) (`rerun-sdk==0.43.2` pinned in [sdk/pyproject.toml](sdk/pyproject.toml)). The [MoE bake-off](experiments/moe-bakeoff/README.md) and shipped exporter (`export_rerun` in [evidence.py](sdk/src/tensorquill/evidence.py)) use a blueprint and built-in views for the detector summary, status heatmap, per-expert load table, probe tab, logged scalars tab, and diversity timeline. Keep the evidence schema independent of Rerun so engineers and agents read the exact same numbers in JSON.

- **Schemas and versioning (`sdk/src/tensorquill/evidence.py`, `capture.py`).** Every JSONL step record carries `"schema_version": 1`, `"ts"` and `"attempt"` (all Nov 14, 2026; `attempt` was added without changing the version, because it is optional to readers: a record without it reads as attempt 0); readers treat records without `schema_version` as version `0` (missing `moe_top_k` already defaults from `--top-k`). The exported `<input>.evidence.json` carries `"schema_version": 1`, `"run_id"`, `"layer_count"`, `"expert_count"`, `"router_names"`, `"overload_threshold"`, `"top_k"`, `"starve_window"`, `"starve_ratio"`, `"incidents"` (each with `kind` and `step`, kind-specific fields, and `scalars` when values were logged with `session.log`), and `"samples"` (one per router per step). Evidence written by `--watch` on a server's store also carries an optional `"detection"` (`source`, `state`, `reason`, and the attempts and steps compared; Nov 15, 2026), and when its incidents come from the server's report `"samples"` is empty and the router keys are absent.
- **Headless screenshots and sample-step sidecar.** Use Rerun's headless Viewer for per-view PNGs and `rerun viewer-mcp` for live screenshots and the widget tree. Because a timeline view displays the most recent sample at or before the cursor, exporting a screenshot for `<run_id>` at requested `<req_step>` writes `<out_dir>/<run_id>.step<req_step>.<view>.png` alongside `<out_dir>/<run_id>.step<req_step>.<view>.meta.json` containing `{"run_id": "<id>", "requested_step": <req_step>, "sample_step": <actual_step>, "view": "<view>", "rrd_path": "<path>"}`.

**Own viewer app on Rune (decided Nov 14, 2026).** Rerun is temporary. TensorQuill will ship its own Rust app built on Rune instead of a custom `ViewClass` inside Rerun. Rerun 0.43.2's built-in dataframe view cannot sort, and `ViewerClient.send_table` opens a separate table page outside the recording blueprint; a custom Rerun view would also tie the product to Rerun's extension interfaces.

- **Data.** The app reads `evidence.json` and the per-rank JSONL (and the ingest server's Parquet parts later) directly. `.rrd` stays an export for the interim Rerun viewer only, so capture and detectors do not change.
- **Parity before replacing Rerun.** Step timeline with scrubbing, layer × expert status heatmap, sortable expert-load table that follows layer selection, time series, probe histograms and attention maps, and loading a full Granite run (650 steps, about 17 MB of JSON) smoothly.
- **Agent access.** Rune apps render headless to PNG and expose their element tree, which replaces Rerun's headless viewer and `rerun viewer-mcp` for Step 19; keep the `requested_step` / `sample_step` sidecar.
- **Headless on Linux.** Step 20's software-Vulkan check (`lavapipe`) applies to the Rune app; Rune renders through wgpu.

Findings along the way:

- **Fixed per-step thresholds failed on real data.** Healthy Granite has experts picked by 85–100% of tokens, and with two documents per batch single experts jump to over half the tokens for one step. Top-k overload therefore requires the router's diversity to drop below 0.6 of its recent median (healthy minimum 0.82; the seeded collapse 0.29). Experts nearly unused for hundreds of steps needed a 50-step windowed check, since one empty step is noise.
- **float32 norms cannot show whether bf16 weights changed.** A first stalled-weight check reported 147 of 218 parameters falsely; float64 norms fixed it but cost ~3.7 ms per check on the RTX PRO 6000. Reading the weights alone costs ~1.5 ms, so the check runs every 50 steps (`weights=50`), as `wandb.watch` (1,000 batches) and TrainCheck (`sampling_interval`) do.
- **Pure-bf16 training freezes norm weights.** In the Granite benchmark's setup (bf16 weights, AdamW, lr 1e-5, no float32 master weights) all 49 RMSNorm weights never change: their bf16 step size near 1.0 is ~0.008. TensorQuill reports this.
- **Block summaries miss growth in a few ordinary channels (A100, Nov 15, 2026).** SmolLM2-360M's block 16 output has `abs_max` about 20,000 and `std` 31 to 37, so two channels scaled 100× moved `std` 1.07 to 1.14× and `abs_max` 0.95 to 1.07× although the loss went from 2.3 to 6.9. Growth of the massive channels or of the whole block is seen at the seeded step. Per-channel statistics would see the rest and are not captured (decision: "What the dense checks seed").
- **A fault in one block shows in every later block.** Seeded in block 16 of 32, the activation spike covered blocks 16 to 31 and listed block 31 first, because modules are listed by ratio. A reader would name the wrong layer. Fixed Nov 15, 2026 in the Python and Rust detectors: the incident leads with the first block in the model, then the rest by ratio (so the largest is second and a list cut at 20 keeps both; checked on an RTX PRO 6000 with the case the old list would have broken: a fault in block 8 reached 24 blocks, the list holds 20, and block 8 still leads with block 31 second), and the summary reads "first in model.layers.16 … the largest, abs_max 723×, is in model.layers.31" on the A100 traces. The first version of the fix would have named the wrong block over the server: the Flight sender wrote `layers_json` with sorted keys, so `model.layers.10` came before `model.layers.2`; `layers_json` now keeps the model's order, and a test sends 12 unpadded blocks through the real server and Parquet.
- **The `Trainer` callback passes on a GPU.** `trainer_check.py` on an A100 (Inductor, fp16, clipping 1, SmolLM2-360M): all ten checks with `--fault massive` and with `--fault block`; 0 graph breaks and no recompiles; loss and clipping norm equal to `Trainer`'s logged values.
- **The probe on a dense GPU run.** SmolLM2-360M on an A100: full capture +2.94%, a probe step +170 ms (0.17 ms per step at every 1,000), the seeded block's largest value 100× between probes, and the next block's attention gone uniform (entropy share 0.34 to 1.00).
- **A100 router-only overhead, profiled.** Granite on an A100: +0.41%, +0.80%, +0.95% over three paired 100-step rounds, against +1.06% to +1.33% at an earlier commit; the added time is GPU work (+1.81 ms busy, 26 more launches, syncs unchanged), not host waits.

Open gaps:

- **A gradient spike in one small parameter is invisible to `grad_spike`.** `detect_grad_spikes` raises an incident only when the total gradient norm reaches 5× its median of the last 50 steps, and then names parameters; a parameter holding a share `s` of the total norm, scaled by `f`, moves the total to `sqrt(1 + (f²−1)s²)`, so ×100 needs `s` of about 4.9%. On the CPU toy a `k_proj` holds 0.18%: ×100 moves the total ×1.02, its own norm went ×100, and nothing was reported. Not measured on trained SmolLM2 (prediction: well under 5%). *Blocks:* nothing (the seeded case picks a factor that reaches the rule). *Closed when:* the detector reports a parameter whose own norm is at least 5× its median even when the total is not, with no false alarms on the healthy Granite and SmolLM2 captures (their per-parameter ratios on healthy steps have not been measured).
- **`stalled_weights` names only the parameters stalled at the first onset.** The incident is built at the first step any parameter has a 3-check streak and lists at most 20 in model order; later onsets only raise `stalled_steps`. With bf16 weights the RMSNorm weights stall from step 199 in every run, so a freeze that begins earlier or later is recorded by the capture and not named (reproduced on the toy in bf16). The Rust detector may share it (not checked). *Blocks:* Gate 2's stalled-weights case on bf16 weights (`--dtype float32` passes). *Closed when:* the strict xfail `test_with_bfloat16_weights_the_incident_names_the_seeded_parameter` passes, in the Python detector and, after a parity check, the Rust one.
- **Full-capture overhead.** Block-level full capture (`Stage 3` in [sdk/README.md](sdk/README.md#rtx-pro-6000-run-with-block-level-capture-stage-3)) measured +4.15% on the RTX PRO 6000 (~0.36 ms routers, ~0.85 ms block activations, ~1.5 ms per-step gradient norms). *Blocks:* None (`capture="routers"` is the MoE default; `capture="full"` is opt-in for debugging). *Closed when:* optional `grads=N` step sampling is benchmarked against single-step spike recall.
- **Headless rendering on Linux.** Headless screenshots have only been run on macOS. Rerun's native viewer on headless Linux requires Vulkan (`mesa-vulkan-drivers` `lavapipe` + `libvulkan1`). *Blocks:* Step 20 and Gate 3. *Closed when:* two consecutive headless exports in a Linux container produce byte-identical PNGs.
- **Many ranks on a shared filesystem.** `WRITER_QUEUE = 8` (`88a20e7`) bounds memory by pausing training with a `RuntimeWarning` when disk writes stall. *Blocks:* Gate 2 multi-GPU run. *Closed when:* tested with ≥2 ranks writing local `.jsonl` and streaming to `tensorquill-server`: done on CPU with two ranks on Nov 15, 2026; what is left is the two-GPU NCCL run and a shared filesystem.
- **`--watch` on a long run.** Python recomputation still reruns the detectors over the whole run (`--recompute`, fallback when reports are missing/stale, or one-shot `build_evidence`). Measured Nov 15, 2026 on a synthetic store of Granite's shape: one rank's update takes 0.4 s at 500 steps, 1.6 s at 2,000 and 8.1 s at 10,000, against 250 ms. On the live path (next action 4, decided Nov 15, 2026), steady-state `--watch` now reads the server's `incidents.json` (2 ms at 10,800 steps) instead of rerunning Python. *Blocks:* only fallback/offline updates (`build_evidence`, `--recompute`) and whether a 10,000-step server restart rebuild (6–7 s) should stop holding back the rank's next part. *Closed when:* either incremental checkpoints/state are kept across `--recompute`/`build_evidence` runs, or 250 ms holds at 2,000 steps for offline recompute as well.
- **Untuned thresholds.** The spike factor (5×), diversity drop (0.6), starved ratio (10% of an even share), and stall count (3 checks) rest on Granite and synthetic fixtures. *Blocks:* Gate 3. *Closed when:* evaluated on the author's own dogfood job without false alarms on healthy segments.

## Free and paid

Everything that runs on the user's own machine or cluster is free and open source. The paid tier, built only if Gate 4 passes, is managed multi-tenant hosting and alerting.

- **Free (`Apache-2.0 OR MIT`):** the capture SDK, opt-in Flight sender, self-hosted `tensorquill-server`, detectors, and Rerun evidence exporter, with zero telemetry.
- **Paid, \$250–500 per seat per month (unvalidated, post-Gate 4):** managed `tensorquill-server` cloud ingest, object-store retention, Slack/PagerDuty incident alerts, and automated PR drafts.
- **Self-hosted enterprise:** managed deployment, SSO/RBAC, and SLA inside the customer's own cloud account.

Cost per monitored run (Parquet storage bytes, `tensorquill-server` CPU/RAM, and headless screenshot rendering; zero LLM calls since the customer's coding agent diagnoses incidents) is measured in Step 26 before setting price.

## Risks

The biggest risk is commercial, not technical: teams may value the tool and still not pay for hosted monitoring.

| Risk | Effect | Mitigation |
| --- | --- | --- |
| Nobody pays for hosted monitoring | No revenue | Release the SDK and self-hosted `tensorquill-server` free first; build a multi-tenant hosted cloud only if Gate 4 shows ≥2 outside teams willing to pay |
| ARIA, Pluto, or TrainCheck adds compiled per-layer capture and MoE/attention detectors | The gap closes | Re-check all competitors at Gate 0 and before Gate 4; stay tracker- and cloud-neutral; lead with MoE, attention, cross-GPU drift, and zero-break `torch.compile` support |
| Trackers add per-layer views | The wedge narrows | Stay tracker-neutral; lead with MoE, attention, and `torch.compile` capture that scalar trackers lack |
| Rerun's extension interfaces change | The interim export breaks | Pin `rerun-sdk==0.43.2`; only the `.rrd` exporter depends on Rerun |
| The viewer depends on Rune, itself under heavy development | Rune's schedule delays the viewer, or a Rune change breaks it | Keep the Rerun export as a working fallback until parity; pin a Rune commit in `viewer/`; keep the app's input to `evidence.json` and JSONL so it can move to another renderer |
| Hooks stall training or break `torch.compile` | Users switch the SDK off | Overhead gate ≤1% for default `capture="routers"`, CI gate with `error_on_recompile` and `graph_break == 0`, and bounded writer queue (`WRITER_QUEUE = 8`) |
| Agents misread the pictures | Wrong diagnoses, lost trust | Every number travels in `evidence.json` (`schema_version: 1`); screenshots include `.meta.json` with `sample_step`; score on Gate 3 |
| Coding-agent clients handle tool images differently | The picture does not reach the model or the user | Test saved PNGs with target agent clients and always supply `evidence.json` alongside |
| Tensor data leaves the cluster | Enterprise deals fall through | Local `.jsonl` by default (zero network calls); opt-in Flight sender targets self-hosted `tensorquill-server` on the user's own cluster |
| W&B's terms restrict competing products and credential sharing | A W&B importer or hosted W&B sync breaches the customer's contract | Read only `wandb.run.id` in-process; require legal review before anything touches a customer's W&B API key |

## Unproven and open decisions

The synthetic MoE bake-off verified recording read-back and headless rendering. Capture now runs on a real MoE model (Granite) on single-GPU RTX PRO 6000 and A100 instances, with router-only overhead under 1% on the RTX PRO 6000 (+0.02% to +0.78%) and +1.06% to +1.33% on the A100, a seeded layer-12 collapse detected, and eleven incident detector kinds implemented in `evidence.py` and checked on Granite or synthetic fixtures. Full capture with block defaults measured +4.15% on the RTX PRO 6000. Multi-GPU NCCL capture, Linux `lavapipe` rendering, the Rust ingest server, real failures on the author's own jobs, and coding-agent diagnosis accuracy remain unmeasured.

**Unproven**

- Which Rune-app interactions (sorting, layer selection, linked table) cut diagnosis time or agent tool calls most in Gate 1.
- Whether `capture="routers"` on the A100 can be brought under 1% once profiled with `profile_overhead.py`, and whether `capture="full"` (+4.15%) needs optional gradient-norm step sampling.
- Whether the detector thresholds (5× spike, 0.6 diversity drop, 10% starved share, 3 unchanged weight checks) hold on models other than Granite without false alarms.
- Whether the hooks keep CUDA graphs on real models that support CUDA graphs (verified on the toy MoE; Granite's `grouped_mm` fails CUDA-graph capture even without TensorQuill).
- Whether the cross-GPU drift tolerance of `1e-6` holds on healthy multi-GPU NCCL runs without false positives from floating-point nondeterminism.
- Whether a coding agent with TensorQuill `evidence.json` and Rerun screenshots beats scalar-only tracker data by ≥30 percentage points in Gate 3.
- Whether outside teams want and will pay for hosted monitoring (Gate 4).

**Decisions**

- [x] **Product and package name (decided Nov 14, 2026): TensorQuill, `tensorquill`.** Checked Nov 14, 2026: free on PyPI and TestPyPI (including the `tensor-quill` spelling PyPI treats as the same), on crates.io (`tensorquill` and `tensorquill-server`), on npm, and as a GitHub handle; no GitHub repository uses the name. Formerly TensorLens, a placeholder: `tensorlens` is taken on PyPI and GitHub by unrelated projects. Rejected on the way: `gradpulse`, because PyPI already has a `gradpulse` (Pure State Labs, a PyTorch quantum pulse optimizer, since Jun 2026); and `gradsight`, chosen briefly the same day, which is free on PyPI and crates.io but whose GitHub handle belongs to an empty organisation created Jan 29, 2026. Done Nov 14, 2026: the GitHub organisation `tensorquill` (created by the author), and the rename in code and docs: package `tensorquill`, command `tensorquill`, server crate and binary `tensorquill-server`, output folder `tensorquill-out/`, environment variables `TENSORQUILL_*`, with no compatibility aliases for the old names, since nobody outside this repository used them. No record field or store path carried the name, so stored data needs no migration and `schema_version` stays 1; only `.rrd` exports change application ID. Not done: the first PyPI and crates.io uploads, which only the author's accounts can make, and moving this repository into the organisation.
- [ ] **Author's dogfood job, tracker, and multi-GPU setup** (Gate 0).
- [x] **Keeping a resumed run's repeated steps (decided and built Nov 14, 2026).** Each `tensorquill.init` stamps `attempt`, its start time in Unix milliseconds, on every record it writes. The server deduplicates on `(run_id, rank, attempt, step)` and writes under `rank=<rank>/attempt=<attempt>/`. The attempt lives on the record, not on the sender or the stream: a later process that resends old lines from the same file (a lost `.offset`, `send_file`) presents their original attempt, so they are still recognised as stored. Readers (`resolve_attempts`, applied by `load_records` and `build_evidence`) treat a later attempt that starts at step S as a rollback: earlier attempts' records at step S or later are left out, including steps the new attempt has not reached yet. `repeated_steps` still fires for a later attempt that starts the numbering over, which is the forgotten `start_step=` case, and for a step written twice within one attempt. Records and senders without `attempt` are attempt 0. This replaced the `(run_id, rank, step)` rule; no store written under the old layout is migrated, since none exists outside tests.
- [x] **Live detection runs in Rust inside the server; Python stays the reference (decided Nov 15, 2026; built the same day, in two slices).** The benchmark below put the Python detectors at 13 times the budget even with state kept, and reading 64 parts back costs about 830 ms before any detector runs, so faster Python alone could not meet it. The server already holds each batch in Arrow.
  - *Built, first slice.* `server/src/detect.rs` keeps per-rank state for `moe_imbalance`, `starved_experts`, `grad_spike`, `activation_spike`, `activation_drift` and `dead_activations`, including the logged-scalar context Python attaches to an incident.
  - *Built, second slice: fourteen of seventeen kinds in the server, three left to Python on purpose.* Added to `detect.rs`: `stalled_weights`, `loss_scale_trouble`, `non_finite`, `replica_drift`, `repeated_steps` and `resume_lr_change`. Added to `watchdog.rs`: `job_stalled` and `rank_silent`, as an `incidents` list in `watchdog.json`. They are not in `incidents.json` because that file is rewritten only when a part is stored, and a stall is when none is. `collective_hang`, `collective_desync` and `traincheck_violation` are not ported: PyTorch's analyzer reads Flight Recorder pickles on the training nodes and TrainCheck writes its results where it ran, so the server has neither (checked in the sibling PyTorch checkout: `torch/distributed/flight_recorder/components/loader.py` loads each rank's dump with `pickle.load` from a local directory, and `collectives.py` calls that analyzer's `build_db`).
  - *Attempts: every new attempt is a replay, and the replay reads rolled-back rows.* `repeated_steps` and `resume_lr_change` compare a new attempt with the rows it replaced and need each step's learning rate. Keeping that history for the life of the server would grow with the run, so it is held only during a replay, and a new attempt always triggers one (before, only an attempt that went back did). Between replays the one thing that can change is a restarted numbering writing more steps an earlier attempt had; the steps still ahead of it are kept for that. An incident of these two kinds names a step whose row may be written later by a newer attempt; its logged scalars are attached when that row is read.
  - *`not_checked` has Python's shape.* The list in `incidents.json` was kind names; it is now the same list of `{check, reason, ...}` entries as in `evidence.json`, with the two sources the server lacks and each resume that could not be compared. Nothing read the old shape.
  - *Three differences from Python by design.* NaN and Inf are `null`; a value that does not fit its column and travels in `extra_json` reads as absent (only `optimizer_ownership`, which has no column, is read from there, and only on the row where a stall is first reported); a step stored twice within one attempt is not looked for, because the server's watermark never stores one.
  - *Live evidence shape.* `runs/<run_id>/rank=<rank>/incidents.json`, rewritten after each stored part: the incidents as `build_evidence` shapes them, `last_step`, the kinds checked and not checked, the thresholds, `moe_flagged` (samples flagged and the last step, since an incident only names the first) and `rebuilds`. No per-step samples: at 10,000 steps Python's evidence file was 86 MB and took 878 ms to write, over budget by itself; the samples are already in Parquet.
  - *Only stored rows are judged, after the acknowledgement.* A crash can then never leave the incidents ahead of the store. A detector error or panic is logged and never fails a flush.
  - *One mechanism for restart and resume: a full replay of the rank's stored parts* with `resolve_attempts`' rules, on the first part after a start and whenever a part is not a plain continuation. Replaying only the last window, as first proposed, would be wrong: a held top-k baseline can be arbitrarily old, and first incidents and counts reach back to the start.
  - *Parity rule: the state after any prefix equals `build_evidence` on that prefix.* Python looks ahead over a finished list in three places; the stream matches it by restarting the gradient state at the first record with `clip_grad_norm`, and differs only for hand-made records whose `moe_top_k` changes in mid-run. `sdk/tests/test_server_detectors.py` (9 tests after the second slice, in the CI server job; 22 deliberate changes to the Rust rules each fail them or the watchdog end-to-end tests; one first survived, a learning-rate history that was not rolled back, and one branch was first unreached, a repeated step counted twice, and each got its own case) checks it through the real binary after 16 stretches of a 300-step run with ten kinds, after each of 12 stretches of a nine-attempt run, on seven short runs for single rules, across a restart inside a 140-step collapse, across two resumes that roll an incident back, on a top-k collapse before a baseline exists and dead experts with none overloaded, and on the seven Gate 1 fixtures (eight changes to the first slice's rules were tried the same way before). A NaN or Inf is `null` in the server's file.
  - *Measured* (M1 Pro, one thread, the benchmark's synthetic healthy store, 64 ranks × 2,000 steps, 50-step flushes, median of 40): detectors 54 ms per flush of 64 ranks (17 µs per step, against Python's 693 µs for all kinds), of which about 33 ms is decoding `layers_json` and `moe_stats_json`; writing the Parquet parts 138 ms; the incidents files 13 ms; about 205 ms together against 250 ms on this healthy run, and about 287 ms if no shortcut applied (136 ms of detectors), which is over. The pass line was set at 80 ms before measuring. The first version took 189 ms (on a busier machine, so roughly); exact shortcuts (no median when a window's lowest or highest value rules a hit out) brought it to 54 ms, and 136 ms is the cost when no shortcut applies. A rank's replay from 2,000 steps takes 73 ms, all 64 at once 0.94 s.
  - *Measured, second slice* (same machine and store): 56 ms per flush (worst 68) for twelve kinds, so the six added cost about 2 ms, not the 26 ms guessed from Python's proportions; replay 75 ms for one rank and 0.98 s for all 64. The store checks weights and replicas once in 50 steps and has no loss scaler, so a run that checks weights on every step was not timed.
  - *The watcher reads the server's report, and only when it is current (decided and built Nov 15, 2026).* `watch` on a rank's folder in a server's store takes its incidents from `incidents.json` and from the status's `incidents`, reads no part, and still adds Flight Recorder and TrainCheck findings itself. `build_evidence` and the one-shot command are unchanged and stay pure Python: they are the reference the parity tests compare the server with, and they need the parts anyway for per-step samples. The report has no clock, so it is dated against the store: current means its `attempt` and `last_step` equal the newest stored part's, read from the part's path (`read_server_report`); the newest attempt only, because after a resume from an earlier step an older attempt's parts reach further. An empty list counts as "no incidents" only then. Missing, unusable (another run or rank, fewer kinds, ahead of the store), or other thresholds: the detectors run here at once. - [x] **S3 and GCS stores, and the watchdog across a restart (decided and built Nov 15, 2026).** *Stores.* `--store s3://bucket/prefix` and `gs://bucket/prefix` are opened by `Storage::open`, which gives the builder the provider's own variables only (`AWS_*` for S3, `GOOGLE_*` for GCS): before, every environment variable was passed and the builders also take bare `token`, `region`, `endpoint` and `bucket`, so a stray `TOKEN` or `ENDPOINT` could configure the store. Credentials come from the variables, then what `object_store` implements (EC2 IMDSv2, ECS and EKS web-identity, GCE metadata, `GOOGLE_APPLICATION_CREDENTIALS`); shared credential files and `AWS_PROFILE` are not read. They are handed to the store and never printed (errors name variables, not values; tested, and the end-to-end test checks the server's output for a dummy secret). An S3-compatible service is `AWS_ENDPOINT_URL`, with `AWS_ALLOW_HTTP=true` for `http://` (the server says so when the flag is missing). Cloud stores are cargo features `s3` and `gcs`, **on by default**: the binary's job is S3, GCS or local disk, and tonic's TLS already brings rustls; switching them off saves 33 crates and 3.9 MB of 22.3 MB (22,262,720 to 18,367,216 bytes, 283 to 250 crates); `--no-default-features` is a local-only build that says so when given an `s3://` store. The server needs only `GetObject`, `PutObject` and `ListBucket` (`list` requests); it never deletes. *Object-store semantics checked.* A PUT replaces `incidents.json` and `watchdog.json` atomically on S3, GCS and local disk (`object_store` writes a temporary file and renames on disk); nothing emulates rename. S3 and GCS list and read strongly consistently, so the watermark read after a restart (one listing of the attempt and one 64 KiB suffix read of the newest part per rank, counted in a test) sees every part that was acknowledged; an S3-compatible service without read-after-write consistency would break that and is not supported. `list` has the trailing delimiter, so `rank=1` does not list `rank=10` (tested). The 128 MiB quota and the rule "acknowledge only after the PUT succeeded" are unchanged and tested with a failing store: no acknowledgement, the rows stay buffered and the quota stays held. A PUT that reports failure may have landed: the buffer is then **sealed**, it takes no rows until a write of it succeeds, so the retry is the same part under the same name and no overlapping part with other bounds can be left (the alternative, writing the larger part and deleting the stale one, needs `DeleteObject`, which append-only IAM policies withhold, and can leave duplicates if the delete fails). The sender keeps the refused rows and resends. Requests are retried for 30 s (`--store-retry-seconds`); a request refused outright (403, 404) is not retried; a bad bucket or credentials stop the server at startup, with the store's own message, because restoring the watchdog is the first read of the store. A timed flush and SIGTERM write ranks 16 at a time, so SIGTERM against a failing store takes one retry period, not one per rank. *Watchdog across a restart.* Every `watchdog.json` also carries `restart`, per rank the clocks its entry in `ranks` leaves out (recent gaps between batches, which give a slow rank its threshold; the work counter; when the stream last changed; the pauses measured), and `abandoned`. All times in the file are seconds before `written_at_ms`, so the file says how long something had lasted, not when; a restart on another host or after a long outage needs no wall clock, and an age longer than the host has been up cannot panic (`Instant` cannot go back that far on every platform: it is cut to what the clock can show, never to zero). At startup, before any stream is served, the server lists `runs/` once (a delimiter listing), reads each run's status (32 at a time) and takes up every run that is neither finished nor abandoned. Rules: (1) *time the server was not running is not held against a rank*: it could not have delivered anything, and a rank that was active at the stop must not look stalled for the seconds its sender takes to reconnect; each clock carries on from what the file said (after a SIGKILL that is up to `status_refresh`, 3 x `--watchdog-seconds`, before the death, which is forgotten; after SIGTERM it is the moment of the stop). (2) Every restored rank that was not finished has no stream: it is `dropped`, `reconnecting` for the usual time while its sender comes back, then `lost`. (3) A rank that was already stopped keeps its quiet time, so a stall is neither forgotten nor started again: a silent or unresponsive rank keeps that verdict for `--silent-seconds` (a hung process whose connection the restart cut is still a suspected hang, not a lost connection) and is `lost` after it; a lost rank is lost at once. The first file the new server writes already carries the incident (`job_stalled` or `rank_silent`) with the old quiet time, from the file of a killed server and from the `server_stopped` file of a clean stop alike. If its sender reconnects, the rank reads silent again (open stream, the old last progress) and a new batch makes it active. (4) Phase-aware pauses carry over: the phase, how long it had lasted, the work counter and when it last moved, the heartbeat age, and the pauses measured (so `recommended_silent_seconds` survives); a pause is measured without the outage. (5) A run is *abandoned* when no stream is open and every rank has been disconnected or finished for `--abandon-hours` (72, 0 never): it is not restored, and its status stops being refreshed (otherwise every dead run is a PUT every 30 s for ever, and every restart would revive it); a reader then reads the old status as "nothing is watching this run", which is true. A run with a stream still open, however hung, is never abandoned. Finished runs are not restored and their files are not rewritten. A status with no `restart` (an older server's) is not restored. A status that cannot be read is logged and skipped; the rest of the runs are taken up. The new server rewrites a restored run's status at its first look, which also ends the reader's "nothing is watching" message. Cost: one listing and one small read per run at startup, before the server listens (simulated: 1,000 runs at 50 ms a request take 1.8 s); `watchdog.json` grows by about 230 bytes a rank (a 64-rank file is 34.7 KB, 14.9 KB of it `restart`) and is still one atomic PUT. Limits: a rank whose sender is dead and whose run is not abandoned shows as `lost` after every restart; the server cannot tell a dead run from a quiet one, as before. A rank that connected before the restore finished is left alone (the restore runs before serving, so this does not happen). Not covered: GCS (compile-checked only), real AWS, TLS to S3, IAM, real latency.

Incidents are grouped across judged ranks when the kind, step and what they name (layer, router, experts, parameters, modules, as the kind has it) are equal; measured numbers and logged scalars are not part of identity, since they differ per rank for the same fault; a group carries the first rank's incident and a flag for differing numbers, and incidents that differ are listed with their own ranks. Stalls and silent ranks, Flight Recorder and TrainCheck are run-level, once. The file is written by rename only when a rank's (state, attempt, last step, steps, rebuilds), the set of ranks, or the status changed; a rank inside its wait is masked so a part-then-report blip is no news, and the comparison is with what was written, not with the last look, so a rank written as behind and then current again is rewritten (a mutation that compares the masked key fails its test). `--recompute`, `--top-k` and `--rerun` are refused with `--rank all` (a recompute would read every rank's parts and run the detectors a rank at a time on every change, about 8 s a rank at 10,000 steps), pointing to `--rank N`. Measured (8-core M1 Pro, shared with other builds): one look of 64 ranks of 10,000 steps (200 parts a rank, ten incidents a rank) 34 ms, 29 ms when nothing changed, 102 ms at 50,000 steps; a real server with 64 ranks of 1,000 steps 14 ms. Against 250 ms. The first version listed part names with `pathlib` and took 100 ms at 10,000 steps and 418 ms at 50,000 (94% of a look was building a `Path` per part); `_newest_part` now walks names with `os.scandir`, equal on odd trees by test, which also speeds the single-rank watcher. Read first (a short check): PyTorch's Flight Recorder analyzer works in sets of expected, found and missing ranks and names the missing ones, Megatron's straggler report names the slowest and fastest rank, and W&B run groups and MLflow parent runs keep each run's record under an aggregate view; none groups incidents across ranks or separates an unknown rank from a clean one, which is designed here. Not covered: more than 64 ranks, a network file system, S3/GCS, a Flight Recorder dump finding a stuck collective in this mode (the one place a part is opened, to date the dump), ranks at very different steps (all current; the spread shows in `last_step` and the status's `stream` entries), and a run with a rank whose server report is rebuilt for longer than the grace. `sdk/tests/test_watch_all_ranks.py` (33 tests, real server; forty deliberate changes to the code: thirty-eight killed, two equivalent survivors; the first pass of that check was fooled by a harness that ignored SIGINT and by tests that did not vary what an incident names, a rank's move between two unknown states, `world_size` alone, or a new attempt ending at the same step: each got a test).

- [x] **Seeded projection in the replica fingerprint (decided and built Nov 15, 2026).** `replica_spread` carries a third float64 value per parameter, a dot product with fixed weights computed from the element index by integer arithmetic (no random number generator, so training's random streams and every device and rank agree), in the same `all_gather` (24 bytes per tensor). - [x] **Ingest details the specification left open (decided Nov 14, 2026, with the build of `flight.py` and `server/`):**
  - *One long-lived `DoPut` stream per rank, acknowledged only when stored.* The sender keeps one stream open and the server answers with `PutResult.app_metadata = {"end_byte_offset": N}` (JSON, like the request metadata, so fields can be added) only after the Parquet part holding those rows is written. A stream per batch would either write a part every 50 steps instead of every 500, or acknowledge rows that exist only in server memory, and then a killed server would lose steps the sender had already moved past. The cost is that `.offset` trails the file by up to 10 seconds or 500 steps; the end-to-end test kills the server while it holds 100 unstored steps and loses none.
  - *Batches are at most 50 steps and 4 MiB even when catching up after an outage*, so the sender's memory stays bounded; a single line over 4 MiB is sent alone. gRPC keepalive (30 s) detects a dead connection, because a long-lived stream cannot carry a deadline.
  - *Three columns beyond the listed schema:* `step_skipped: Boolean` and `grad_scale: Float64` (written by `scaler=`, added after the schema was drafted), and `extra_json: Utf8`, which carries any key the schema does not know and any value that does not fit its column's type, so nothing is dropped and `row_to_record` returns the original dict. The `moe` field is the `moe_counts` column. Non-finite numbers are real NaN and infinity in the float columns and return to the strings `"nan"`, `"inf"`, `"-inf"` when read back.
  - *The server checks only the key columns* (`schema_version`, `run_id`, `rank`, `step`, and `attempt` when present) and the batch metadata, and writes whatever other columns arrive. A column added by a newer SDK then needs no server release; a schema change in mid-buffer starts a new part, because a part has one schema.
  - *The watermark is read when an attempt's first batch arrives*, from the footer of its newest part (by the last step in the file name; a part with a foreign name is always opened), not for every run at startup, which would list the whole store.
  - *Only the footer is fetched (decided Nov 14, 2026).* One suffix range request of 64 KiB, a bounded range on stores that refuse suffix requests, and a second read only for a larger footer; page indexes are skipped, since the row-group statistics hold the step range. The server's own parts measured 7.2–7.7 KiB of footer on router-only and full captures, so 8 KiB, the first choice, left about 500 bytes; DataFusion's default for the same reader call is 512 KiB, which also covers page indexes. Before this, each part opened was downloaded in full.
  - *Quota.* Buffered bytes are the rows' own Arrow bytes (`get_slice_memory_size`): `get_array_memory_size` counts a decoded message's shared buffer once per column. A batch that does not fit first writes that rank's own buffer; if it still does not fit, the reply is `RESOURCE_EXHAUSTED`. A batch larger than the whole quota is accepted when nothing else is buffered, so it cannot wait forever. Messages up to 64 MiB are decoded.
  - *Setup errors raise at `init`; failures while running never do.* A bad endpoint scheme, a missing `pyarrow`, or `endpoint=` with a sink that has no file raises before training starts. After that the sender only records `last_error`, backs off and retries, and `close()` prints the local path if bytes are unconfirmed. `tensorquill.flight.send_file` sends what a finished run still owes.
  - *Complete lines that are not step records of this run are skipped and counted* (`skipped_lines`), which is what a killed writer leaves when the next process appends after its half line.
  - *`run_id` on the server is limited to letters, digits, `-`, `_` and `.`*, because it becomes a directory name; other IDs are refused with `INVALID_ARGUMENT`.
  - *On `SIGTERM` the server does not wait for open streams*, which never end on their own: it refuses new batches, writes every buffer and exits.
  - *Consequence of watermark deduplication, handled Nov 14, 2026 by attempts (see above):* a run restarted from an earlier step under the same `run_id` used to have its repeated step numbers dropped by the server.
