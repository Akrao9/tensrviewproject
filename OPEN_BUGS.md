- `codebase_review_findings.md`, the first outside review: 87 findings with IDs SDK, DET, CLI and RUST.

**How far to trust a row.** The "Checked" column says who last confirmed it:

- *Run*: reproduced with a script, by a fix lane or by lane T6. *Run on main* means the script was run again on `main` on Nov 19, 2026, after wave U.
- *Read*: seen in the code, not run.
- *Audit*: the audit's claim, not checked again by this project's sessions.
- *Cross-check*: reproduced by the cross-check's author with temporary files and CPU jobs, as that list records; not run again when it was copied here.

Only the rows marked *Run on main* were run again when this file was written. Rows last checked before wave U may have moved.

**Where it came from.** The six CPU proofs of the v1 plan ran on `eade0d1` on Nov 22, 2026 (`wave-af-proof-cpu.md` in the side-session notes, with raw output). Four passed or were measured with no finding: ingest across a 200-step server stop (900 of 900 steps, none twice), scale at 512 and 1,024 ranks, the support envelope, and the three older issues (two not reproduced in 10 runs each; the Linux exit of rank 0 cannot be checked on macOS). Two gave a finding each, and the author said to fix both ("Fix P1-1 ... Fix P5-1 in the same batch").

**P1-1, fixed: a rank already stopped when its stream drops lost its stall.** A rank that read `silent` at `critical` with a suspected hang and was then killed read `reconnecting` with no severity for the whole `--silent-seconds` (300 s by default); the run's incident list emptied and its summary read `active`. Materially wrong live status for a bounded time; no alert lost in the proofs, no data lost, training untouched.
- **The rule now, in both engines.** The server keeps the stall with the rank while its stream is dropped: the rank reads `reconnecting`, then `lost`, with the severity it had, counted on the clock it already had, and `stopped_as` (`silent` or `unresponsive`) in its entry. It is not counted active, and the run's `rank_silent` or `job_stalled` goes on listing it. A rank that was healthy at the drop has the ordinary grace, judged as it read at the drop. A stream that opens again clears nothing; a new step recovers the rank by the rules there were; a newer attempt that takes the rank clears it.
- **One rule for which rank is stopped**, `is_stopped` in `watchdog.rs` and `rank_is_stopped` in `evidence.py`, used by every reader and by the trigger's stall episodes, with nine shared cases (`sdk/tests/fixtures/wave_ah/cases.json`).
- **Tests, committed failing before the fix** (`511b7b1`, `9c76473`; the fix is `a856eec`): 12 server regressions (9 failed), among them a healthy disconnect, a critical disconnect, a warning that becomes critical during the grace, the grace's end with the severity sampled every 5 s and never below critical, a reopen without progress, recovery on a new step, a replacement attempt, an unresponsive rank, and two and three ranks; 14 Python tests (11 failed), among them the trigger across the drop, the loss and the reconnect, a stall first seen while the rank reconnects, and the real server driven through all six steps with a real `Trigger`, which fired once. The real-server test fails with the server binary of `eade0d1`.
- **A visible change besides:** eight pinned status fingerprints of `lane_ad2_tests.rs` were retaken, for the ranks of that fleet that stop and then drop; checked rank by rank that no other rank's entry changed.
- **Not changed, by the decision of Nov 17, 2026:** a server restart does not carry the kept stall. Every unfinished rank gets a fresh window, so a stalled run still reads `active` for that window after a restart (seen again in the proof below, phase D). The documents say so.
- **A healthy rank that is killed** is still called only after `--silent-seconds`, and the run reads `active` until then. That is the grace the author kept; the documents now say what `reconnecting` means.

**P5-1, fixed: the id the trigger handed over was not one `get_incident` takes.** The delivery id (`<run_id>/rank0/non_finite/150`) is unchanged. Beside it the command's document, the webhook body and the environment (`TENSORQUILL_INCIDENT_MCP_ID`) now carry `mcp_id`, `<run_id>/<ranks>/<kind>@<step>` (`#2` onwards for a second incident of that kind and step on those ranks). `get_incident` resolves it for that run and those ranks whatever the server was started on, refuses another run's by name, and answers the delivery id passed by mistake with the id to pass. The payload stays version 1 with one key added; the id is made at each look and is not in the state file.
- **Tests, committed failing first** (`604193d`; the fix is `69a1e0c`): the real `--watch --on-incident` command feeding the real stdio MCP server, for a watcher of rank 0, of rank 1 and of all ranks, against the run folder, each `rank=<n>` folder and the evidence file, on a store a real server wrote in which the two ranks show `non_finite` at step 30 and name different layers: each id finds its own rank's incident and never the other's.
