# TensorQuill capture SDK

The capture SDK, detectors and evidence exporter of the v3 plan. It records what happens inside a PyTorch model during training, cheaply enough to leave on, and in a way that survives `torch.compile`.

```python
import tensorquill

model.to(device)
session = tensorquill.init(model, routers={"blocks.3.router": 128})  # before torch.compile
# Router load only, cheap enough to leave on. For debugging, add capture="full".
model = torch.compile(model)

for batch in loader:
    loss = model(batch).mean()
    optimizer.zero_grad()
    loss.backward()
    optimizer.step()        # TensorQuill counts the step here

session.close()
```

To add TensorQuill to your own training job, follow [Run TensorQuill on your own job](RUN_ON_YOUR_JOB.md).

Each optimizer step becomes one JSON line in `tensorquill-out/<run_id>.rank<rank>.jsonl`.

A record holds the training forwards of its step only. Evaluation statistics are not recorded: the capture hooks leave out a forward when the module they watch is in eval mode and gradients are off (`model.eval()` with `torch.no_grad()` or `torch.inference_mode()`, as Lightning, the Hugging Face `Trainer` and Accelerate's examples evaluate), and inside `with session.phase("eval"):` when either one is. Forwards before the first step (Lightning's sanity check) and the probe's are left out the same way. The forwards of a step's gradient-accumulation microbatches are all counted. Not left out: an evaluation in train mode with gradients on, one in eval mode with gradients on, or one in train mode without gradients, unless it is inside `session.phase("eval")` (the last two then are); training with modules kept in eval mode and gradients on is recorded as before. **Training in eval mode under reentrant activation checkpointing** (wave AF), whose first forward runs without gradients and so reads as an evaluation, is counted from its recomputation inside backward, one recomputation for each forward held, in eager mode; the counts and block statistics then equal those of the same model in train mode. Under `torch.compile` the hooks count it as before, since Dynamo runs a reentrant checkpoint as a non-reentrant one. Where a router's forward was held and nothing of it was recomputed on a step (a reentrant checkpoint with no input that needs a gradient), the router is left out of that record's `moe`, `moe_stats` and `moe_top_k` instead of being written as zeros, and the block has no `layers` entry; a router not called on a step still writes zeros. What cannot be told apart: an evaluation forward without gradients made inside a step before a held training forward (one forward is counted, with the recomputation's values), and a module forward run inside backward that is not a checkpoint's recomputation, such as one in a backward hook (counted where a forward is held). Batches noted with `session.data` or `watch_loader` and the data-loader wait outside `session.phase("eval")` are not forwards and still count toward the next step.

There are two capture modes. `capture="routers"`, the default when `routers` are given, records only MoE router load (`moe`, `moe_stats`, `moe_top_k`) and the learning rate: this is the always-on mode. `capture="full"`, the default for models without routers, adds block activation statistics, gradient norms on every step and a weight check every 50 steps: this is the debugging mode. `layers`, `grads` and `weights` override either mode. See [Capture-mode decision](#capture-mode-decision) for the measurements behind it.

- **`layers`**: mean, standard deviation, absolute maximum and zero fraction of each watched module's output. By default the watched modules are the model's repeated blocks, such as each transformer decoder layer: the children of every outermost `ModuleList` of two or more composite modules, the unit PyTorch's FSDP `transformer_auto_wrap_policy` wraps. A list counts when its children share one class, or, for a list that mixes classes, when every child is composite: a hybrid stack is one stack, and an encoder-decoder's two stacks are both watched. A list inside a block already taken (an MoE layer's experts) is not, a module reachable from two lists is watched once, and a list whose items are whole sub-models (`ModuleList([encoder, decoder])`) is taken as two blocks, not their layers. A model without such a list falls back to every leaf module with parameters, which `layers="all"` also selects, and a model that is itself one leaf module (a bare `nn.Linear`) is watched under its class name, so the activation detectors can fire on it too; for Granite that is 171 modules against 24 blocks.
- **`grad_norms`** and **`grad_norm`**: the L2 norm of each parameter's gradient and their total. A gradient that cannot be read, such as one on `meta`, is left out on its own and named once under `grads_not_read`; the others keep their norms. The parameters recorded (here, in `weight_norms` and in `update_rms`) are those trainable when `init` runs, and a parameter frozen then and unfrozen later (a fine-tuning schedule that unfreezes layers) from the first step on which it is trainable, under its own name, said once in a warning; the records before that step do not name it, and the detectors compare only the parameters two records both name, so its arrival raises nothing (shown with both engines on a CPU toy whose first layer is unfrozen at step 120). A parameter added to the model or replaced after `init` is not recorded and is named once in a warning. The drift check across GPUs keeps the parameters chosen at `init`. **A stated limit of the router-only mode:** there a parameter frozen at `init` and unfrozen later is never recorded, with no warning, also when `session.record_grads()` is called by hand, which records only the parameters trainable at `init`. With `capture="full"`, or `routers=...` with `grads=True`, the same parameter is recorded from the step it is unfrozen.
- **`weight_trends`** (in `evidence.json`, from `build_evidence`): each kind of parameter's latest norm relative to its first recorded norm, as numbers only.
- **`weight_norms`** and **`weights_unchanged`**: each parameter's L2 norm after the optimizer step, and which parameters' norms are exactly unchanged since the previous check, plus `optimizer_ownership` (whether an optimizer that stepped holds each trainable parameter, or why that is unknown). Checked every 50 steps by default (`weights=N` for every N steps, `weights=False` to turn it off); a check also records that step's gradient norms.
- **`schema_version`** (1) and **`ts`**: the record format's version, and when the step ended, in Unix seconds.
- **`attempt`**: when the `tensorquill.init` that wrote the record started, in Unix milliseconds. A job that resumes from an earlier checkpoint under the same run ID writes some step numbers again; the attempt tells the new records from the ones they replace. A resume that does not share the run ID (no `run_id=`, tracker or launcher ID) is a second run with a file of its own, and the resume checks do not reach across the two.
- **`lr`**: each parameter group's learning rate after the step.
- **`step_skipped`** and **`grad_scale`** with `init(..., scaler=)`: whether the loss scaler skipped this optimizer step on Inf or NaN gradients, and the loss scale used.
- **`clip_grad_norm`**: the total gradient norm before clipping, in any capture mode, when your training clips gradients. TensorQuill records what `torch.nn.utils.clip_grad_norm_` returns for this model's parameters while the session is open, which also covers Lightning's `gradient_clip_val` (Lightning calls that function and discards the result). A call counts when any of the parameters it is given is one of this model's trainable ones, so a LoRA or PEFT model whose first parameter is frozen is covered. Only an L2 norm is recorded (`norm_type` 2, the default): a call with another norm type records nothing as `clip_grad_norm`, and the spike detector then reads `grad_norm` where that is recorded, which is taken after clipping. It costs nothing extra: the norm is computed anyway and stays on the GPU until the next flush. Code that imported the function before `init`, or computes the norm elsewhere, can call `session.record_grad_norm(norm)`; with Megatron, pass the `grad_norm` that `optimizer.step()` returns. `clip_norm=False` turns the automatic recording off.
- **`moe`**, **`moe_stats`** and **`moe_top_k`**: tokens routed to each expert, plus router entropy, diversity (`exp(H)/N`), and dead-expert count/fraction, for every router you name (works whether the router outputs integer indices or floating-point logits with `Router(n_experts, top_k=...)`). Set `top_k` for top-k routers; the detectors need it. A router is read in one of three ways: by default the first integer tensor in its output is taken as the chosen expert indices, or else the top-`top_k` of the first floating-point tensor whose last dimension is `n_experts`; `Router(n_experts, top_k, indices=fn)` takes the indices from `fn(output)`; or name the module inside the router whose output is its logits. A router whose output cannot be expert indices is not counted for the rest of the session and leaves no entry in `moe`, `moe_top_k` or `moe_stats`: an integer tensor that does not hold `top_k` ids for each token the router was called on (nanoMoE's router returns per-expert counts first; two ids a token under a `top_k` of one is refused too, and the reason names both numbers); a `top_k` above `n_experts`, however the router is read: an integer tensor, an `indices=` function, a routing map or logits (`top_k` equal to `n_experts` is counted); with no integer tensor and no routing map, a first floating-point tensor whose last dimension is not `n_experts` (a block that returns its hidden states first); an output the counting cannot read, judged from its type and device alone: on another device than the counts (a model split across GPUs; the fix offered is an `indices=` function that returns the indices on the counts' device), a DTensor, a sparse tensor, uint16/32/64 indices or float8 logits; or an `indices=` function that raises, returns something other than an integer tensor on the counts' device, returns the wrong size, or returns a value at or above `n_experts` on any step (a negative value is no assignment, below; judged from the counts after their copy to the CPU, so with no added sync; a router counted until then keeps its earlier records). In eager mode any other error in the counting is caught and refuses the router the same way; none is raised into training (the refusal's warning is, if warnings are turned into errors). The session warns once, the first record written after says why under `moe_refused` with how to have it counted, for how that router was named, and the evidence and the server list it under `not_checked` (`check: "router"`), which makes `moe_imbalance` and `starved_experts` `unavailable` and the run `degraded`, even beside a router that is counted. An output with no integer or floating-point tensor at its top level (a dict, `None`) is refused too, and a default router's integer ids are judged on their values as `indices=` ids are (below). Not checked: the size when the router's first argument has fewer than two dimensions, since the token count is read from it.
- **When router counts are the routing.** TensorQuill reads a router's output in this order: an `indices=` function; an integer tensor, taken as the chosen experts; a bool routing map `[tokens, n_experts]` beside a float tensor, as Megatron's `TopKRouter` returns, counted as it routes, leaving out entries whose paired probability is zero (the padding of `pad_to_capacity`); and otherwise the plain top-`top_k` of the scores it hooks. With a map, an assignment dropped at capacity is not counted (a CPU stand-in that follows Megatron's code, Nov 19, 2026; Megatron itself not run); where the output holds logits, probabilities and a map, the logits are the pair and padding is counted. For integer indices, from the output or from `indices=`, a negative index is no assignment (Megatron uses -1 for no route): it is not counted, and their number is written as `moe_unassigned`; an index at or above `n_experts` refuses the router with a reason, and nothing is raised. With a routing map, the entries left out are written per expert as `moe_left_out`, so each expert's map count is `moe[e] + moe_left_out[e]`. Both fields are written as explicit zeros when the check ran and found none, and are absent for a router the check does not apply to; a record from before these fields has neither, which a reader should take as unknown, not zero. The length check asks for the token count times the declared `top_k`, from the output and from `indices=` alike; any other count refuses the router. A `top_k` above `n_experts` refuses the router on every path, an `indices=` function that returns that many ids a token and a routing map included (`Router(8, 12, indices=fn)` was counted, 1,440 assignments for 120 tokens, before Nov 20, 2026). The plain top-k is the model's routing only when the model picks the plain top-k of those same scores. It is not when the model adds a per-expert balancing bias used only for the choice (DeepSeek-V3, Motif 3 and Mamoda2.5 do), adds noise to the router logits after the hooked module, or applies a capacity limit after it. Then the counts are wrong, and a healthy model can get `moe_imbalance` with dead experts. On a CPU toy with such a bias the model routed 1,703 / 1,406 / 1,003 / 1,008 tokens and TensorQuill counted 5,120 / 0 / 0 / 0. For a bias the function can reach, pass `indices=` with a function that applies it, such as `Router(n, top_k, indices=lambda out: (out + bias).topk(top_k, dim=-1).indices)` where `bias` is the model's own bias tensor; on the same toy that gave the model's own counts. For noise or a capacity limit, name the module whose output holds the chosen experts, since an `indices=` function sees only the hooked module's output. No real model has been tested this way.
- **A shared expert is not seen.** A shared expert takes every token without passing through the router, so the router hook has nothing to count for it, and no MoE kind would report it degrading.
- **`scalars`**: values you pass to `session.log`, such as `session.log({"train/loss": loss})`. A one-element tensor is copied on its device and moved to the CPU with the rest of the step data, so logging a CUDA loss adds no GPU sync, as Lightning keeps logged values on the device until it writes them. Call it before `optimizer.step()`, because with automatic step counting the step ends there; a value logged after it, in training, belongs to the next step. **Values logged after a step (Nov 24, 2026).** Inside `with session.phase("eval"):` (or `set_phase("eval")`, which the Lightning and Hugging Face callbacks set around an evaluation), a value is recorded on the newest step, the one the evaluation followed, while that step is still in memory: the ring's last row, or the step kept back when the ring last filled, until the next step ends, a `flush()` or `close()` (nothing is flushed on a timer or a phase change, so a slow evaluation does not move it out). A name logged twice there keeps the last value. A value still pending at `close()` (a final evaluation, or the last loss of a loop that logs after `optimizer.step()`) goes on that step too, unless the step already holds its name. A record already written is never changed: with no step in memory (a baseline evaluation before the first step, or one after `flush()` with no step since) the value is left out, and a warning says so once per session; before, it was written on the next step. A step of its own for such a value comes with protocol 5's scalar-only record. A late tensor is copied on its device and read with that step's data, never on its own. Leave the phase as you found it: a value logged while `"eval"` is still set goes on the step before, until the next step ends the phase (the Hugging Face callback sets it back when a training step begins). `session.log(..., step=...)` raises `TypeError`, as an image does: an explicit step is not supported yet and comes with protocol 5; a key `"step"` in the dictionary (`session.log({"step": 5})`, as W&B users log a custom x-axis) is an ordinary scalar. Pass the same values your tracker logs: TensorQuill does not capture the loss on its own, since patching `Tensor.backward` would miss Megatron (which calls `torch.autograd.backward` directly) and record the scaled loss under `GradScaler`. Every incident in the evidence carries the logged values at its step with the median of the previous 50, and the Rerun export plots them under a Logged tab.

## Support: what is captured, and what has been verified

Two different things. The first table is what TensorQuill records for each kind of model: that is the code's scope, dense and MoE transformers trained with PyTorch. The second is which combinations of model, framework and hardware have actually been run, and where. A combination that is not in the second table as run on a GPU has not been verified on one, whatever the first table says is captured.

## What is not built or not verified

- **The agent loop has not met an agent.** The MCP server has been driven by a scripted client only, and the trigger by a local script and a local HTTP server. No agent session has been started by the trigger or has used the server.
- **Detectors on the server's Parquet, limits.** The reader takes a local path, so parts in S3 or GCS cannot be read yet. A directory holding several ranks is read one rank at a time, and only that rank's `rank=` folder is opened; `--rank all` reads every rank's report and no part (see "All ranks at once"). On a `.jsonl` file, or on a store whose server did not report (`--no-detect`, or `--recompute` here), `--watch` reruns the detectors over the whole run on every update, so an update takes time in proportion to the run's length: 0.4 s at 500 steps and 8.1 s at 10,000 on a Granite-shaped 64-rank store (see [Detector benchmark on 64 ranks](#detector-benchmark-on-64-ranks)). Since Nov 21, 2026 a watcher with the Python detectors (`--watch --detectors python`, or `watch()` in Python) keeps what it has judged and judges only what is new; the command line's `--watch` uses the Rust detectors unless told otherwise, and those still judge every record at each rebuild. Those two figures are from before that and were not measured again on that store (see [A score, four measurements and two changed rules](#a-score-four-measurements-and-two-changed-rules) for what was measured). On a store the server is judging it reads the server's report and no part (see [Watching a run the server is judging](#watching-a-run-the-server-is-judging)).
- **Streaming, not verified:** GCS stores (S3 ran against an emulator only, see "Storing to S3 or GCS"), more than two ranks from real training processes at once (two pass on CPU, `tests/test_two_ranks_e2e.py`), a remote server and a GPU job. A token from the Python sender, TLS on loopback (`--tls-cert`/`--tls-key` with `TENSORQUILL_TLS_CA`), a non-zero rank, and forked `DataLoader` workers while the sender runs each pass an end-to-end test on macOS and on Linux in CI (as of `f30e639`). In a forked child the sender does nothing: the fork copies the object but not its thread, so `close()` there returns at once and the parent keeps streaming. No deadlock was seen in either fork test, but gRPC's behaviour across `fork` differs by platform, so a Linux machine with a CUDA job is still worth checking. The sender's memory bound during an outage is measured with `tracemalloc`, which does not see gRPC's own allocations.
- **What was checked, limits.** A kind counts as checked from the first record that carries its input, before its rule has the history to fire; each kind says so with `enough_history`, which is a floor on the count of records and not a promise about every parameter or module. In the all-ranks view `duplicate_batches` reads `checked` when the server's status lists every judged rank in `ranks_compared`, which it writes whether or not it finds a duplicate; a rank it did not compare, as right after a server restart, reads `not_configured` (see "What was checked").
- **One Rust copy of the detectors is not finished.** The Rust path gives the incidents and the MoE samples. On the command line the Rust detectors are the default when the binary and `pyarrow` are there; in Python, `build_evidence` and `watch` default to `detectors="python"`. No Python detector is deleted. On the command line `--watch` judges with the Rust detectors unless it is told `--detectors python`, and runs them through `tensorquill-server detect` over every record read so far at each rebuild made here; in Python, `watch()` defaults to the Python detectors. `--rank all` runs no detector here and reads the reports the server wrote. The router names, sizes and experts per token in the evidence are still read from the records in Python.
- **Replay** of a flagged batch (Tier 3). The probe pass (Tier 2) has run on a GPU with SmolLM2-360M, not yet with Granite.
- **The Rust detectors are the default on the command line only, and the Python ones are all still here.** On the command line the Rust detectors are the default when the binary and `pyarrow` are there; in Python, `build_evidence` and `watch` default to `detectors="python"`. `--detectors rust` covers one read, `--watch` and `--rank all`, and `duplicate_batches` across ranks has a Rust path without a server (`detect --run`). The per-step MoE `samples` come from Rust on that path too. What is left before the Python copies can go is the switch of the default in Python, and then deleting them. Not verified: Linux, any run longer than 10,000 steps, `detect --run` on more than four ranks or on a real multi-rank capture, and the release binary in the tests (they use the debug one; the release one was only timed). See "The Rust detectors on a local file".
- **Multi-rank reporting.** Every rank writes its own file. The watcher has an all-ranks view of the server's reports (`--rank all`); what stays per rank is the Python detectors, the per-step samples and `--rerun`.
- **Detector thresholds are untuned.** The gradient-spike factor (5× the median of the last 50 recorded steps, and for one parameter 3 steps in a row at 5× its own), the top-k diversity drop (0.6 of its recent median), the starved-expert ratio and the stalled-weight check have been checked on synthetic cases and, for the MoE rules, on one Granite capture. Weight norms, learning rates and the spike and stalled-weight detectors have run on the Granite captures from the A100 and RTX PRO 6000 runs below, but not against a planted failure of their own kind on a GPU; the steps they flagged there are unconfirmed.
- **One extra compiled graph on PyTorch 2.6.0, when you compile your own clipping.** Observed on CPU with the `eager` backend (Nov 23, 2026), on the two versions measured. On PyTorch 2.6.0, `clip_grad_norm_` compiled on its own makes no graph, so a compiled function that clips compiles nothing for the clip; with TensorQuill on, its reading of the pre-clipping norm is compiled there once, at the first step: one graph more than without TensorQuill. On PyTorch 2.15.0 the clip compiles on its own and the first step compiles the same number of graphs with TensorQuill as without. ## Seeded Granite collapse on CUDA

The Colab run with `--collapse-layer 12` passed on the RTX PRO 6000 with PyTorch `2.14.1+cu130`, Inductor, and CUDA graphs disabled. The healthy run above supplies the overhead gate measurement. The gradient-norm cost in this run was **+1.78%**, against **+2.60%** in the healthy run; one round without gradient norms took 78.078 ms against about 68–69 ms for the others, so treat that cost as roughly 2–3% until it is measured more often.

### Viewer check

`granite-router-only.rrd` opened in the stock Rerun 0.43.2 viewer (headless, screenshots at steps 400 and 450). At step 450, layer 12 showed 8 amber and 24 red cells, the layer 12 expert table listed experts 1–8 at 12.50% and the rest at 0.00% with their change from step 449, and layer 12's diversity dropped to 0.25.

The check found a mismatch between the heatmap and the detector. Experts with no tokens in a sample were always red and labelled Dead, including transient gaps in healthy layers that the detector deliberately ignores; one appeared at step 400 and three outside layer 12 at step 450. Commit `40ce26a` colors those experts near-black (`IDLE_COLOR`), labels them Idle, keeps red for experts in the detector's dead list, and prints 12.5% instead of rounding it to 12%. The fix was then confirmed on the real capture by exporting a later run's `granite-router-only.jsonl` with the current SDK.

### Starved experts

That export showed 1,303 zero-token cells across 650 steps, mostly from a few experts that were almost never used. Layer 5 expert 25 had no tokens in 514 of 650 steps and an average share of 0.005%, against 3.125% for an even share; layer 8 expert 21 had none in 356 steps. These experts came that way in the pretrained model. The per-step detector never flags them, because one empty expert in a single step is ordinary noise.

`build_evidence` now flags an expert as starved when its share over the last 50 samples (`starve_window`) is below 10% of an even share (`starve_ratio`). It waits until an even share would have received at least 100 assignments in the window, and dead or overloaded flags take precedence. Starved experts are violet in the heatmap, `Starved` in the expert table and listed in the summary, worst first. Other zero-token experts are now gray rather than near-black, which was hard to tell from dark blue.

On the Granite capture it flags 20 experts in 15 layers, from 0.018% to 0.312% of assignments; 14 are flagged at step 49, the first full window. The 10% ratio is a starting point: about a third of those sit just under it, so a lower ratio would list only the most extreme few. The collapse result is unchanged.

## Detectors added for the failure list

From the [failure list](../TensorQuill%20failure%20list.md), entries 3–6 and 12:

- **Top-1 and top-2 overload.** An expert's assignment share must exceed the largest of the configured base threshold (35% by default), 1.5 times an even share, and an even share plus three standard errors. Dead experts can trigger an incident independently and never lower the overload threshold.
- **Top-3 and higher overload.** Once a router has ten unflagged samples, its diversity must fall below 0.6 times the median of its last 50 unflagged samples, and a flagged expert's selection rate must rise by at least 25 percentage points. Leaving flagged samples out of the baseline keeps a persistent collapse visible. During warm-up, a router that already has significant dead experts can attribute overload to experts above both twice an even assignment share and an even share plus three standard errors. Each sample records the rule it used. Use `python -m tensorquill --top-k 8` for captures made before `moe_top_k` was recorded.
- **Weights not updating.** Every 50 steps by default, the capture computes every parameter's norm in float64 and compares it with the previous check; `weights_unchanged` lists the parameters whose finite float64 norm is exactly the same. That is necessary for an unchanged weight, not sufficient: two different weights can share a norm (two rows swapped, for example). A parameter that was not compared at a check is never listed: the first check, a norm that is not finite or could not be read, and a parameter with no elements. A parameter with a finite non-zero gradient whose norm is unchanged on 3 checks in a row (150 steps by default) is reported as a warning (equal norms do not prove the weights are equal), for example because it was left out of the optimizer. Since Nov 15, 2026 each weight check also records `optimizer_ownership`, and the incident reports whether an optimizer that stepped holds the stalled parameters: `known`, or `unknown` with a reason when ownership cannot be established (`auto_step=False`, DeepSpeed ZeRO, Megatron, FSDP1). Since Nov 16, 2026 every parameter is judged on its own history: the incident is still dated at the first step anything stalled, and its `onsets` list each later step at which more parameters stalled, with their names (those not shown unchanged at an earlier check first), how many of them were (`trained_before`: changed, or not compared, at an earlier check; the record does not tell the two apart, so it is not proof that the weight ever moved) and the optimizer evidence for them, so a freeze that begins after the bf16 norm weights have stalled is named at its own step; `stalled_total` counts every stalled parameter and `weight_dtypes` (recorded at each weight check) says how many trainable parameters have each dtype. A check breaks a parameter's streak whenever the parameter is missing from a written list, with or without a gradient at that check, and the parameter stays tracked, so a later stall is still reported. A listed parameter with no gradient entry at that check holds its streak; one with a zero or non-finite gradient resets it. A step with a non-finite total gradient norm adds no stall evidence, though its resets apply. The first version compared float32 norms, and on the A100 run below it reported 147 of 218 parameters from step 1: a bf16 weight under a 1e-5 AdamW step changes in only a few elements per step, which a float32 norm often misses (`model.layers.7.self_attn.k_proj.weight` kept the same float32 norm for 128 steps while changing). Float64 norms resolve those changes. bf16 RMSNorm weights near 1.0 are still reported, correctly: their step size in bf16 is about 0.008, so a 1e-5 update rounds away, and in a CPU simulation such a weight was exactly unchanged on 273 of 650 steps. Each check reads every weight once, with no copy, accumulated in float64; on Apple MPS, which has no float64, the check is off. Captures made before `weights_unchanged` existed are not checked. The check runs every 50 steps rather than every step because the read alone costs about 1.5 ms for Granite's 2.6 GB of bf16 weights on the RTX PRO 6000, about 2% of a step, whatever arithmetic is used; with float64 on that GPU it measured about 3.7 ms. wandb.watch (every 1,000 batches by default) and TrainCheck (`sampling_interval`) sample their weight checks for the same reason. At every 50 steps the average cost is under 0.1 ms per step, not yet measured on a GPU.
- **Gradient spikes.** Two rules, and the incident is the first either establishes. The total: a step whose total gradient norm is at least 5× the median of the previous 50 recorded steps; the report ranks parameters by their own spike and names the one that started rising first. One parameter (`"trigger": "parameter"`, since Nov 16, 2026): a parameter whose own norm stays at least 5× its own median for 3 recorded steps in a row, whatever the total does, dated at the first of those steps and known two recorded steps later. A small parameter cannot move the total (a `k_proj` holding 0.2% of it, times 100, moves it 1.02 times). Three in a row comes from the real captures: in six recorded Granite captures (650 steps, 218 parameters; the rule was chosen on two and checked on the other four) a single step at 5× happened 277 to 473 times and two in a row 2 to 15 times, never three, nor on the steps before the seed in three SmolLM2-360M captures, while each seeded fault held it from its seeded step for as long as the capture ran. Norms that are part of such an excursion stay out of the parameter's median. On the SmolLM2 block-8 capture, where the total reached 3.9× and nothing was reported before, it reports step 250 with `model.norm.weight` (62×) and `model.layers.8.input_layernorm.weight` (9×), the seeded block. A single-step jump in one small parameter is still not reported: it cannot be told from the healthy ones.
- **Update-size jumps** (opt-in, `tensorquill.init(model, updates=True)`; built Nov 17, 2026, CPU-tested on a toy only). After each optimizer step the capture reads Adam's or AdamW's own state and records the RMS of the update to each parameter as `update_rms` (`lr · m̂ / (√v̂ + ε)`, weight decay left out, no copy of the weights). `update_spike`, an anomaly, flags a step where the largest of them moved from the step before by more than `baseline / (0.05 · √rise)`: the rule of Altenbernd et al. ([arXiv 2604.00726](https://arxiv.org/abs/2604.00726), eq. 13), with `rise` how far the total gradient norm before clipping rose and `baseline` the mean of that change over the last 100 comparable steps that were not flagged (`update_window`). The paper takes the mean once, over the learning-rate warm-up, which the records do not say; a mean frozen that way flagged a clean toy run, and the mean of the last steps did not. The incident names the parameters whose own update moved most.
  - *Limits.* The rule is not calibrated on any real run: on a CPU toy its worst clean step reached 0.75 of the limit. After a flagged jump, the fall back joins the baseline and dulls the rule for the next 100 steps. Any other optimizer is not read, and the evidence says why under `not_checked` (`update_size`). A run that clips through a function TensorQuill does not see has a flat total, so nothing is flagged. A clean check rules no fault out: the paper detected under half of its injected faults at this setting.
  - *Cost, CPU only.* On an M1 Pro laptop under load, the read took about 0.47 ms a step for 28 parameters holding 21,760 values and 3.3 to 5.2 ms for 28 parameters holding 3.2 million. It also turns on per-parameter gradient norms on steps where clipping was not seen. Nothing is measured on a GPU, and the paper's 1% is the paper's.
- **Repeated steps.** Step numbers written twice by the same rank where that is not a resume from a checkpoint: within one attempt, or by a later attempt that starts the numbering over, as after a resume without `start_step`.
- **Activation spikes, drift and dead outputs** (full capture). Each watched module is compared with its own history, because trained LLMs carry large outliers by design: in healthy Granite the largest value in middle blocks is 740–840 times the standard deviation, so a fixed outlier threshold would fire at step 0. A spike is `abs_max` or `std` at 5× its median over the previous 50 records, and the incident lists the first module in the model first, then the rest by ratio: a change in one block's output travels down the residual stream, so every later block shows it and the largest ratio is in the last of them (a fault seeded in block 16 of 32 reached blocks 16 to 31, largest in 31), while the first module is where it showed first; drift is the median of a module's last 10 records of `std`, or of the outlier ratio `abs_max / std`, 3× above or below the median of the 50 records before those 10, judged from the module's 110th record (until Nov 21, 2026 the baseline was the module's first 50 records, which a model trained from scratch outgrows; see [A score, four measurements and two changed rules](#a-score-four-measurements-and-two-changed-rules)); dead outputs are a zero fraction 0.25 above its baseline. On the healthy Granite capture (24 blocks, 650 steps) one-step jumps peaked at 2.2× and drift at 1.27×, and nothing was reported. A weight blown up 50× in one block of a test model was reported at that step. It judges the block's output as a whole, so growth confined to a few ordinary channels is invisible once the output holds massive activations: in SmolLM2-360M's block 16 (A100, Nov 15, 2026) `abs_max` is about 20,000 and `std` 31 to 37, and two ordinary channels times 100 moved `std` 1.07 to 1.14 times and `abs_max` 0.95 to 1.07 times although the loss went from 2.3 to 6.9. Growth of the massive channels themselves, or of the whole block, is seen (both are seeded by `--fault`, below). Per-channel statistics would see the rest; they are not captured, and what they would cost is not measured. Kurtosis, the outlier measure used in FP8 training research, is not captured, and `abs_max / std` is not a stand-in for it: the ratio is over a whole block output and is set by its single largest value, where that research takes kurtosis per token and averages it, and found its early sign on the query, key and value tensors, which TensorQuill does not hook. Kurtosis would need a second pass over each module's output inside the compiled graph.
- **Learning rate** is recorded per step and logged to the Rerun recording with the total weight norm.

## Capture-mode decision

Decided on Nov 13, 2026, after Stage 3: **router-only capture is the default for MoE models, and full capture is an opt-in debugging mode.**

- **Measured cost on Granite, RTX PRO 6000:** router-only +0.02% to +0.78% across three runs; full capture with block defaults +4.15%, of which about 1.5 ms is gradient norms on every step and 0.85 ms block activation statistics. On the A100, router-only was +1.06% to +1.33% at one commit and +0.41% to +0.95% in a later profiling run (see "Where the A100 router-only overhead goes"). The gate protocol (`moe_dogfood.py`: three paired rounds of 200 steps after 50 warmup steps; commit `2b56eac`, Nov 15, 2026) read router-only +0.70% (64.97 to 65.42 ms per step; rounds +0.76%, +0.67% and +0.56%), full capture +4.11%, and gradient norms +3.42% (+2.25 ms) over full capture without them; the layer-12 collapse was found at step 450 with diversity 0.25 as before.
- **Why not sample gradient norms to bring full capture down:** it would still be about 2%, because the block statistics run inside the compiled graph on every step and cannot be sampled without extra compiled variants; and most gradient spikes last one step, so sampling would miss them.
- **What comparable tools do:** detailed per-layer monitoring is sampled or opt-in. Composer's `ActivationMonitor` runs every N batches and warns that it adds overhead; wandb.watch defaults to every 1,000 batches and its docs say logging every step can significantly slow training; Lightning documents per-layer `grad_norm` as a debugging step. Always-on profilers aim for about 1% or less.
- **Why routers are the right always-on signal for MoE models:** a 2026 paper ([Mechanism-Aligned Observability for Training Instability of Large Language Models](https://arxiv.org/abs/2606.28116)) argues that the loss and the gradient norm show a fault late, and that in an MoE model the router is the place to look. What it measures there is the entropy of each token's routing distribution before the top-k choice, which needs the router's logits. Router-only capture records something else: how many tokens each expert received, and the entropy of that load. The paper says the two can part: routing can grow more concentrated per token "while the selected expert set and aggregate assignment counts remain unchanged". So the paper supports watching routers; it does not show that load statistics warn early.
- **What router-only gives up by default:** layer statistics, per-parameter gradient norms, stalled weights and non-finite gradient detection. Turn on `capture="full"` while investigating.
- **Gradient spikes stay on in router-only mode when the run clips gradients.** Training loops that clip compute the total gradient norm on every step; TensorQuill records the value `clip_grad_norm_` returns (`clip_grad_norm`) and the spike detector uses it, without naming a parameter. PyTorch's `clip_grad_norm_` returns the pre-clipping norm as a tensor, Lightning's `Precision.clip_grad_by_norm` discards it, and Megatron's optimizer returns it from `step()`, which is why both automatic recording and `record_grad_norm` exist. Tested with Lightning 2.6.5's clipping path; not yet run on a GPU.

**The automatic drift check (Nov 20, 2026, the SDK-22 wave).** A session given `replica_group=` issues no collective of its own, inside a training step or at `init`, and waits for no other rank. On each scheduled step (`(step + 1) % replica_every == 0`, 50 by default, as Megatron's `check_weight_hash_across_dp_replicas_interval`) each rank records its own observation of the compared parameters under the record's `replica` key: for each parameter its shape, dtype, float64 norm, sum and a projection seeded by its name (`name-v1`), and an exact 64-bit signature of its bits, shape and dtype (`fold64-v1`); a parameter it could not read is listed under `unread` with why. The record also names the start of the job it belongs to (`launch`, a nonce rank 0 makes at each `init` and shares through the process group's store beside the run ID) and the global ranks it is to be compared with (`group`). `REPLICA_OBSERVATION_CONTRACT.md` at the repository root is the record's definition. The observation is computed on the device and moved to the host with the rest of its block of steps, so it adds no synchronisation to the step.

**The verdict comes later, from a reader.** The comparison is made by a reader that has every rank's records: the server's cross-rank stage, or the all-ranks reader on local files. `replica_drift` is raised when every rank of the group has an observation for the step and their fingerprints spread more than the tolerance (`1e-6`). A rank whose records have not arrived leaves the step `insufficient`, never clean, until they do. So the check costs a scheduled step only its own reading, and the verdict is known one server status interval (`--watchdog-seconds`) or one look of a watching reader after the last rank's records arrive, not inside the step. Signatures that differ while the fingerprints agree are shown as evidence and raise nothing yet.

**What the evidence says of it.**

- **`replica`** is the cross-rank result, as the contract spells it: `v`, `tolerance`, `steps` (each with its `launch`, `group`, `coverage` and what was compared) and `replica_drift`. Local rank files are compared by the Python reader when a run's files are opened together. For a server's store the object is taken from `watchdog.json` as the server wrote it, and no part is opened for it.
- **`replica_not_stated`** says why a store's view has no result: the status has no `replica` object (an older server, or one started with `--no-detect`), or one that cannot be read.
- **The incident.** The first drift from observations is one `replica_drift` run incident with `source: "replica"`, its `launch` and its `group`. A gathered spread on the same step is named under `also`.
- **`kind_checks.replica_drift`** carries `coverage`: how many step entries there are, how many compared fingerprints, the ranks missing from any of them (`missing_ranks`) and the latest steps that were not compared, each with why. A step that is `insufficient` or `not_established`, or complete with nothing compared, does not read as checked. With no step compared the kind is `not_configured` in one rank's evidence and `unavailable` in an all-ranks view, which makes the run `degraded`; a run whose every step is a group of one rank is `not_configured` in both. `signatures_differ` lists the steps where signatures differ.
- **`ranks_in_source`** is on one rank's evidence picked out of a file that held other ranks too, and lists every rank the file held.
- **Which rank a drift is attributed to (Nov 20, 2026).** The cross-rank result, `compare_replicas`' and the server's `replica` object alike, gains `attribution`, a list present only when it has an entry. For a step with complete coverage and a parameter on which the ranks differ, it says which ranks stand apart, once by fingerprints and once by signatures. Each entry has `step`, `launch`, `group`, `parameter`, `by`, and a `verdict`: `attributed` with `outliers`, or `inconclusive` with `why` (`two_ranks`, `no_outlier` or `no_majority`). Two ranks that differ establish a divergence and name no rank. The `replica_drift` incident carries the fingerprints' entries for its step, and its text names the ranks; an entry by signatures alone is evidence and raises nothing.
- **In the all-ranks view (Nov 20, 2026).** `head_trends_by_rank` is a list of `{rank, head_trends}`, each judged rank's head numbers from the report or evidence the view already reads. **The two explicit calls are collectives.** `tensorquill.distributed.replica_spread(params, group)` and `session.record_replica_spread(group)` each issue a small exchange and then, when every rank can take part alike, one `all_gather` on `group` (32 bytes per parameter per rank, 24 with `replica_projection=False`). Every rank of the group must call them, on the same step, and each call waits for the others as any collective does: a rank that never calls leaves the others waiting until the process group times out, and a gather that fails once issued raises into the caller. A stopped session (see "The writer queue"), or one that compares no parameter, still enters an explicit `record_replica_spread(group)` and drops its result, since the other ranks are entering it too. With a group whose global ranks can be read, and a launch, the record says what the gathered spread covers (`replica_spread_scope`); a precomputed table passed in has none. A replicated parameter that some replica cannot read (on `meta`, nested or sparse, or one whose reading raised) is still gathered, so every rank enters the same collective, and is then left out of `replica_spread` and named once in a `RuntimeWarning`; a NaN weight that was read still reads as drift. The public `replica_spread` gives NaN rows for such a parameter with a warning; `parameter_fingerprints` still raises on one. Where the gather cannot run at all (a CPU table under NCCL, as with FSDP's CPU offload, or a destroyed process group) the call skips it and names each parameter as not compared.

**Every rank gathers, or every rank skips.** Before the gather, each explicit call exchanges one row per rank whose shape never depends on what was passed (246 int64, one `all_gather`, as PyTorch's DDP exchanges parameter counts before it compares shapes): how many parameters the rank compares, the device type of its table, whether it can gather it, and its projection setting. The row goes on the CPU when the group has a Gloo backend for it, else on the current CUDA device (NCCL); every rank reads the group's backends alike, so every rank picks the same place. Every rank then takes the one decision the rows give, and says the same why, naming the ranks. Two cases a rank cannot see alone are caught this way:

- **Unequal parameter counts.** Ranks that compare different numbers of parameters (`replica_params=` chosen differently, or models that differ) would enter an `all_gather` of tables of different shapes, which under Gloo does not complete. Every rank skips, with the counts (`2 on rank 0; 3 on rank 1`). A rank that compares none takes part too, and its peers skip. The public `replica_spread` with an empty list takes part, then raises `ValueError` on that rank.
- **Mixed device types.** A rank whose table is on another device type (a session on the CPU beside sessions on CUDA, or a device the group has no backend for) would have skipped while its peers entered the gather. Every rank skips, naming the device types (`cpu on rank 0; cuda on ranks 1, 2`), or the rank that cannot gather and why. Fingerprints made on different devices are not compared, as the observation's reader does not compare them either.

A different `replica_projection` on one rank is caught the same way. The exchange costs one small collective per explicit call, and its rows are read on the host, so on a GPU the call waits for the device once. It is a collective like the gather: a rank that never calls still leaves the others waiting, a group that fails raises into the caller, and every rank must run a TensorQuill that exchanges alike (a rank on an older version enters the table's gather while the others enter the exchange). Run with Gloo on CPU here; NCCL and a real mix of CPU and CUDA sessions are not run. The scheduled observation issues no collective, exchange included.

## Probe pass

`tensorquill.init(model, probe={"input_ids": fixed_batch}, probe_every=1000)` runs one fixed batch through the model every 1,000 steps (wandb.watch's default for histograms) and adds a `probe` field to that step's record:

- **`histograms`**: a 64-bin histogram of each repeated block's output (`lo`, `hi`, `counts`, and `nonfinite` for NaN and Inf values left out).
- **`attention`**: for each `scaled_dot_product_attention` call, named after the block it ran in, per head: the largest finite pre-softmax logit (`max_logit`), the mean entropy in nats (`entropy`), and `entropy_share`, each query row's entropy divided by the log of that row's own visible key count, so uniform attention is 1.0 under a causal mask too. Rows are kept apart by kind, so padding and numerical failures do not read as concentrated attention: `masked_rows` (every key masked, as for padded queries) and `invalid_rows` (a NaN or +Inf score among the visible keys) are counted over batch × heads × queries (`rows`) and left out of the entropy, as are rows with a single visible key. Also sample 0's attention map over its valid rows, averaged over heads and pooled to at most 64 × 64 (keys summed and query rows averaged per bin, so each row sums to 1; rows with no valid query are 0).
- **`head`**: four numbers of the language-model head's logits on the probe batch, from FP32: `norm` (mean over positions of each position's L2 norm over the vocabulary), the signed `mean`, `log_z` (mean over positions of logsumexp), and `gap`, RMS(z_bf16 − z_fp32) over every logit, the head applied a second time to the same hidden states in BF16 and FP32 (Chen et al., arXiv 2610.38277, p. 7), with `gap_relative` (over the RMS per-position spread). The head is the module named by `probe_head=` or returned by `get_output_embeddings()`, asked of the model and, under a wrapper module, of the models inside it (two different heads are a `not_read` reason), and must be a plain `nn.Linear`; otherwise `not_read` says why. Positions whose FP32 logits are finite but whose BF16 pass is not (its logits hold an Inf or a NaN, so the gap has no value) are counted as `overflow_positions`, apart from positions whose FP32 logits hold a NaN or an Inf. Numbers only, as `head_trends` in the evidence: no incident. `probe_head=False` turns it off.
- **`error`** instead of the above when the probe raised. The step itself is always written: the probe runs after the step is complete, and a failure is reported as a `RuntimeWarning`.
- **`not_run`** instead of the above, once, on the first step's record, when `probe=` was given and the probe is off. That is the case on a sharded model (see "The probe is off on a sharded model" below). The report then lists the checks that read the probe (`attention_collapse`, `attention_uniform`, `attention_logit_growth`) as unavailable, with the reason, in the Python and the Rust report alike.

`probe` can be a tensor (`model(batch)`), a mapping of keyword inputs (`model(**batch)`), or a callable `fn(model)`. How it runs:

- **After the step's statistics are recorded.** The capture hooks fire during the probe's forward pass too, so their buffers are cleared again afterwards; the probe never shows up in the step's activations or router counts.
- **Without the compiler**, under `torch.compiler.set_stance("force_eager")`, in eval mode and without gradients. Each module's own training flag is restored afterwards (not `model.train()`, which would unfreeze submodules kept in eval mode), and the random number generator state is restored, so training sees the same random numbers as without the probe.
- **No recompiles.** The probe's hooks are registered once at `init` and do nothing unless a probe is running, which only happens without the compiler. Adding and removing hooks around each probe would recompile the model.
- **Attention is recomputed alongside the real call.** Fused attention kernels never store the attention map, so during the probe `torch.nn.functional.scaled_dot_product_attention` is wrapped: the original computes the output, and the wrapper recomputes `softmax(QKᵀ)` from the query and key a block of query rows at a time (at most 2^26 scores, 256 MB, per block). Grouped-query attention (`enable_gqa`, as Hugging Face uses on CUDA without a mask) repeats the key heads to the query's head count. Hugging Face models loaded with `attn_implementation="flash_attention_2"` or `"flash_attention_3"` never call SDPA, so the probe switches them to `"sdpa"` and back, config by config, so a composite model keeps each part's own setting. Only the probe's own thread is read: an attention call another thread makes meanwhile goes straight to the original. Code that imported `scaled_dot_product_attention` by name before the probe, or uses another attention kernel, is not seen; the record then says `no scaled_dot_product_attention call seen`.
- **Deterministic mode** is left as the job set it (since Nov 19, 2026; the probe used to turn it off for the whole process). With it on, the histograms are counted with `bincount`, and a probe function that uses an op with no deterministic kernel fails as a probe error, which is in the probe's record. That path has not been run on CUDA.
- **Cost** is one eager forward pass plus the attention recomputation and one sync per histogram, every `probe_every` steps; not yet measured on a GPU. A Granite probe record should be on the order of 2 MB of JSON (24 maps of 64 × 64), also not measured. The Granite benchmark takes `--probe-every N`.

The Rerun export adds a Probe tab: the largest attention logit and `entropy_share` per layer over training, the count of invalid attention rows when there are any, a histogram per block and an attention map per layer at each probe step. There is no detector on the probe data yet: thresholds for logit growth or entropy collapse need real failures first.

## Streaming to an ingest server

The local `.jsonl` file is always written and stays the source of truth. Streaming is off unless you set an endpoint, and then needs `pyarrow`:

```sh
pip install -e 'sdk[flight]'
cargo build --release --manifest-path server/Cargo.toml
server/target/release/tensorquill-server --listen 127.0.0.1:50051 --store file:///var/lib/tensorquill
```

**Evaluation and checkpoints are not hangs.** With `endpoint=`, a thread of its own sends the server a heartbeat every 15 seconds (`init(heartbeat_seconds=...)`, `None` turns it off) naming the rank's phase. Mark a stretch with no training steps with `with session.phase("eval"): ...` (or `session.set_phase("checkpoint")` and back to `"train"`); the Lightning callback marks validation and the Hugging Face callback marks evaluation and saves. While the phase is not `train` and heartbeats continue, the rank is `paused` and raises nothing. Each heartbeat also names the session's attempt (since Nov 17, 2026), so a job started again is known to the server from its new process's first beat, before it stores a step: the rank's `attempt` in the status changes at once, `attempt_without_steps` is true until the new attempt stores a batch, and it is judged as a rank that has not stepped yet (`starting` for `--start-seconds`, then a warning, critical `--critical-seconds` later), not from the earlier attempt's last batch, which would call it critical at once. A reconnect of the same process is not a new attempt. Which attempt owns a rank is decided by when each was first seen, not by its number: an attempt first met in a claim (a heartbeat, or a batch whose sender names its own attempt, `sender_attempt`) is the newest, and an attempt first met only in rows goes just before the attempt that sent them. The server keeps that order per rank in `runs/<run_id>/rank=<n>/attempts.json`, written before it answers, so it survives a restart and the stored replay uses it. A beat from an earlier attempt's process that is still alive is always ignored, and its rows sent late are stored, counted (`superseded_rows`) and are not progress. A row the server drops because its run, rank, step, attempt or schema version is null is counted too, in that rank's entry of its own run's status: `dropped_rows` is the total and `dropped_row_keys` the count by the first null key, both present only when above zero, and neither changes a state or raises an incident. While the new attempt has stored nothing the rank shows its `attempt`, `attempt_without_steps: true` and `last_step: null`: the earlier attempt's last step is not shown as its own. A local file with no server orders attempts by first appearance in the file; across several files of one rank, each file's own order is kept first, then each attempt's first `ts` decides, then its number, never the path order, and files that disagree give numeric order with `attempt_order: "numeric"` and the files named. Two limits: across files, `ts` is each host's clock; and rows from an SDK older than `sender_attempt` are placed by attempt number, so a lower-numbered replacement (a clock behind) whose rows arrive before its first heartbeat is taken as backlog. The attempt is read once, when the session starts, and adds a number to each beat; the first beat waits for it (2 s at most) and the stream's first connection waits for that beat, on their own threads: nothing on the training thread waits. A job that crash-loops faster than its start window without storing a step is not called critical, since each new attempt starts the window again. A server older than this ignores the field. A rank that has not sent its first batch yet is `starting`, not stopped, within two bounds, because the capture holds `every` steps (50) before it writes any and a job can hang before that. Once its heartbeats show it stepping, the work counter is its progress: it is `silent` when the counter has stood still past its threshold (`--silent-seconds`, or five times its own time per step, never under three heartbeat intervals), so 30-second steps that take 25 minutes to fill the first batch raise nothing. Before its first training step (compilation, a data load, the first collective, or no heartbeat at all) it is `starting` for `--start-seconds` (default 1800) since its last sign of work, then `silent` at `warning`, and `critical` `--critical-seconds` later (2700 s in all by default); set `--start-seconds` above your longest startup. A pause is bounded: heartbeats carry a work counter (steps plus `session.tick()`, which the callbacks call once per evaluation batch), a pause that keeps ticking is not limited, one with no sign of work is suspect after `--pause-seconds` (default 1800), and a committed training step always ends a pause. A quiet rank in `train` is `silent` (`suspected_hang`; `confirmed_hang` only when a Flight Recorder dump shows a stuck collective; since Nov 17, 2026 a stall that a lost rank explains reads `lost_connection` instead, and is then not upgraded from a dump: see "The trigger"), `warning` after `--silent-seconds` and `critical` after `--critical-seconds` (default 900) or three of its own silence thresholds, if longer, so a slow rank still gets a warning first. `confirmed_hang` needs a complete Flight Recorder dump newer than the last recorded step. If the heartbeats stop too, the rank is `unresponsive`: the whole process is frozen or gone. The server records how long each pause lasted and `watchdog.json` carries `recommended_silent_seconds` (twice the longest pause); the summary says it. TensorQuill only reports: it never blocks or terminates training. All thresholds are uncalibrated starting values. A stuck evaluation that keeps its heartbeats going raises nothing, and a hung main thread keeps the heartbeats going too, so a heartbeat shows the process is alive, not that it is making progress.

**Where a silent rank is stuck.** When a rank's work counter (steps plus `session.tick()`) has not moved for 60 seconds (`init(stack_seconds=...)`, `None` turns it off), each heartbeat also carries where the process's Python threads are: file, line and function names, the main thread first (up to 40 frames, 4 for each of up to 7 other threads, so under 10 KB a rank at the most), with TensorQuill's own threads left out and frames of TensorQuill's own code marked. No source text is read and no local values are taken. The server keeps the newest one in the rank's entry in `watchdog.json` as `stack` (dropped if the heartbeat is larger than 64 KB), also after the heartbeats stop and over a server restart, and clears it when a heartbeat arrives without one. `job_stalled` and `rank_silent` then list `stuck_at`: for each stopped rank the innermost frame, the nearest frame that is not a library's (`caller`), how long the main thread's stack had not changed (`unchanged_seconds`), and `in_tensorquill` when the call was reached through TensorQuill's own code, such as an explicit `replica_spread`'s `all_gather`. The server's own `incidents` in `watchdog.json` carry the same `stuck_at`; the whole stacks stay in the status's `ranks` and are not copied into incidents or `evidence.json`. The assessment stays `suspected_hang`: a stack says where Python was, not why. Limits: Python frames only, so a hang inside NCCL shows as the Python line that called the collective (PyTorch releases the interpreter lock around its collectives, so the heartbeat thread keeps running); a main thread hung while holding the interpreter lock stops the heartbeat thread, so the rank is `unresponsive` with no stack; verified with a process blocked in a Python wait, not yet with a real stuck collective on GPUs.

**What the stacks do not show.** They are the Python threads of the rank's own process. A data-loader worker or a checkpoint writer runs in a process of its own, and a stall whose cause is there shows only as the main thread waiting for it; one production team reports such causes (ByteRobust, p. 8).

**Stopped ranks grouped by stack.** The all-ranks view (`--rank all`, `get_all_ranks_status`) adds `stopped_stacks` while a rank is stopped: the ranks that sent a stack grouped by where their main thread was (every kept frame compared on function, file after `site-packages` or the base name, and line for the job's and TensorQuill's own code), the ranks that sent none, and an odd group named only when there are exactly two groups and the smaller is one rank or at most a quarter of them (`verdict`). It is an observation, never the cause: the papers disagree on whether the odd rank is the culprit, a rank stuck in a data-loader worker shows only its main process's stack, and one snapshot cannot name a slow rank.

**Closed or stopped.** When `session.close()` (or the end of `with session:`) has closed the local file, it leaves `<name>.end.json` beside `<name>.jsonl`; a session closed by an exception says so. The evidence of a local file carries `run_end`, the summary says it, and `python -m tensorquill runs` has an `end` column. No marker (`not_closed`) means still running, killed, or never closed: the file cannot tell which. A session that opens the file again removes the marker first, and the marker records the file's size, so a file written after it is not read as closed.

**TrainCheck** (OSDI '25, a separate tool that checks a run against invariants inferred from a clean reference run) is read, not embedded: `python -m tensorquill <input> --traincheck <violations_summary.json or the traincheck-check results directory>` turns its violated invariants into one `traincheck_violation` incident beside TensorQuill's own. Its steps are its own iteration count, which match TensorQuill's only without gradient accumulation; running both tools in one process has not been tried, since each patches PyTorch's API.

**When a multi-GPU job hangs**, PyTorch's Flight Recorder already knows which collective is stuck; TensorQuill reads its dumps instead of tracing collectives. Set `TORCH_FR_BUFFER_SIZE` (formerly `TORCH_NCCL_TRACE_BUFFER_SIZE`; the default is 2000 entries), `TORCH_FR_DUMP_TEMP_FILE=/some/dir/fr_trace_rank_` (formerly `TORCH_NCCL_DEBUG_INFO_TEMP_FILE`) and, with NCCL, `TORCH_NCCL_ENABLE_MONITORING=1` and `TORCH_NCCL_DUMP_ON_TIMEOUT=1`, so each rank writes `<prefix><rank>` when a collective times out. Then `python -m tensorquill <input> --flight-recorder /some/dir` (add `--flight-recorder-prefix fr_trace_rank_` if PyTorch cannot infer it) runs PyTorch's analyzer over the dumps and reports the first stuck or mismatched collective as `collective_hang` or `collective_desync`. PyTorch 2.10 or later; checked only on dumps built in the analyzer's own test format. The dumps are pickles, so read only dumps your own job wrote. PyTorch's debug server (`torch.distributed.debug.start_debug_server`) is experimental and meant for trusted networks only, so TensorQuill does not start it.

**The rank that reports a timeout is often a victim.** PyTorch's post on Flight Recorder, from Meta's fleet, says the rank that first raises the timeout is rarely the cause, and that almost all timeouts there came from ranks falling out of step, not from a slow collective. It maps the record to likely causes: a missing rank or a state mismatch points to a CPU-side stall or a code path that differs across ranks (data loading, checkpointing, compilation, an `except` that swallows an error, one rank running out of data early), or a hung GPU kernel; a size or dtype mismatch to wrong arguments; a different collective type or call stack to code paths that differ; all ranks started and none finished to the network. CPU-side causes were over 60% there. TensorQuill labels a collective with a missing rank `collective_hang`, where the post counts it as a desync. These are one company's experience, and TensorQuill makes no rule from them: it does not name the rank that caused a hang.

**A local run with no server cannot detect a hang at all.** A capture that only writes its `.jsonl` file has nothing watching it: when the job hangs the file simply stops growing, which reads the same as a job that ended, and no incident is ever listed. The two stall kinds, `job_stalled` and `rank_silent`, come only from the server's watchdog, so they need `endpoint=` and a running `tensorquill-server`; `collective_hang` needs PyTorch's Flight Recorder dumps given with `--flight-recorder` (the paragraph above). The evidence of a local file says so: these kinds are `not_configured` under `kind_checks`, never "checked, none found".

The server also watches each run for ranks that stop making progress, using only what it receives, so it works when the training process is hung. It looks at each run every 10 seconds (`--watchdog-seconds`, 0 turns it off, at shutdown too) and writes `runs/<run_id>/watchdog.json` when the verdict changed, and at least every third look (`refresh_seconds` in the file, 30 by default) while the run is unfinished, so that a reader can tell a server watching a stalled run from one that is gone; `python -m tensorquill <store>/runs/<run_id>` reads it and reports `job_stalled` (no rank progressing) or `rank_silent` (some ranks silent, lost or never connected). A rank is silent after `--silent-seconds` without a new step (default 300) or `--silent-factor` times its own usual time between batches (default 5), whichever is longer. `--silent-factor` takes 0, which leaves `--silent-seconds` alone, or a finite number above 1; the server refuses any other value when it starts. Set it above your longest evaluation or checkpoint pause: the default is not calibrated, and a long pause looks the same as a hang. The server sees only ranks that connected since it started, and it names a rank as never connected only after `--silent-seconds` (ranks start a moment apart), so capture on every rank. It rewrites the file only when something changed and marks it `server_stopped` when it shuts down cleanly. A rank that goes silent or unresponsive before its first training step gets the start window (`--start-seconds`) before `--critical-seconds`, as a rank that is starting does. A finished or abandoned run is let go of from the server's memory an hour after its status is written; its files stay.

**What `reconnecting` means.** A rank reads `reconnecting` when its stream dropped without ending (its process was killed or crashed, or the network failed) less than `--silent-seconds` ago. It says what the connection is doing, not that the rank is well. A rank that was healthy when its stream dropped has no `severity` for that time and is not listed in any incident; if its sender does not come back it then reads `lost`, with a `rank_silent` or `job_stalled` labelled `lost_connection`. So a healthy rank that is killed is called 300 s later at the defaults, and the run reads `active` until then. A rank that was already `silent` or `unresponsive` when its stream dropped (a hung process that was then killed is the usual case) keeps what it had: it reads `reconnecting` and then `lost` with the same `severity`, counted on the clock it already had, with `stopped_as` saying what it was, and the run's `rank_silent` or `job_stalled` goes on listing it (from Nov 22, 2026; until then such a rank read as a healthy rank reconnecting, and the run as `active` with no incident, for the whole `--silent-seconds`). A stream that opens again changes nothing by itself: only a new step recovers the rank. A newer attempt that takes the rank clears it. A server restart does not carry it over: every unfinished rank gets a fresh window from the restart, as before.

**A rank that goes silent after its capture stopped (Nov 20, 2026).** A rank whose capture stopped while training went on still raises `rank_silent` or `job_stalled` if its heartbeats later cease. The incident then carries `capture_stopped`, as the rank's status entry holds it (the reason and how long ago), and `capture_last_step`, the last step the rank's current attempt stored, or null when that attempt stored none. Its text says TensorQuill cannot tell from that rank whether training itself stalled. After a restart whose new attempt stopped capturing before its first record, the incident gives the reason and names no step: the earlier attempt's last step is not this attempt's. Only a rank that went silent gives the incident these keys; one that is still sending heartbeats does not.

```python
session = tensorquill.init(model, routers=..., endpoint="grpc://127.0.0.1:50051")  # or TENSORQUILL_ENDPOINT
```

- **It does not touch the training thread.** A daemon thread reads complete lines from the file, at most 50 steps or 4 MiB at a time, every 50 steps or 2 seconds. A line the writer has not finished is never sent. A writer that opens a file whose last line was torn by a killed process ends that line first, so its own first step stays a line of its own; readers skip the torn line and say how many lines they left out. The offset file holds the offset with the server, run, rank and digests of the file's bytes: a resume that does not match all of them sends the file from the start, and the server drops the rows it already has. The first resume after upgrading from a version whose offset file held the number alone does this once.
- **A server that is down, slow or full only delays the stream.** The sender keeps no backlog in memory: it sleeps (100 ms doubling to 30 s, with full jitter) and reads the file again from `<run_id>.rank<rank>.offset`. That file moves only when the server confirms the bytes are in a stored Parquet part, so it trails the `.jsonl` by up to 10 seconds or 500 steps, and a server killed with rows still in memory loses nothing. The offset is bound to the server's store, not its address (Nov 20, 2026): each ack carries the store's ID, the offset file keeps it, and before a saved offset above 0 is used the sender asks the server which store it is. A store that was replaced behind the same address is sent the file from its start, and the same store reached by another address is not. A server whose ack has no store ID leaves the offset bound to the address, as before; a saved offset with no store ID, met by a server that has one, is sent again from the start once. A store wiped while its server keeps running is not noticed until that server restarts.
- **Resending is harmless.** The server drops rows whose step is not above the last one it kept for that `(run_id, rank, attempt)`, and reads that mark from its Parquet files after a restart.
- **`session.close()` waits up to 5 seconds** for the server to store what is left, and otherwise prints the local path. `tensorquill.flight.send_file(path, endpoint, run_id, rank)` sends the rest later.
- **Errors in the setup raise at `init`:** an endpoint that is not `grpc://` or `grpcs://`, a missing `pyarrow`, an unreadable `TENSORQUILL_TLS_CA` file under `grpcs://`, or `endpoint=` with a sink that has no file. Nothing raises once training runs: the sender keeps its last failure in `session._sink.sender.last_error`, and a local sink that fails stops capture with one warning ("The writer queue" under Things to know). The exception is an explicit gather the caller issues (`replica_spread()`, `session.record_replica_spread(group)`), which raises if it fails once issued; the scheduled drift check gathers nothing.
- **The server** writes `{store}/runs/{run_id}/rank={rank}/attempt={attempt}/part-{first step}-{last step}.parquet`, one row per step. It listens on loopback by default; any other address needs `TENSORQUILL_TOKEN` (the sender reads the same variable and sends it as a Bearer token) or `--allow-unauthenticated`, with optional TLS (`--tls-cert` and `--tls-key` on the server, `grpcs://` and `TENSORQUILL_TLS_CA` for a custom CA on the sender). On `SIGTERM` it writes what it holds and exits. It buffers at most 128 MiB across all ranks and refuses batches beyond that, which the sender retries.
- **Run IDs** may hold only letters, digits, `-`, `_` and `.` on the server, because the ID becomes a directory name.
- **A run resumed from an earlier step under the same run ID** is a new attempt. The server checks each row against its own attempt, so the steps written again are kept, in their own `attempt=` directory, and a resend of old lines after a lost offset file still stores nothing twice.
- **Columns.** Numbers and name-to-number maps are typed columns; `layers`, `moe_stats` and `probe` are JSON strings (`layers_json`, `moe_stats_json`, `probe_json`; `layers_json` keeps the model's key order, which the activation detectors use to say which block showed a change first, while the other two are written with sorted keys; Parquet parts sent by a version before Nov 15, 2026 have `layers` sorted by name, so "first" there is first by name); anything else travels in `extra_json`, so a row converts back to exactly the record in the `.jsonl` file. The choices behind this are in the plan's Decisions section.

## Detector benchmark on 64 ranks

[`examples/benchmark_detectors.py`](examples/benchmark_detectors.py) times the Python detectors against the plan's budget of 250 ms per 50-step flush across 64 ranks (or one CPU core). It trains a Granite-shaped MoE (24 blocks, 32 experts, top-8, 219 parameters) for 105 steps under `tensorquill.init`, takes the record shapes from that capture, writes a healthy synthetic run of 64 ranks and 10,000 steps in the server's layout (50-step Zstd parts, 3 GB), and times `load_records`, `build_evidence` and one `--watch` update at 500, 2,000 and 10,000 steps, then profiles the slowest stage. `python examples/benchmark_detectors.py` runs all of it in about 6 minutes (384 s on the machine below, building the store included) with no GPU or server (`--quick`: 4 ranks, under a minute; `--json` keeps the numbers).

The template's weight-check records carry the scheduled replica observation (`replica`) that a run given `replica_group=` records, taken under a process group of one rank on Gloo, and every synthetic rank's observation names the whole store as its group and agrees. The figures below were measured before that, when those records carried the explicit gather's `replica_spread` instead; they have not been measured again.

Measured on an Apple M1 Pro (8 cores, 16 GB, macOS, no GPU), Python 3.12.3, pyarrow 26.0.1, with other work on the machine (load average 3 to 6): the update is one flush of 50 steps from 64 ranks for rank 0, median of five runs, warm file cache.

| Run length | Poll | Detectors | Write | `--watch` update (worst) | Against 250 ms |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 500 steps | 13 ms | 341 ms | 42 ms | 395 ms (402) | 1.6x |
| 2,000 steps | 15 ms | 1,450 ms | 167 ms | 1,631 ms (1,664) | 6.5x |
| 10,000 steps | 21 ms | 7,169 ms | 860 ms | 8,067 ms (8,156) | 32x |

The rebuild costs about 0.72 ms of detector time per step, so an update grows with the run, and one worker per rank over 64 ranks at 2,000 steps takes 105 s (3,200% of a core at Granite's 65 ms per step). A worker that kept the detectors' state between flushes would still pay one part read (13.6 ms) and 50 steps of detectors (35.9 ms) per rank: 3.2 s for 64 ranks, 12.7x the budget and 105% of a core, projected from the slope. The time is spread over per-step loops with rolling medians (activation checks 27%, gradient spikes 15%, the starved-expert window 15%, non-finite scan 13%, top-k overload 12% of a 2,000-step build), not one hot spot. Peak memory is 1.15 GB for one rank's 10,000 steps and 1.28 GB for the update. A 2-block, 8-expert, top-1 model (21 parameters) is 17 times cheaper per step: an update at 2,000 steps takes 100 ms, and the stateful floor for 64 ranks is 343 ms (1.4x, 17% of a core). The values are synthetic and healthy and the run is one process on one machine, so treat the figures as the shape of the cost, not as a forecast for a GPU job.

Two fixes came out of it, with identical output on 29 healthy and faulted runs, except for a store whose `rank=<n>` folder holds another rank's rows, which the server never writes. Reading `--rank N` from a directory of ranks opened every rank's parts and kept one in 64: the poll took 1.0 to 1.5 s, and the whole directory sat in memory at once (495 MB for 64 ranks of 100 steps, about 50 GB at 10,000 steps); it now opens only that rank's folder (poll 13 to 21 ms, 32 MB). The activation drift check now computes each module's baseline once, taking the 10,000-step build from 9.2 s to 7.2 s.

## Detectors in the server

`tensorquill-server` runs the detectors itself, in Rust: every kind that is read from a rank's step records (`server/src/detect.rs`), and the two that are read from the progress status (`server/src/watchdog.rs`). Python (`evidence.py`) stays the reference: new rules land there first, and the server must give the same answer.

| Where | Kinds |
| --- | --- |
| `runs/<run_id>/rank=<rank>/incidents.json` | `moe_imbalance`, `starved_experts`, `grad_spike`, `stalled_weights`, `repeated_steps`, `loss_scale_trouble`, `resume_lr_change`, `resume_data_mismatch`, `resume_incomplete`, `data_stalled`, `epoch_order_repeated`, `activation_spike`, `activation_drift`, `dead_activations`, `attention_collapse`, `attention_uniform`, `attention_logit_growth`, `non_finite`, `memory_growth`, `memory_pressure`, `allocator_retries`, `hardware_errors`, `gpu_throttled`, `input_starvation`, `replica_drift` (Nov 16, 2026: the data, checkpoint, attention and system kinds added) |
| `incidents` in `runs/<run_id>/watchdog.json` | `job_stalled`, `rank_silent`, `duplicate_batches` (cross-rank), plus the `run_state` |
| Python only | `collective_hang`, `collective_desync`, `traincheck_violation`, `memory_imbalance` (cross-rank, in `--rank all`) |

The first three Python-only kinds stay in Python because their sources never reach the server: PyTorch's Flight Recorder dumps are pickles on the training nodes, read by PyTorch's own analyzer, and TrainCheck writes its results where it ran. `memory_imbalance` compares ranks, and the server's detectors see one rank at a time; it reads the `memory` summary the server writes into each rank's `incidents.json`. The timings below are from Nov 15, 2026 with twelve kinds; they were repeated with all 25 per-rank kinds on Nov 16 (see [Re-measured with 25 kinds](#re-measured-with-25-kinds)).

- **What it writes.** After each part is stored and acknowledged, the server reads that part's rows and rewrites the rank's `incidents.json`: the incidents in the shape and order `build_evidence` gives them, `last_step` (detection has run through here), the kinds `checked`, `not_checked` (in the shape of the same list in `evidence.json`: the two sources the server does not have, and each resume whose learning rate could not be compared), `kind_checks` (one of three values for each of those kinds, see [What was checked](#what-was-checked)), the thresholds applied, `moe_flagged` (how many router samples had an overloaded or dead expert and the last step one did, which says whether an imbalance is still going on), and `rebuilds`. It holds no per-step samples: those stay in the Parquet parts, so the file stays a few KB however long the run is. `--no-detect` turns it off. The watchdog status carries its verdict as an `incidents` list as well, rewritten whenever the status changes, so a stall shows there although no part arrives. `python -m tensorquill --watch` reads both (see [Watching a run the server is judging](#watching-a-run-the-server-is-judging)); without `--watch` the command works the incidents out itself from the parts.
- **Only stored rows are judged**, so the file can always be rebuilt from the store. After a server restart, on every new attempt, and whenever an older attempt's rows arrive late, the rank's state is rebuilt from all of its stored parts with the same attempt rules as `load_records`. That replay also reads the rows a later attempt rolled back: `repeated_steps` and `resume_lr_change` compare a new attempt with what it replaced. The step numbers and learning rates it needs for that are held only while the replay runs. A detector error or panic is logged and never fails a flush.
- **How late it is.** Detection follows storage, and a part is written every `--flush-steps` steps (500 by default) or `--flush-seconds` (10), so by default an incident shows about 10 seconds after its step reached the server, at the latest.
- **Same answers as Python.** [`tests/test_server_detectors.py`](tests/test_server_detectors.py) (16 tests) streams records through the real binary and compares `incidents.json` with `build_evidence` on the same records: after 16 stretches of a 300-step run in which ten kinds each happen once; after 12 stretches of a 400-step run in which one small parameter's gradient spikes without moving the total and five parameters stall at three different steps, and across a restart inside that excursion; across a server restart in the middle of a 140-step collapse; after each of 12 stretches of a run with nine attempts (resumes at a step the run had, past the stored steps, with no learning rate, and two restarts of the numbering); on seven short runs for rules the long one does not reach; and on the seven Gate 1 fixtures. `test_flight_e2e.py` and `test_two_ranks_e2e.py` compare the status's `incidents` with `detect_watchdog_incidents` on a stalled job, a killed one, a lost rank and a rank that never connected. Twenty-two deliberate changes to the Rust rules each fail these tests, and so do nineteen more to the per-parameter rules added Nov 16, 2026 (one first survived, excursion norms entering the median, and the fixture was changed until it failed). Steps, layers, experts and names match exactly and numbers to 1e-12.
- **Where the server differs, by design.** NaN and Inf are `null` in its files, which are strict JSON. A value that does not fit its column's type travels in `extra_json` and reads as absent. The server never stores a step twice within one attempt, so that case of `repeated_steps` cannot arise from its store. A stream cannot look ahead as Python does over a finished list; the places that matters (when clipping starts, a `moe_top_k` that changes in mid-run, and attempts) are described at the top of `detect.rs`.

Timed with `cargo run --release --example detect_store -- <store> <run_id> --bench` on the benchmark's own synthetic store (64 ranks, 2,000 steps, Granite's shape, healthy), Apple M1 Pro, one thread, median and worst of 40 flushes of 50 steps from every rank:

| Per flush of 64 ranks | Rust, twelve kinds | Python, all kinds |
| --- | ---: | ---: |
| Detectors | 56 ms (68) | 2,220 ms, projected with state kept |
| of which decoding `layers_json` and `moe_stats_json` | about 33 ms, measured apart | |
| Writing the 64 Parquet parts (already on the live path) | 138 to 145 ms | |
| Writing 64 `incidents.json` files | 13 ms (14) | |
| Reading the parts back | not needed live | 830 ms |

The first six kinds took 54 ms; the six added on Nov 15, 2026 cost about 2 ms more, not the 26 ms guessed from Python's proportions. That is 17.5 µs of detector time per step against Python's 693 µs. Detection, storage and the incidents files together are about 210 ms on one thread, under the 250 ms budget on this healthy run (about 290 ms, over it, if no shortcut applied: see below); the server spreads ranks over its threads, which this does not measure. Rebuilding one rank from 2,000 stored steps takes 75 ms, and all 64 at once 0.98 s.

What these numbers do not show:
- The store is healthy, and most of the speed comes from skipping a median when a window's lowest or highest value already rules a hit out, which is exact. Before those shortcuts the first six kinds took 136 ms per flush; take that as the cost when every check has to work its median out, as on a run that is failing everywhere.
- Two thirds of the detector time is decoding the two JSON columns. Typed columns for the per-layer statistics would remove most of it; that is a schema change and is not made.
- The store has a weight check and a replica check once in 50 steps and no loss scaler. A run that checks weights on every step pays for 219 name comparisons on each; that was not timed.
- The detectors' state is outside the server's memory quota and is kept until the server exits: 1.5 to 2 MB per rank at Granite's shape, measured under live streams below. A replay also holds every step number and learning rate of the rank while it runs (under 100 bytes a step, by its layout).
- A real model's values, a GPU job, and S3 or GCS are not measured.

### Storing to S3 or GCS

```sh
tensorquill-server --listen 0.0.0.0:50051 --store s3://my-bucket/tensorquill
tensorquill-server --listen 0.0.0.0:50051 --store gs://my-bucket/tensorquill
```

Credentials come from the usual environment: `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN` and `AWS_REGION`, or the instance or pod role (EC2, ECS, EKS web identity); for GCS `GOOGLE_APPLICATION_CREDENTIALS` (a service-account file) or the instance's own account. Shared credential files and `AWS_PROFILE` are not read. For an S3-compatible service (MinIO, an emulator) set `AWS_ENDPOINT_URL`, plus `AWS_ALLOW_HTTP=true` if it is `http://`. The server needs `GetObject`, `PutObject` and `ListBucket` on the prefix and nothing else; it never deletes. Credentials are never printed. S3 has run against the `moto` emulator through the real binary; **GCS has never run** (the code compiles and its builder is unit-tested), and nothing has run against real AWS, TLS to S3 or real latency. `python -m tensorquill --watch` and `load_records` still read a local directory only.

The server reads the store when it starts (it lists `runs/` and reads each unfinished run's `watchdog.json`), so a wrong bucket or bad credentials stop it with the store's message instead of failing at the first batch. A failing store is retried for `--store-retry-seconds` (30); then the sender is told the store is unavailable and keeps its rows. A restarted server takes up the runs it was watching, and the time it was down is not counted against a rank. Since Nov 17, 2026 every rank it takes up gets a fresh window from the restart, so a rank is not called stopped, or critical, before its sender has had a chance to reconnect: `--start-seconds` (1800) for a rank that has shown no training step, its own silence threshold (`--silent-seconds`, 300, or its slower cadence) for one that has. A rank whose sender does not come back in that window is `lost` (or `unresponsive`, if its heartbeats had already stopped). The quiet time the status shows is kept. The cost: a hang or a killed job that spans a restart is called later by the time it had already been quiet. With the defaults a rank that had stepped is critical 900 s after the restart (a rank hung 800 s is called 800 s later), and one that never stepped 2,700 s after it, up to 2,700 s later than before. A stalled run reads healthy for the window, and a server restarted more often than the window never calls a hang. A run whose ranks have all been disconnected or finished for `--abandon-hours` (72) is given up. `cargo build --release --no-default-features` builds a local-disk-only binary (3.9 MB smaller).

### Under 64 live streams

[`server/examples/live_streams.rs`](../server/examples/live_streams.rs) opens one `DoPut` stream per rank against a running release server and replays the same store, one 50-step part per message, each rank waiting for its acknowledgement as the Python sender does (`--flush-steps 50`, so every message is one flush; all 64 ranks start together, so their flushes coincide, which is the worst case). Same machine (8 cores), with the client on it too, decoding Parquet and encoding Flight beside the server it times.

| 64 ranks, 2,000 steps each | Detectors on | `--no-detect` |
| --- | ---: | ---: |
| As fast as acknowledgements return | 3.4 to 4.0 s, 32,000 to 37,800 steps/s (18 runs) | 2.7 to 2.9 s, 44,700 to 48,000 steps/s (3 runs) |
| At 10 ms per step: sent to acknowledged, median / p99 / worst | 52 / 99 / 125 ms | 41 / 81 / 92 ms |
| At 65 ms per step (Granite's): the same | 54 / 100 / 132 ms | not run |
| Acknowledged to `incidents.json` covering the part, median / p99 / worst | 0.1 / 15 to 25 / 50 ms | |
| Server CPU for the run (2,560 flushes) | 14.3 s at 10 ms per step, 15.2 s at 65 ms | 10.1 s |
| Server peak memory | 360 to 415 MB | 260 to 300 MB |

- **Rate.** 64 ranks at Granite's 65 ms per step produce 985 steps a second; the server took 35 times that with the detectors on. At that pace it used 15.2 s of CPU in 130 s, 12% of one core.
- **The budget.** Every one of the 64 simultaneous flushes was stored and acknowledged within 132 ms, under 250 ms. As CPU it is over: 5.6 ms per rank and flush, 358 ms for a flush of all 64, of which the detectors and the incidents files are about 105 ms (1.6 ms per rank; 69 ms when timed alone on one thread above) and receiving, decoding and storing the rest (253 ms with `--no-detect`). The single-thread table above leaves out receiving and decoding the Flight messages.
- **Memory.** The detectors add roughly 100 MB for 64 ranks, 1.5 to 2 MB a rank, measured as the difference in peak memory between the two columns; the estimate from window sizes was 1 MB. It is outside the 128 MiB quota.
- **10,000 steps.** 64 ranks × 10,000 steps sent flat out took 18.3 s (35,000 steps/s, the same rate as at 2,000), acknowledgements 73 / 218 / 1,027 ms, the report 0.1 / 6.6 / 77 ms behind, peak memory 448 MB.
- **A restart with 10,000 steps stored.** Each rank's first part after the restart was stored and acknowledged in 100 to 170 ms at the median (442 worst, four runs). The server then rebuilt all 64 ranks from the store at once: the reports were current again 6.1 to 7.0 s later, and each rank's next part waited that long for its acknowledgement (6.2 to 7.1 s), because a rank's parts are taken one at a time. Nothing is lost while it waits: the sender keeps the lines in its file. The rebuild used 29 to 32 s of CPU over 8 cores, 0.5 s a rank, and peak memory was 400 to 535 MB.
- **A new attempt on all 64 ranks at once** (no restart) cost the same rebuild: 6.2 to 6.8 s (two runs).
- **Same answers.** After five restarts and three new attempts (10,800 stored steps, four attempts), the reports for the two ranks compared (5 and 40) equal `build_evidence` on the same store, one `resume_lr_change` each. A watcher's look at such a rank (216 part names listed, the report and the status read, the evidence written) took 2.0 ms (worst 4.3 of 50); `build_evidence` on it took 12.0 s.
- **One stream dropped once.** In the first of 19 flat-out runs with detectors on, made while the machine was still busy from a build, one rank's stream ended with a broken pipe 6 s in and the server logged nothing. It did not happen again and is not explained. A real sender reconnects and resumes from its offset file; this client does not. It was not the memory quota: a quota refusal reaches the client as `ResourceExhausted` ("ingest buffer full"), which a run with `--quota-mib 32` shows.
- **The quota at 64 ranks.** One 50-step part of this store is 1.4 MB as Arrow, so 64 ranks' parts arriving together hold 85 MiB of the default 128 MiB quota. With these record sizes about 90 ranks flushing at the same instant would fill it; the server then writes a rank's buffer early, and refuses the batch only if that is not enough. Not tried beyond 64.
- **Not covered:** more than 64 ranks, a second machine between client and server, TLS, S3 or GCS, a run where incidents happen (the store is healthy until the resumes), and rebuilds longer than 10,800 steps. By the slope, 64 ranks of 100,000 steps would take about a minute to rebuild, longer than the watcher's default 30-second wait; `--report-grace` raises it.

### Watching a run the server is judging

`python -m tensorquill <store>/runs/<run_id> --watch` takes its incidents from the server while it can: the rank's `incidents.json` for the 26 kinds read from step records, and the `incidents` list in `watchdog.json` for `job_stalled` and `rank_silent`. It reads no Parquet part then: a look lists the rank's part names and reads two small files, 2 ms with 216 parts (10,800 steps), where running the detectors here took 12 s. `--flight-recorder` and `--traincheck` are still read here and added, in the order `build_evidence` gives.

An empty `incidents` list means "no incidents" only in a report that covers what is stored. The report carries no clock, so the watcher compares it with the store: `read_server_report` takes the report's `attempt` and `last_step` and the newest stored part's, which are in that part's path (`attempt=<a>/part-<first>-<last>.parquet`), and calls the report:

| State | Meaning | What the watcher does |
| --- | --- | --- |
| `current` | The report ends exactly at the newest stored step of the newest attempt, covers all 26 kinds, and no threshold given here differs from the one the server applied (see "Detector thresholds") | Uses it. "No incidents detected" is followed by "current through step N of attempt A (M steps judged)" |
| `behind` | The report stops before the newest part. Normal for a moment after every part (0.1 ms at the median, 77 ms at worst, measured), and for 6 to 7 s while a restarted server rebuilds 64 ranks of 10,000 steps | Waits, up to 30 seconds (`--report-grace`) since the report was last current; then the report is `stale` |
| `stale` | Still behind after that wait: the server was restarted with `--no-detect`, its detectors failed for this rank, or it died between storing a part and reporting on it | Reads the parts and runs the detectors here, and says the report stops at step X while the store holds step Y |
| `missing` | Parts, and no report: `--no-detect`, or a server from before its detectors | The same, at once if no report was ever seen |
| `unusable` | A report for another run or rank, from a server with fewer kinds, ahead of the store, or beside parts whose names carry no steps | The same, at once |
| `other_thresholds` | A threshold given here (`--overload-threshold`, `--drift-tolerance`, `--starve-window`, `--starve-ratio`, `--top-k`) differs from what the server applied (its own are set with `tensorquill-server --thresholds`). One not given here is taken as the server applied it | The same, at once, with the value given here and the server's values for the rest |
| `unreadable` | The file could not be read or parsed on this look | Waits like `behind` |

Each evidence file says which happened under `detection` (`source` is `server` or `python`, with `state`, `reason`, and the steps and attempts compared), and the summary's last line says it in words. Evidence built from a report has no `samples`, `weight_trends`, `layer_count` or `router_names`: per-step data stays in the parts. `--recompute` ignores the report and gives them, at the cost above.

After a restart, specifically:

- **A clean stop or a kill, then a new server.** Every part the old server acknowledged was judged before it went on, so the report it left is still `current` for what is stored, and stays so until a rank sends again. The new server then rebuilds that rank from the store and the report moves on (`rebuilds` starts again at 1).
- **A kill between storing a part and reporting on it** leaves a report that is `behind`. A watcher that starts then works the incidents out itself; one that was already running waits its 30 seconds first. The next part the new server stores brings the report up to date.
- **The status file.** A killed server leaves its last `watchdog.json`, which may say `active`. A running server rewrites an unfinished run's status at least every `refresh_seconds` (30 by default) whether or not anything changed, so a stall that lasts an hour still has a fresh status. When the status claims a running server and is older than twice that, the summary says the status was last written N seconds ago and that nothing is watching the run for stalls; the same holds after a restart until a rank of the run reconnects, because the new server does not know the run yet. After a clean stop the status says `server_stopped`, and the summary says so. Neither is printed as a bare "No incidents detected."

Limits: the watcher judges freshness by the newest attempt only, so a part of an older attempt that arrived late and was not judged goes unnoticed; a NaN or Inf logged value prints as "not finite" (it is `null` in the server's file); `job_stalled` and `rank_silent` carry no logged scalars when they come from the status; and one rank is watched per command unless `--rank all` is used. [`tests/test_server_reports.py`](tests/test_server_reports.py) (12 tests) produces each state with the real server. Twenty-two deliberate changes to the reader's rules each fail it.

**All ranks at once.** `python -m tensorquill <store>/runs/<run_id> --rank all --watch` (and `watch(run_folder, rank="all")`) keeps one evidence file for a run with several `rank=N` folders, `<run_id>.all-ranks.evidence.json`, in a shape of its own (`"view": "all_ranks"`, `"view_version": 1`; no `schema_version`, `incidents` or `samples`, so the per-rank shape is never mistaken for it). A look reads each rank's `incidents.json` and newest part name, and the run's `watchdog.json`, and nothing else: 34 ms for 64 ranks of 10,000 steps, 102 ms at 50,000, on an 8-core laptop. A rank counts for or against incidents only while its report is `current`; `behind`, `stale`, `missing`, `unreadable`, `unusable`, `other_thresholds` and `nothing_stored` are *unknown*, with the reason, and never in the list of ranks with no incidents. Each rank has its own wait (`--report-grace`), and inside it reads as its last current report when another rank or the status causes a write (since Nov 18, 2026; before, it was unknown for that write). Incidents with the same kind, step and named layers, experts, parameters or modules are one group naming the ranks ("0-63"); those that differ are listed with their ranks, and an incident on one rank is named with that rank alone. A group carries one incident (the first rank's) and says whether the others' numbers differ. The text summary gives what is common to all judged ranks, what only some show, the ranks with none, and the unknown ranks; stalls and silent ranks (`job_stalled`, `rank_silent`) are in `run_incidents` once for the run. Ranks are the `rank=N` folders, the status's ranks and `world_size`, so a rank that never stored anything is `nothing_stored`, and after a restart a rank that has not reconnected is still judged from the store. The file is replaced by rename only when a rank's report, a rank's state, the set of ranks or the status changed. No part is read and no detector runs here, so `--recompute` and `--rerun` are refused with `--rank all` (use `--rank N`), a threshold option given with it must be the one each rank's server applied (else that rank is `other_thresholds`), and `--detectors rust` changes nothing; without `--watch` it makes one look. The same look is one call in Python, `tensorquill.evidence.all_ranks_evidence(run_folder)`, which returns the evidence and writes nothing. Limits: a rank is called stale only after `--report-grace` and a blip inside it is not written; `stored_last_step` of an unknown rank is as of the last write; a rank is judged against its own store, so ranks at very different steps are all `current` (the spread is in `last_step` and in the status's `stream` entries and `rank_silent`); numbers differing between ranks are in each rank's own `incidents.json`, not copied.

### The Rust detectors on a local file

`tensorquill-server detect` runs the server's detectors over one rank's rows without a server or a store, and prints the report the server would write as that rank's `incidents.json`. Python calls it, so the 26 per-rank kinds can come from the one Rust implementation on a local `.jsonl` file too:

```sh
cargo build --release --manifest-path server/Cargo.toml
export TENSORQUILL_SERVER_BIN=$PWD/server/target/release/tensorquill-server
python -m tensorquill tensorquill-out/RUN.rank0.jsonl --detectors rust
```

**Which detectors run (Nov 17, 2026).** `--detectors` takes `auto`, `python` or `rust`.

- *One read* (`python -m tensorquill run.jsonl`) uses `auto`: the Rust detectors when the binary and `pyarrow` are there, and otherwise the Python detectors with one warning on standard error that says what to install. `--detectors python` gives the Python detectors without the warning, and `--detectors rust` stops when the Rust ones cannot run.
- *`--watch`* needs the Rust detectors. Without the binary or `pyarrow` it stops before its first look, with exit status 2 and what to install; only `--detectors python` makes it watch with the Python ones. `--rank all` runs no detector, so it asks for no binary.
- *The binary* is looked for in `TENSORQUILL_SERVER_BIN`, then beside the Python that is running (where `pip install tensorquill-server` puts it; `tensorquill` depends on that package), then on `PATH`. It is run only when `tensorquill-server protocol` prints the number this package was built for (`server_detect.PROTOCOL`); another number, or none, counts as no binary, and the message says to upgrade both packages. The SDK and `tensorquill-server` must be built from the same version: both speak protocol 4 since Nov 21, 2026 (3 before), when `detect --follow` was added. With a binary of another protocol:
  - `--watch`, and `--watch --detectors rust`, stop before the first look with exit status 2 and no evidence file: `--watch needs the Rust detectors: <binary> speaks protocol 3 and this tensorquill needs protocol 4: install a tensorquill and a tensorquill-server that match (pip install --upgrade tensorquill tensorquill-server), or rebuild the binary from this source. To watch with the Python detectors, add --detectors python`.
  - One read with `--detectors rust` stops with exit status 2, no evidence file and the same message from `<binary> speaks protocol ...` on.
  - One read with no `--detectors`, or `--detectors auto`, uses the Python detectors, writes the evidence and prints one line on standard error that starts `tensorquill: warning: using the Python detectors, not the Rust ones: <binary> speaks protocol 3 and this tensorquill needs protocol 4: install` and ends by saying that `--detectors python` asks for the Python detectors without this warning.
  - A binary you built yourself with `cargo build` must be built again after you upgrade the SDK; until then it is refused as above.
- *In Python* the default is unchanged: `build_evidence` and `watch` use `detectors="python"` and start no process, and `detectors="auto"` chooses as one read does, with a `RuntimeWarning`.
- *Not yet true of an install:* `tensorquill-server` is not on PyPI, so until it is the binary comes from `cargo build`. `pyarrow` is the `flight` extra and not a dependency, so a plain `pip install tensorquill` will warn on each read and refuse `--watch` until `pip install 'tensorquill[flight]'`.

In Python it is `tensorquill.build_evidence(records, detectors="rust")`, and `tensorquill.server_detect.server_report(records)` gives the report itself.

- **What it needs:** the binary (found as above) and `pyarrow` (the `flight` extra). The records travel as an Arrow stream in the schema the sender uses.
- **What comes from Rust:** the incidents of the 26 per-rank kinds, with their scalars, the `not_checked` entries, what was checked for those 26 kinds (`kind_checks`), and the per-step MoE `samples`. The evidence then carries `"detectors": "rust"`.
- **What is still made in Python:** the router names and sizes, the weight trends, the run state, and the kinds read from other files (the server's status, TrainCheck, the Flight Recorder). No MoE rule runs in Python on this path.
- **The samples** are an option of the subcommand, `tensorquill-server detect --samples` (`server_report(records, samples=True)`): one more key in the report, `samples`, with one entry for every record and router as `build_evidence` lists them. Without the option the report is unchanged, and the server's own `incidents.json` never has them.
  - *Why not in `incidents.json`.* On 10,000 steps of 24 routers of 32 experts the report is 2.1 KB without samples and 96.9 MB with them, and the server would hold every sample in memory for each rank. The Parquet parts already hold the counts.
  - *Time, release binary, the same run, on a laptop under load:* 131 ms without samples and 324 ms with them. Through Python, with the records turned into an Arrow stream (1.8 s) and the output parsed, `server_report` takes 2.2 s and 3.5 s. `build_evidence` takes 5.6 s with the Python detectors and 3.5 s with `detectors="rust"`.
  - *Equal to Python's with no tolerance:* every field of every sample is the same value of the same type, a float the same double.
- **Thresholds:** the six options of `build_evidence` (`overload_threshold`, `drift_tolerance`, `starve_window`, `starve_ratio`, `top_k`, `update_window`) go to the Rust rules, and each has a flag on the command line (`--overload-threshold`, `--drift-tolerance`, `--starve-window`, `--starve-ratio`, `--top-k`, `--update-window`). See "Detector thresholds" below.
- **Limits:**
  - In Python the default is still `detectors="python"`; on the command line it is `auto` for one read and `rust` for `--watch` (above).
  - A binary built from other thresholds than the SDK's, or one that lacks any of the 26 kinds, is refused.
- **Checked** in `tests/test_server_detect.py`: both paths give the same evidence on 57 record sets and on the seven Gate 1 fixtures. The record sets plant every one of the 26 kinds and every kind of `not_checked` entry, and include resumes and restarts written a stretch at a time and the edge cases of the server parity tests. Run by hand on eight recorded GPU captures (the seven of Nov 15, 2026 and an older Granite one; five hold 15,600 real MoE samples each), both paths give the same incidents, `not_checked`, `kind_checks` and run state, and the same samples with no tolerance.
  - The samples are compared field by field on those sets, at each of the 18 threshold option sets and with a `top_k` for one router. A difference is reported by step, router and field. The golden files (`tests/golden/`) hold the Rust samples to 1e-12, because a file may have been written on another platform.
- **Two differences, both pinned by a test:**
  - A step written twice within one attempt is reported by both, but Rust attaches the scalars logged at its second writing and Python those of its first. The server's own store never holds such rows.
  - Both engines take attempts in the order they first appear, whatever their numbers, and read each attempt's rows in step order.
- **Two more, in hand-made records only** (the SDK writes neither):
  - Python applies the last `moe_top_k` a run recorded to every step; Rust judges each step with the value known when it is read. This already held for the incidents and now holds for the samples' `overload_rule`.
  - A recorded `moe_stats` diversity that is not a finite number is used as it is by Python and replaced by the one worked out from the counts in Rust.

**Watching through Rust.** `python -m tensorquill run.jsonl --watch --detectors rust` (and `watch(path, detectors="rust")`) judges through `tensorquill-server` whenever the detectors run here: for a growing `.jsonl` file, and for a server's store whose report cannot be used (`--recompute`, or a report that is missing, stale or unusable). Since Nov 21, 2026 (protocol 4) the watcher keeps one `tensorquill-server detect --samples --follow` process for the whole watch, which holds the rank's detectors between looks, and sends it only the records appended since the last look (`server_detect.FollowedDetect`).

- **What is an append.** The records read before are the first records now, each unchanged; the thresholds are the same; and every new record is of the newest attempt, with a step above every step read before. The binary checks each append again and refuses one that names a router it has not seen or gives a router more experts.
- **What is judged again in full.** Anything else: late rows of an earlier step, a new attempt (a resume), a file rewritten, truncated or replaced, a stored part replaced or removed, other thresholds, and an append the binary refuses. The watcher then ends that process, starts another and sends it every record. The first look always judges every record.
- **A change of the thresholds the watcher reads** (those a server applied, from its report) is judged again at once, in full, with no new record needed. Before Nov 21, 2026 such a change waited for the next record, and the file showed thresholds no longer in force.
- **Its memory.** That process holds the rank's detectors in memory between looks, for as long as the watch runs; before protocol 4 a `detect` process existed only during a look. On the 10,000-step, 24-router benchmark store (32 experts, top-8; measured once by wave AF-W, Nov 21, 2026) the detector child had about 237 MB resident after the first look and between looks, 239 MB after one more part, and a peak of 386 MB during the first look. These are the detector child's figures, not the watcher's: the watcher's own Python process was about 1.56 GB resident beside it.
- **Its end.** It ends with the watcher: when the watch returns, at Ctrl-C, after an error inside a look, and when the watcher is killed with SIGTERM or SIGKILL, because it then reads the end of its input. One read without `--watch` runs `detect --samples` and starts no such process.

- **The same evidence at every look.** Each of the 57 record sets and the seven Gate 1 fixtures is written to a file a quarter at a time under two watchers, one with each engine: at every look the incidents, `not_checked` and the run state are the same (numbers to 1e-12, a logged NaN as `null`) and every other key is equal ([`tests/test_watch_rust.py`](tests/test_watch_rust.py), 77 tests).
- **`--compact` and the trigger are the same.** They act on the evidence after it is built. The compact file is equal but for `"detectors": "rust"`, a planted failure starts the command once with the same payload, and five of the trigger's own tests pass again unchanged with the option given.
- **A missing binary or `pyarrow` is said before the first look**, not at the first rebuild, and the command line exits with status 2 and the reason.
- **What a rebuild costs.** One rebuild over every record read so far, timed in its parts. Medians of five on an Apple M1 Pro (8 cores, macOS) shared with other work: the load average fell from 45 to 4 during the run, and the 1,000-step rows ran at the highest.

  | --- | ---: | ---: | ---: | ---: | ---: | ---: |
  | Granite-shaped (24 routers, 32 experts, top-8), 1,000 steps, 28 MB | 766 ms | 885 ms | 304 ms | 199 ms | 383 ms | 1,229 ms (548) |

Measured again on the merged tree with the samples from Rust (release binary, medians of five, load average 7, records from the bake-off's generator with 24 routers of 32 experts, top-8): 435 ms through Python and 401 ms through Rust at 1,000 steps, and 4,500 ms against 3,877 ms at 10,000 steps. So a rebuild through Rust is now 8% to 14% shorter. The parts were not timed again, and the sentences below describe the table.

  Through Rust a rebuild takes 10% to 23% longer than through Python with the release binary, and 46% to 68% longer with the debug one. At 10,000 Granite-shaped steps the judging itself is the smallest part (1.8 s); before it the records are converted to Arrow (2.8 s), and beside it Python still makes the per-step samples and the other keys of the evidence (4.3 s, not timed apart). Reading the whole 285 MB file once takes 2.3 s, which a poll does not pay again.
  The table and the sentence above are a full look, every record judged: what the first look, and any look that is not an append, still costs. They were measured before `detect --follow`.
- **What is and is not read again.** The file is tailed from an offset, so only new lines are read from disk. A look that is an append converts only the appended records to Arrow, and the `detect --follow` process judges only those (above). A look that is not an append converts every record read so far and judges them from the first row, as every look did before Nov 21, 2026.

**All ranks.** `--rank all --detectors rust` is accepted and changes nothing. That view takes one source, a run folder in a server's store, and runs no detector: every rank's incidents are read from the report its server's Rust detectors wrote. So it needs no binary, and the evidence is equal with and without the option. (It needs `pyarrow` in one case only, as before: `--flight-recorder` finding a stuck collective opens the newest stored part to date the dump.) [`tests/test_all_ranks_rust.py`](tests/test_all_ranks_rust.py) runs every test of the all-ranks view a second time with the option given (36 tests).

**Every rank of a run: `detect --run`.** `duplicate_batches` compares the rows of several ranks, which `detect` on one rank cannot do. The server judges it for a live run and writes it to `watchdog.json`. Without a server:

```sh
tensorquill-server detect --run rank0.arrow rank1.arrow     # or one stream holding every rank, on standard input
```

- **How the ranks reach it.** With `--run`, `detect` takes any number of Arrow streams and groups the rows by their `rank` column, so it does not matter how the ranks are spread over the inputs. Within a rank the rows must be grouped by attempt, in the order first seen, as for one rank; an attempt whose rows reappear after another's is refused. Rows of a second run are refused.
- **What it prints.** One JSON document: `reports` (each rank's report, exactly what `detect` gives for that rank alone), `duplicate_batches` (the finding the server puts in a run's status, or `null`), `incidents` (the same as an incident with its class), `ranks`, and `ranks_compared` (the ranks that had a hashed batch to compare, so "no duplicates" can be told from "nothing to compare").
- **From Python.** `tensorquill.server_detect.server_run_report(records)` returns the document, and `server_duplicate_batches(records)` gives the incident or `None`, sending only each record's keys and `data`. Pass every attempt of every rank: Rust leaves out what a resume rolled back.
- **Checked** in [`tests/test_run_detect.py`](tests/test_run_detect.py) (73 tests) against Python's `detect_duplicate_batches` on the same records: the cases of the data-check tests, the four-rank run with a resume that the server test uses, a run longer than the 4,096-step window, a rank that stopped early, and each of the 57 parity record sets as two ranks that share every third step's batch.
- **One difference, pinned by a test:** a step written twice within one attempt is compared across ranks by its last writing in Rust and by both writings in Python.
- **Limits.** Without `--run`, `detect` reads one rank as before and refuses a second. Every rank's rows are held in memory at once. Not run on more than four ranks, and not timed.

### Detector thresholds

The Rust detectors take their options as one JSON object, `--thresholds`, on the server and on `detect`:

```sh
tensorquill-server --store /var/lib/tensorquill --thresholds '{"overload_threshold": 0.5, "top_k": 2}'
tensorquill-server detect --thresholds '{"starve_window": 20}' < rows.arrow
```

| Key | Default | What it sets |
| --- | --- | --- |
| `overload_threshold` | `0.35` | The base assignment-share threshold for top-1 and top-2 routers |
| `drift_tolerance` | `1e-6` | The relative spread between replicas above which a parameter has drifted |
| `starve_window` | `50` | How many samples of a router the starved check sums over |
| `starve_ratio` | `0.1` | An expert is starved below this fraction of an even share of that window |
| `top_k` | `null` | Experts chosen per token: `null` is what the run recorded, a number applies to every router, and an object gives a number per router name |
| `update_window` | `100` | How many of the last step-to-step changes of the update size, flagged ones left out, make the baseline of `update_spike` |

- **A key left out keeps its default**, so `{}` and no argument are the same.
- **Refused, with exit status 2 before the server listens or `detect` reads its input:** an unknown key, anything that is not a JSON object, a value of the wrong type, a negative number, and a `starve_window`, `update_window` or `top_k` below 1.
- **Only these six are options.** A report lists every other rule's constant under `thresholds` too, but those cannot be set.
- **Every report says what was applied.** `incidents.json` and the output of `detect` list the six values under `thresholds`, and a `replica_drift` incident carries the tolerance it was judged by.
- **A reader takes the thresholds the server applied.** A reader of a server's report (`--watch` on a store, `--rank all`, `read_server_report`) gives no threshold unless one is typed, and then takes the report with whatever the server applied. Only a threshold the reader gives itself that differs from the applied one makes the report `other_thresholds`. This rule is recorded as open to change.
  - **The command line has a flag for each of the six:** `--overload-threshold`, `--drift-tolerance`, `--starve-window`, `--starve-ratio`, `--top-k` and `--update-window`. None has a value until it is typed. On a `.jsonl` file one left out is the default in the table above.
  - **When the one-rank watcher has to judge here,** it uses the value it was given and the server's values for the rest, so the incidents do not move with who judged them. A watcher that never saw the server's report uses the defaults, and so does a read without `--watch`, which does not look at the report.
  - **`--rank all` takes all six,** `--top-k` among them. A rank whose server applied another value than the one given is `other_thresholds` and listed as unknown; nothing is recomputed there.
  - **It is never silent.** Whenever a threshold that was applied is not the default, the summary of the evidence (`incident_summary`, which the command line prints for every look, `--watch` and `--rank all` among them) ends with one line that names each such threshold with its value and the default: `Thresholds that are not the defaults: the server applied overload_threshold 0.5 (default: 0.35), top_k 2 (default: what the run recorded).` When the detectors ran here it reads `the detectors ran here with ...`, and when the judged ranks of the all-ranks view differ, each set is named with its ranks. At the defaults there is no line. `evidence.thresholds_line(evidence)` returns it, or None. A local `.jsonl` file, and a read of a store's parts without `--watch`, print it too when an option typed there is not the default, in one read, with `--rank N`, `--compact` and `--watch`, with the Python detectors and with `--detectors rust` alike: `build_evidence` then lists the five it ran with as `thresholds`, the name the server's report gives them, and the line reads `the detectors ran here with ...`. At the defaults, also when an option is typed at its default value, that evidence has no `thresholds` key, so its file and what is printed are what they were, byte for byte.
  - **The evidence says what was applied.** For one rank of a store, `detection.thresholds` holds the six, whether the server judged or this process did. In the all-ranks view `thresholds` holds them. Evidence judged here with no `detection` key (a local `.jsonl` file, a read of a store's parts without `--watch`, `--watch --recompute`) holds them as `thresholds` only when one is not the default. When the judged ranks were not all judged by the same values, which a server restarted with other thresholds leaves until each rank sends again, `thresholds_by_rank` lists every set with its ranks and the summary says so.
  - **`top_k` left out is "not given"** like the other four, so a reader cannot insist on "what the run recorded" against a server started with a `top_k`.
  - **Checked** in [`tests/test_reader_thresholds.py`](tests/test_reader_thresholds.py) (24 tests): taking, matching and refusing, each through `read_server_report`, the one-rank watcher, the all-ranks view and the command line, and a watcher that loses the server's report and judges here with the server's values.
  - **The printed line is checked** in [`tests/test_thresholds_line.py`](tests/test_thresholds_line.py) (20 tests): no line at the defaults, also after a round trip through JSON, and the summary there is what it was; each threshold alone and all five; a real server started with `--thresholds` and one at the defaults, for one rank's evidence, for the all-ranks view, for ranks judged by different sets, and in what the command line prints; and for a local file in every output of the command line (one read, `--rank 0`, `--compact`, `--watch`, the Rust detectors) and a read of a store's parts without `--watch`, each with options off the defaults and at them.
- **From Python**, `build_evidence(..., detectors="rust")` sends its own options this way, and `server_report(records, thresholds={...})` takes the object directly. A value the Rust rules refuse raises `ValueError` under either detectors, checked before anything is sent: "the detectors refuse these thresholds: ...".
- **Checked** in `tests/test_server_detect.py`: 17 option values and one combination of all five, each on the eight record sets that hold MoE counts or a replica spread, give the same evidence on both paths, and each changes at least one incident in Python, so an ignored option would fail. A per-router `top_k` is tested on five record sets against the value recorded on every row. A live server started with thresholds matches Python across three appended stretches and a restart, and a watcher asking for the same values or for none takes its report while one asking for another value recomputes.
- **Not re-timed:** the 64-rank detector benchmark has not been rerun with the options in place.

## Compact evidence and the trigger

Built Nov 16, 2026 in `compact.py` and `trigger.py`, with small calls from `watch` and the command line.

**Compact evidence.** For an MoE run the per-step `samples` are nearly the whole evidence file. `--compact` writes the file an agent reads: every incident and every other key as they are, and of `samples` only the steps near each MoE incident.

```sh
python -m tensorquill run.jsonl --compact
python -m tensorquill run.jsonl --watch --compact --compact-window 20
```

- **What is kept.** The samples within `--compact-window` recorded steps (default 5; 0 keeps the incident's own step alone) of each `moe_imbalance` or `starved_experts` incident, for every router of those steps.
- **Where it goes.** `<input>.evidence.compact.json`, written instead of the full file. The full file is the cost being avoided and can be rebuilt from the records; under its own name, a full file already on disk is never replaced by a smaller one.
- **What says it is compact.** A `compact` key lists the window, the incidents the windows are around, the steps kept, how many samples were left out, and how many samples were flagged and the last step one was.
- **Replica observations (Nov 21, 2026).** Two lists of a run's replica observations are shortened in the compact file only; the full evidence is unchanged.
  - *Routine step entries of `replica.steps` are left out and counted.* An entry is routine when every rank of its group observed that step and either the fingerprints and signatures agree or the group is one rank, and it says nothing else. Every other entry is kept, with every entry of the steps within `--compact-window` observed steps of a replica incident, a verdict, an attribution entry or a step the kind's entry names. The marker `compact.replica_steps` gives `total`, `kept`, `omitted`, `not_routine`, `around`, `kept_steps` and `observed_steps`; `compact.describe` then names how many routine entries were left out.
  - *A coverage list of one-rank gaps is shortened.* When every gap in `kind_checks.replica_drift.coverage.not_compared` is a group of one rank (`fingerprints_why: "one_rank"`), the latest gap of each launch, group and reason is kept in the list's order, and `not_compared_omitted` counts every other. The marker `compact.replica_not_compared` gives `listed`, `kept`, `removed` and the `not_compared_omitted` the full evidence had. A list with any other gap, a missing peer among them, is kept whole.
  - `replica_line`, the summary's replica line, reads the same from both files. Code that needs every step entry can call `compact.require_all_replica_steps(evidence, what)`, which raises `compact.ReplicaStepsOmitted`, a `SamplesOmitted`, on a file that left some out.
- **What still works.** `incident_summary` and the `Run state:` line print the same text for both files. `expert_load_table` and `export_rerun` raise `compact.SamplesOmitted`, naming the kept steps, when asked for what was left out. `--compact --rerun` records from the full evidence in memory.
- **Measured** on the detector benchmark's Granite-shaped run (24 routers, 32 experts, top-8) at 10,000 steps with two MoE incidents planted:

  | File | Size |
  | --- | --- |
  | Full | 86.5 MB |
  | Compact, window 5 | 195 KB |
  | Compact, window 0 | 22 KB |
  | No samples at all | 3.9 KB |

  The 1 MB line holds up to a window of 28 steps.

  These were measured before the evidence said what was checked. `kind_checks` adds 3.0 KB to every file: measured again as compact JSON, the same run gives 197,570 bytes at a window of 5, 24,541 at 0 and 6,495 with no samples, and the 1 MB line still holds up to 28 steps. With `enough_history` and `records_needed` (added Nov 16, 2026) the key is 4.2 KB as compact JSON, 1.2 KB more (4,239 bytes against 3,023 on a router-only run); the three sizes were not measured again.

**The trigger.** With `--watch`, `--on-incident COMMAND` starts a command and `--webhook URL` posts JSON, once for each new incident. Nothing is started or sent without one of the two.

```sh
python -m tensorquill run.jsonl --watch --compact --on-incident 'my-agent "Explain the $TENSORQUILL_INCIDENT_KIND incident in $TENSORQUILL_EVIDENCE"'
python -m tensorquill store/runs/r --rank all --watch --webhook https://example.com/hooks/tensorquill
```

- **New** means its rank, kind and step have not fired before in its run (a later run whose evidence goes to the same path fires its own); for a stall, that no stall episode of its run is open (below). What fired is kept in `<evidence>.fired.json`, so a restarted watcher does not fire again; delete the file to start over.
- **What fires.**
  - By default: invariants, and **a stall that has reached `critical`**.
  - `--fire-anomalies` adds the anomalies, whose thresholds are not tuned on other jobs yet.
  - `--fire-kind KIND` adds one kind by name. It is the only way any other observation fires, or a stall that is still a `warning`.
  - A change of run state never fires, and neither does a kind this version does not know.
- **A hang.** A stalled job (`job_stalled`) and a silent rank (`rank_silent`) fire with no option once their `severity` is `critical`.
  - The server sets the severity: `warning` after `--silent-seconds`, and `critical` after `--critical-seconds` (900 by default) or three of the rank's own silence thresholds if that is longer. Only a rank that is silent, unresponsive or lost has one, or one that was silent or unresponsive when its stream dropped and reads `reconnecting` (see "What `reconnecting` means"): a hung rank whose connection drops, opens again under the same attempt and still does not step is one episode and fires once (a rank that is killed and started again is a new attempt, which ends the episode: if it stalls too, it fires again). A rank in a declared evaluation or checkpoint phase is `paused` and cannot make a stall critical.
  - Any stall at `critical` fires, whatever its `assessment`, and the label goes with it: `TENSORQUILL_INCIDENT_ASSESSMENT` for the command, `assessment` in the document, and the summary. `suspected_hang`: a stopped rank is still connected and does not step. `lost_connection`: a rank's stream dropped and did not come back, as it does when its process is killed (an out-of-memory kill among them) or the network fails; the summary says it is not read as a hang. A stall reads as a lost connection when a lost rank explains it: every stopped rank is lost, or the whole job stopped (`job_stalled`) and at least one rank is lost, since the ranks still connected are then waiting for it. A lost rank beside a silent one while other ranks step is a suspected hang. `lost_ranks` names the lost ranks either way.
  - The two kinds stay observations. The command gets `observation` as the class, and the run state reads `unknown` for a stall, not `unhealthy`.
  - Once: a stall named with `--fire-kind` fires at `warning` and not again when it becomes `critical`. One not named fires once, when it becomes `critical`.
  - One firing for one stall episode (the author's decision of Nov 17, 2026, in place of one firing a run). A stall that fires opens an episode and nothing more fires until a stall is next listed showing progress or a new attempt. Progress: for an episode opened by `job_stalled`, a rank has stored a step beyond the run's highest step when it fired; for one opened by `rank_silent`, a rank of the episode has stored a step beyond the one it stopped at (also once it has recovered: a `rank_silent` lists the other ranks' steps under `other_ranks`), so the ranks stepping beside a silent rank never end it. A new attempt: the `attempt` the server's status gives a rank of the episode has changed, and no rank of the episode is still stopped exactly as it was (the ranks of a job started again come back a look or more apart). The server learns it from the new process's first heartbeat, before it stores a step. A silent rank whose job then stops is one firing; a job that steps past its stall, or is started again, and stalls again fires again, each time after a fresh `--critical-seconds` of silence. A server restart re-arms nothing. A rank that stops during an open episode joins it; once any rank of the episode steps on, it is over, and a joined rank still stuck then fires. A state file of an earlier version loads, its last stall taken as the open episode. A job started again that hangs before it stores a step fires once it is critical in its own start window: with the defaults 2,700 s after the new process's first heartbeat. Not seen with heartbeats off (`heartbeat_seconds=None`) or a sender from before Nov 17, 2026, whose heartbeats name no attempt: its new attempt is known from its first stored batch, as before.
  - **Only a watcher of a server's store can fire for a hang.** A local `.jsonl` file with no server has no stall kinds at all (see "Streaming to an ingest server"), and `collective_hang`, an invariant, needs `--flight-recorder`.
  - Not held back: ranks that wait in `train` while another rank runs a long declared evaluation are silent, not paused, and become critical like any other.
- **The command** is one string run by the shell.
  - It gets the incident as JSON on standard input, and `TENSORQUILL_EVIDENCE`, `TENSORQUILL_RUN_ID` and `TENSORQUILL_INCIDENT_ID`, `_MCP_ID`, `_KIND`, `_CLASS`, `_STEP`, `_RANKS`, `_SUMMARY` and `_ASSESSMENT` (a stall's label, empty for other incidents) in its environment.
  - **Two ids.** `id` (`TENSORQUILL_INCIDENT_ID`, `<run_id>/rank0/non_finite/412`) names the delivery, the same on every try, for a receiver that drops repeats. `mcp_id` (`TENSORQUILL_INCIDENT_MCP_ID`, `<run_id>/rank0/non_finite@412`, from Nov 22, 2026) names the incident for the MCP server: pass it as `id` to `get_incident`, with no `rank`. It names its run and its ranks (`rank0`, `ranks0-3,7`, or `run` for an incident of the whole run; `#2` onwards for a second incident of that kind and step on those ranks), so it finds the same incident whether that server was started on the run folder, a `rank=<n>` folder, the capture or the evidence file, and it is refused by name for another run. The delivery id is not a lookup id. The ids `list_incidents` gives (`<kind>@<step>`) are numbered over the whole view, so they can differ from one view to another. 
  - **A stall's `mcp_id` is of its episode.** A stall changes its kind and step inside one episode (a `rank_silent` becomes a `job_stalled`) and fires once, and a later stall of the same run, or the job started again, can read exactly as an earlier one did. So a stall's `mcp_id` is its delivery id in the lookup form (`<run_id>/run/rank_silent@49`, and `~2` for a later episode that fired at the same kind and step), and `get_incident` resolves it only where it can show the episode is the same: on the evidence file the trigger named (`TENSORQUILL_EVIDENCE`), whose state file (`.fired.json`) must show that firing's episode still open and not ended by the stall listed now. Then it answers with the stall as it reads now, with `looked_up_as` when its kind or step has changed. Anywhere else (a server started on the run folder, a stall that is over, another episode open) the answer is `"result": "original_incident_no_longer_identifiable"` with the reason, and `current_stall` gives the id of the stall listed now for a separate lookup. A later stall is never presented as the one that fired.
  - It is started and not waited for, so a long agent run does not hold the watcher. The watcher never stops it.
- **The webhook** is one POST of `application/json` with the standard library, 10 s by default (`--webhook-timeout`). Redirects are not followed, and the URL is never printed or stored. The body carries the evidence file's absolute local path.
- **Failures** are printed and never stop the watcher. A command that cannot start or exits with a status other than 0, and a post that fails, is tried again on later looks, 4 tries in all.
- **Limits.**
  - An incident counts as fired once its command has started, so a command that fails while the watcher is down is not tried again.
  - The trigger turns on `--compact` (since Nov 17, 2026): the watcher writes the full evidence as before, and the trigger writes `<name>.compact.json` beside it on every look and names that file in `TENSORQUILL_EVIDENCE` and the document, so the agent that is woken reads the small one. With `--compact` or `--compact-window` given, the watcher writes the compact file alone, as before, and that is the one handed over.
  - Two watchers must not share one evidence path; the state file is not locked.
  - In the all-ranks view an incident several ranks share fires once for those ranks, and once more for ranks that show it later.
- **Checked** in `tests/test_compact.py` (9 tests) and `tests/test_trigger.py` (37 tests): a planted failure in a growing file starts a command with no human step, exactly once across later looks and a restart; the webhook's body against a local HTTP server; a failing command and an unreachable webhook leave the watcher running. For a hang: a real training process that stops stepping while it lives, beside a real `tensorquill-server` with short silence settings, starts the command of a one-rank watcher and of a `--rank all` watcher once each, when the stall becomes `critical` and not while it is a `warning`, and not again on later looks or a restart.
- **Checked, Nov 17, 2026,** with real training processes and a real server (short timings): a rank that falls silent and then a job that stops altogether post once to a `--rank all --watch --webhook` listener, which is handed the compact file while the full one is still written; a rank killed with SIGKILL beside a live one reads as a lost connection, in Rust's incidents and Python's alike, and starts the command once with that label; a server killed and started again while a rank is hung at `warning` fires nothing for 9 s (the rule before fired about 4 s after the restart) and fires once when the rank is critical 12 s after the restart.
- **Not checked:** a real agent as the command, an outside webhook, https, a proxy, Linux and Windows. The watchdog's default timings (300, 900 and 1,800 s) have not been run for real; tests use seconds, and one Rust test pins the defaults on a made clock.

## Data progress and checkpoints

Built Nov 16, 2026, on CPU; no GPU run yet. Both are opt-in.

- **Data.** Iterate `session.watch_loader(loader)` instead of `loader` to record which samples each step drew (a 64-bit BLAKE2b of their indices, never the samples) and the sampler's epoch. For an `IterableDataset` pass `ids=lambda batch: batch["id"]`; `session.data(...)` records them by hand. Measured on CPU: 4 µs per batch of 32 indices, 48 µs per 1,024.
- **Checkpoints.** Call `session.checkpoint(state)` with the dict you pass to `torch.save`, and `session.checkpoint(state, event="load")` with the one you resume from, before the first step; pass `start_step=` as for any resume, under the same run ID, since the resume checks read one run. The Lightning, `Trainer` and Accelerate adapters record checkpoints themselves; none of them turns the loader hook on.
- **Whether the checkpoint holds the model's tensors** (TrainCheck B14; built Nov 21, 2026, on CPU; [contract](../CHECKPOINT_TENSOR_CONTRACT.md)). At `session.checkpoint(state, event="load")` the names and shapes in the checkpoint are compared with the model's, once, before the first step. Say which mapping you load, and nothing has to be inferred:

  ```python
  state = torch.load(path)
  model.load_state_dict(state["model"], strict=False)
  session.checkpoint(state, event="load", model_state=state["model"])
  ```

  - **A trainable tensor that is not in the checkpoint is named.** `resume_incomplete` gets the finding `missing_tensors` with each name (50 at most, and the count), and `shape_differs` for a name both hold with another shape. A frozen parameter, a buffer and a tensor the model does not have are named in the evidence's `checkpoint_tensors` and raise nothing, so an adapter-only checkpoint stays quiet.
  - **Without `model_state=`** the entry is inferred: the one entry under a conventional key (`model`, `state_dict`, `net`, `module`, `network`, `weights`), even beside a fuller `ema` copy, or else the one entry whose names are the model's. An inferred entry is compared only when it holds at least half of the model's names. Two entries that could each be the model's, or one that holds too little, give no comparison: `checkpoint_tensors` says `unavailable` with `ambiguous` or `weak_match`, and nothing is named as missing.
  - **Silence means every trainable tensor was verified only where `checkpoint_tensors` says `compared`.** A checkpoint folder whose weights are not in `.safetensors` files (FSDP's `pytorch_model_fsdp*`, DeepSpeed's `*_model_states.pt`, any `.bin` or `.pt`), or whose headers are refused, reads `unavailable`, `folder`: the tensors were not looked at. A capture written before this has no `checkpoint_tensors` at all.
  - **A checkpoint folder** (lane AK-2, Nov 24, 2026, on CPU; the contract's folder section awaits the author's sign-off). At `session.checkpoint_files(folder, event="load")`, which the `Trainer` and Accelerate adapters call at a resume, the model's weights in the folder are compared as a state dict is: `model.safetensors.index.json` with the shards its `weight_map` names (what `save_pretrained` writes when it shards), or each `.safetensors` file on its own (`model.safetensors`; Accelerate's `model_1.safetensors` for a second prepared model is a second candidate, never part of the first). From each file only the first 8 bytes (the header length N) and the N-byte JSON header are read, with plain file reads: no tensor byte, no `safetensors` import, and a pickled file (`.bin`, `.pt`) is never opened. `entry` is the file compared and `by` is `name` (`model…`) or `names`. Anything that cannot be trusted (N over the format's 100 MB cap or past the file's end, a short file, a header that is not a UTF-8 JSON object, an entry without a string `dtype` and a `shape` of whole numbers, an index naming an absent shard or a path, a tensor in two shards, a file that is not a regular readable file, more than 1,024 files or 32 MiB of headers in all) is refused, never raised: `unavailable`, `folder`, with `refused` giving the reason and `file` the file, both in the record only. A save opens no file. Measured on an 8-core Apple M1 Pro shared with other tests, warm page cache, median of 50: reading the headers takes 0.07 ms for one file of 12 tensors, 0.4 ms for one of 291 (a 32-layer Llama), 0.55 ms for the same in 3 shards, 1.4 ms for 14 shards and 723 tensors (an 80-layer Llama) and 17 ms for 11 shards and 9,555 tensors (1 MB of headers); the whole call, with the model read and compared, takes 0.18, 2.4, 2.8, 6.9 and 23 ms. A real `Trainer` resume from a folder whose `model.safetensors` lost a tensor names it (`tests/test_lane_ak2_safetensors.py`, through both engines for a hand-made folder). **A Mixtral or another model Transformers 5 converts on load** is saved by `save_pretrained` in its original format (experts one by one, where the model holds them fused), so its folder reads with the fused experts `missing`: true for a `Trainer` resume, which loads that file with `load_state_dict(state_dict, False)` and leaves the experts and the router as initialised (a real resume of a tiny Mixtral, transformers 5.23, shows it), and wrong for a folder loaded with `from_pretrained` and recorded by hand. Not run: a cold disk or a network file system, where each file's open and two reads cost more; a GPU; a real FSDP or DeepSpeed folder, which holds no `.safetensors` weights and so stays `folder`.
  - **What it reads.** Each module's own parameter and buffer tables: names, shapes and `requires_grad`. `model.state_dict()` is not called and no state-dict hook runs, so nothing is gathered from other ranks and no tensor's values are read. A model with a module that replaces PyTorch's walk of parameters (FSDP's wrapper, the activation-checkpoint wrapper) is not read: `unavailable`, `model_not_readable`. A tied weight saved once is not missing. Lightning passes its own `state_dict` entry. Each module's children are read from its own `_modules` table, as `state_dict()` walks them, so a module held twice by one parent is named twice. Two private attributes are read, `_modules` and `_non_persistent_buffers_set`: a module that has buffers and not that set is not read, `unavailable`, `model_not_readable`, since which of its buffers are saved cannot be told. Where taking off `module.`, `_orig_mod.` or the one prefix makes two names of one side one name, which tensor a name stands for cannot be told: `unavailable`, `ambiguous`, with `collides` naming the side (`model` or `checkpoint`).
  - **Only a load at the start of a later attempt is judged.** A checkpoint loaded inside one attempt (a rollback in the same process) is recorded and compared, and the record names what is missing under `checkpoint.load.tensors`, but no detector judges it: no `resume_incomplete` incident, the kind reads `checked`, and the evidence has no `checkpoint_tensors` for it (both engines).
  - **Measured** (CPU, a 5,000- and a 10,000-tensor model, lane AC1's numbers on a shared machine): 18 to 94 ms at the load, never on a step. On 14 model classes (tiny GPT-2, BERT and T5 from configs, nanoMoE, BatchNorm, weight norm, LSTM, a LightningModule, `DataParallel` and `torch.compile` wrappers among them) the names read equal `state_dict()`'s. The re-created B14 run names `lstm.weight_hh_l0` and `lstm.bias_hh_l0` with the Python detectors and with the server, and its healthy twin raises nothing.
  - **Not seen:** a tensor that is in the checkpoint and was never loaded (names are compared, not values); a parameter frozen after the call counts as trainable. Not run: Linux, PyTorch 2.6, a GPU, a real FSDP or DDP job.
- **What is reported.**
  - `epoch_order_repeated`: an epoch in the previous epoch's order (`set_epoch` not called).
  - `data_stalled`: steps advance without new data.
  - `duplicate_batches`: two ranks drew the same batch (in `watchdog.json`, compared across ranks).
  - `resume_data_mismatch`: a resume repeated or skipped data.
  - `resume_incomplete`: a resume did not restore a component (optimizer state, scheduler, scaler, RNG). For the model component, when no entry of the checkpoint is identified as the model's state, the finding is `not_identified` ("model state could not be identified") and not `missing`: the rule that looks for it can fail to find one that is there. At a load the entry is found by its names against the model's (above), so a bare state dict is the model's and a cache with parameter-like names is not. The last two are observations, judged at a resume's first step as `resume_lr_change` is.
- `python examples/data_checkpoint_check.py` shows all of it on CPU.
- **Limits.**
  - A save made just after a flush is recorded with the next step and is lost if the process ends first.
  - Per-epoch schedulers trip the scheduler check (they count epochs).
  - Lightning saves no RNG state by default, so its resumes list `rng` missing.
  - The server compares duplicates only among ranks it has read since it started, within each rank's last 4,096 hashed steps.
  - Wrapping the loader before handing it to Lightning or the `Trainer` is untested.

## Attention rules and run state

Built Nov 16, 2026.

- **Attention rules.** With `probe=`, three kinds are read from the probe's records, in Python and in the server:
  - `attention_collapse`: a block's mean attention-entropy share at most half its own baseline.
  - `attention_uniform`: the share risen to 0.98 or more, at least 0.2 above its baseline (attention that had structure spread evenly over every key).
  - `attention_logit_growth`: the largest pre-softmax logit at least twice its baseline.

  A block's baseline is the median of its last five probes that met no rule. A change must hold on two probes in a row and is dated at the first. With the default `probe_every=1000` nothing can be reported before the 4,000th step (the fourth probe, which confirms a change first seen on the third). Until then the attention kinds are `checked` with `enough_history` false, which does not degrade the run.

  Calibrated on the recorded SmolLM2-360M seeds (the blocks after the seed go uniform, 0.23 to 1.00, or collapse, 0.30 to 0.05) and on small models trained from scratch on CPU. The logit rule's margin is thin: healthy training moved the largest logit 1.7×, and the rule needs 2.0×. Nothing about MoE models was calibrated (the Granite captures have no probe records). `probe_json` now keeps the model's module order.
- **Run state.** `evidence.json`, the all-ranks file and the server's `watchdog.json` carry `run_state`; the worst reason wins, and each reason is listed with a stable `code`:
  - `healthy`: every expected source is current and no incident is listed. A `.jsonl` read alone can be healthy: no server was watching it, so its stall kinds are not configured (see "What was checked").
  - `degraded`: a kind is unavailable (anything in `not_checked`, or no `watchdog.json` where a server stores the run or a status was named).
  - `unknown`: required evidence is stale or missing (no steps judged, a server report that is not current, a rank without a current report or not yet connected under `world_size`, an old status, a stopped server, a status this version does not know).
  - `unhealthy`: an invariant or anomaly is listed (or a kind this version does not know).

  Every incident carries a `class` (the table is `tensorquill.evidence.INCIDENT_CLASSES`, the same in the server):
  - `invariant`: should never happen, such as `non_finite`, `replica_drift`, `duplicate_batches`, `epoch_order_repeated` or `hardware_errors`.
  - `anomaly`: judged against the run's own baseline, such as spikes, drift, collapse, attention, memory growth or input starvation.
  - `observation`: context that claims no failure. These are `resume_lr_change`, `resume_data_mismatch`, `resume_incomplete`, `gpu_throttled`, `memory_imbalance`, `memory_pressure`, `allocator_retries`, `job_stalled` and `rank_silent`.

  Observations are listed under the reason `observations` and never make the state worse, so a run with only observations reads `healthy` with them named. A stall is an observation of the stream (a hang, a long pause and a dead sender look the same), so a `stalled` or `degraded` status makes the run `unknown`, not `unhealthy`. The CLI and `--watch` print the state as `Run state: ...`, and the summary adds a `By class:` line. Incidents are never closed, so a run stays unhealthy once an invariant or anomaly is found. A `watchdog.json` that is no longer being rewritten says nothing about now: read its age (`written_at_ms`, `refresh_seconds`) before its `run_state`.

## What was checked

Built Nov 16, 2026. "No incidents" means little without knowing what could have been found: a router-only capture cannot show stalled weights, and a run without `scaler=` has no loss-scale check. Every evidence file now gives each of the 33 kinds one of three values, under `kind_checks`:

| Value | Meaning | Run state |
| --- | --- | --- |
| `checked` | Records carried what the kind is judged from, and its rule ran over them. For a kind read from a file (the server's status, Flight Recorder dumps, TrainCheck's results), the file was given and read | Unchanged |
| `not_configured` | The capture was never set up to provide it: no record carries the input, or the file was not given | Unchanged |
| `unavailable` | It was asked for and could not be judged: a `not_checked` entry names the kind, or a server stores the run and its progress status is missing | `degraded` |

```json
"kind_checks": {
  "moe_imbalance": {"value": "checked", "records": 60, "records_needed": 11, "enough_history": true,
                    "needs": "moe: a router's expert counts"},
  "grad_spike": {"value": "checked", "records": 3, "records_needed": 13, "enough_history": false,
                 "needs": "grad_norm or clip_grad_norm"},
  "stalled_weights": {"value": "not_configured", "records": 0, "records_needed": 3, "enough_history": false,
                      "needs": "weights_unchanged with grad_norms (full capture)"},
  "attention_collapse": {"value": "unavailable", "records": 5, "records_needed": 4, "enough_history": true,
                         "needs": "probe with attention (probe=)",
                         "check": "probe", "reason": "1 of 6 probes failed, the first at step 30: RuntimeError: CUDA out of memory"},
  "job_stalled": {"value": "not_configured", "enough_history": false, "needs": "the server's progress status (watchdog.json)"}
}
```

- **The summary carries the count.** `python -m tensorquill` prints a line such as `3 of 33 kinds checked, 30 not configured`, with the unavailable kinds by name when there are any. `tensorquill.evidence.checked_counts(evidence)` gives the numbers and `kinds_by_value(evidence)` the names.
- **Enough history (added Nov 16, 2026).** A kind is `checked` from its first record, and a rule that is still warming up does not degrade the run. So "checked, nothing found" after three records would read as healthy for a rule that needs thirteen. Each kind therefore says whether its rule has had enough history.
  - The 26 kinds read from step records carry `records_needed` beside `records`, and `enough_history` is `records >= records_needed`, whatever the value.
  - The definition: for each rule of the kind, take the fewest records it can report an incident on; the kind needs the largest of those. From then on every one of its rules could have fired. A kind with one rule and no warm-up needs 1.
  - The numbers: `moe_imbalance` 11, `starved_experts` 50 (the `starve_window` the run was judged with), `grad_spike` 13, `stalled_weights` 3, `loss_scale_trouble` 10, `data_stalled` 4, `epoch_order_repeated` 4, `activation_spike` 11, `activation_drift` 110 (60 until Nov 21, 2026), `dead_activations` 60, the three attention kinds 4, `memory_growth` 6, `hardware_errors` 2, `input_starvation` 21, and 1 for the other nine. `tensorquill.evidence.RECORDS_NEEDED` lists each kind's rules beside the table, and `server/src/detect.rs` has the same table.
  - The other seven kinds have no count. Their source is whole once it is read, so `enough_history` is true exactly when the kind is `checked`.
  - The summary names the kinds that are still warming up: `6 of 33 kinds checked, 1 of them without enough history yet (grad_spike 3 of 13 records), 27 not configured`. `kinds_by_value` lists them under `not_enough_history` with the two numbers, and no longer under `checked`.
  - Too few probes is no longer a `not_checked` entry. The three attention kinds used to be `unavailable`, and the run `degraded`, until a module's fourth probe; they are now `checked` with `enough_history` false, and the run can read `healthy`. A probe that failed is still a `not_checked` entry and still degrades.
  - It is a floor. `records` counts every record that carried the input. A parameter, module or router seen on fewer records has less history of its own, the memory, hardware and data-wait rules start over at each attempt, and an epoch must end before the next can be compared with it. So `false` means the kind's slowest rule cannot have fired, and `true` means the count has reached what that rule needs. A kind can report an incident before it has enough history, through one of its rules that needs less.
  - A file or a server's report written before the field does not say. `kinds_by_value` lists its checked kinds under `history_not_stated`, never under `checked`, and `build_evidence(..., detectors="rust")` refuses a binary that does not give the field.
  - Checked: each of the 16 kinds that need more than one record has a record set of exactly that many records on which its slowest rule reports and, with one record fewer, does not, through Python and through Rust (`BOUNDARY` in `tests/test_kind_checks.py`, run again in `tests/test_server_detect.py`). The numbers are written by hand in a Python test and in a Rust unit test, and held equal. Tested on macOS; not run on a real job.
- **How a value is worked out.** For the 26 kinds read from one rank's step records, `records` counts the records that carried the kind's input, and `needs` names it (`tensorquill.evidence.KIND_INPUTS` and `INPUT_NEEDS`; `input_counts(records)` does the counting). "Carried" means the field holds something a rule reads: an empty `layers` does not count, and a probe that failed carries no attention.
  - A kind that a `not_checked` entry names is `unavailable`, with that entry's `check` and `reason`, however many records carried its input. One failed probe leaves its step unjudged, as one failed memory reading does.
  - Otherwise it is `checked` when any record carried the input, or when an incident of one of the server's kinds is listed (with a `note`), and `not_configured` when none did. For `resume_incomplete` a finite loss scale counts as its input, beside a checkpoint; a step the loss scaler skipped does not count toward `update_spike`.
- **A failed probe is now listed.** A probe that raised is recorded as `{"error": ...}`. It used to be skipped in silence. It is now a `not_checked` entry with the check `probe`, the three attention kinds, how many probes failed and the first error, so the run reads `degraded`.
- **The other seven kinds.**
  - `job_stalled` and `rank_silent` are `checked` when the server's status was read, `unavailable` when one was expected and is missing, and `not_configured` for a local file that no server was watching. A status is expected when the source is a directory of the server's parts or one part, or when `watchdog=` names one.
  - `collective_hang`, `collective_desync` and `traincheck_violation` are `checked` when `flight_recorder=` or `traincheck=` was given and read, `unavailable` when it could not be read, and `not_configured` when it was not given.
  - `duplicate_batches` and `memory_imbalance` compare ranks, which one rank's evidence cannot: `not_configured`. The all-ranks view judges them.
- **For the whole run, in the all-ranks view** (`--rank all`, `evidence.all_ranks_evidence`, `get_all_ranks_status`). That evidence carries a `kind_checks` of its own, with the same three values and `enough_history`, made from the ranks' reports with no detector run. The rule is `run_kind_checks` in `evidence.py`:
  - Only judged ranks count. A rank that is not judged is named in the count line as not counted and is in no value.
  - A kind read from a rank's step records takes its worst judged rank's value: `unavailable` if any judged rank is, else `not_configured` if any is, else `checked`. So `checked` means every judged rank. When the judged ranks differ, the entry lists them by value under `ranks`, and the count line names them: "1 of them checked on some ranks only (stalled_weights on rank 0)".
  - `enough_history` is false when any judged rank is short (`not_enough_history_ranks`), and is left out when none is short and some rank's report does not say (`history_not_stated_ranks`). `records` is the fewest any judged rank has.
  - `job_stalled`, `rank_silent` and the three file kinds are the run's, by the rule above for the other seven kinds, with a status expected.
  - `memory_imbalance` is `checked` when every judged rank's report has a peak memory reading and there are at least two ranks. `duplicate_batches` is `checked` when the status's `ranks_compared`, which the server writes whether or not it finds a duplicate, lists every judged rank and at least two ranks; without the status it is `unavailable`. A rank is listed only when it was compared with at least one other, so one rank with batch hashes and no peer is listed nowhere and reads `not_configured`, with the note "one rank observed, zero peers compared". A judged rank the list leaves out is `not_configured` for it (unless its own report says its data could not be read), for example right after a server restart, and is named under `not_compared_ranks` when it recorded `data`: the server compares the ranks whose stores it has read since it started, and only batches with a batch hash. A status from a server older than `ranks_compared` keeps the earlier rule (every judged rank recorded `data`, there are at least two, and a status was read), with a `note` saying the status does not list the ranks compared.
  - When no rank is judged, or a judged rank's report has no `kind_checks` (an older server wrote it), the evidence has no `kind_checks` and no count: `kind_checks_not_stated` gives the reason and the ranks, and the summary says "What was checked is not stated".
  - Each judged rank's entry has `kind_counts`, the count of its own report's 26 kinds.
  - One rank's `unavailable` makes the run `degraded`, as before: the rank's `not_checked` entry already did.
  - Checked in `tests/test_kind_checks.py` (15 tests on stores written by hand, each read through `all_ranks_evidence`, the watcher's file and `get_all_ranks_status`), `tests/test_watch_all_ranks.py` (the real server's reports) and `tests/test_mcp_server.py` (over the protocol).
- **A rule that changed: a local file can read `healthy`.** Before, any evidence built without a server's `watchdog.json` read `degraded` (reason `no_status`). Now a `.jsonl` file or a list of records that no server was watching has its stall kinds `not_configured` and no such reason. A server's store whose status is missing, or a named status that cannot be read, still reads `degraded` with `no_status`.
- **In the server's report too.** `incidents.json` and the output of `tensorquill-server detect` carry `kind_checks` for the 26 kinds the server has, made by the same counts. `checked` (the kinds this server can judge) and `not_checked` keep their names and shapes. `build_evidence(..., detectors="rust")` takes the 26 from the report and adds the other seven.
- **Checked** in `tests/test_kind_checks.py` (17 tests, Python only) and `tests/test_server_detect.py`: Python and Rust give the same value, count and reason for every kind on the 57 record sets, the seven Gate 1 fixtures and seven more sets (a router-only run, and probes that are all good, one failed, all failed, too few, or failed with an error that is not text). Every one of the 25 kinds is `checked` in some set and `not_configured` in another, and the 11 kinds a `not_checked` entry can name are each `unavailable` in one. The golden files hold `kind_checks` for both paths.
- **Limits.**
  - `enough_history` holds a count of records against a fixed number. It does not follow each parameter's, module's or router's own history, and it does not know that a rule started over at a new attempt (see "Enough history" above). The run state has no reason for a kind that is warming up: a run a few steps old reads `healthy`.
  - Evidence built from the server's report by `--watch` carries `kind_checks`: the report's 26 and the reader's seven, with a status expected. A report from a server older than the key gives evidence without it. The server's own `watchdog.json` run state does not read it either; it still degrades on `not_checked`, which gives the same state.
  - A resume in a run that recorded no learning rate reads `unavailable`, not `not_configured`, because `not_checked` has always listed it.

## GPU memory, NVML and data wait

Built Nov 16, 2026, tested with mocked CUDA and NVML; the GPU side waits for a Colab run.

- **Memory and NVML.** `tensorquill.init(model, system=True)` records, at each flush, the CUDA allocator's counters (`allocated`, `reserved`, `peak_allocated`, `alloc_retries`, `ooms`). With `pip install "tensorquill[nvml]"` it also records NVML's temperature, SM clock, power, ECC counts, throttle reasons and Xid events, read on a daemon thread of its own. The writer never waits for a reading: each flush attaches the newest finished one, so an NVML reading lands one flush later than it was asked for and carries `read_at`, and the first flush has none. Both go into `system` on the flush's last record. Reading them never waits for the GPU. A reading that cannot be taken is written once as unavailable and listed in `not_checked`. It is off by default until its GPU cost is measured.
- **Data wait.** `data_wait=True` records `data_wait` and `step_time` per step: the host time spent fetching batches, never the move to the device. It is on in the Hugging Face, Lightning and Accelerate adapters, at +0.5 µs per batch on CPU. For a loader that is not a PyTorch `DataLoader`, use `for batch in session.time_data(loader):` and move the batch to the device inside the loop. Two conditions decide whether a fetch counts, for the `DataLoader` timer and for `time_data` alike. **The thread:** only fetches made on the thread that created the session count, so call `time_data` from your training loop's own thread; a fetch made on a prefetch or worker thread is not `data_wait`. **Training, not evaluation:** a fetch counts while the phase is `train` and either gradients are enabled or the model is in training mode. A fetch inside `session.phase("eval")` does not count, and neither does one in an unmarked evaluation loop that runs under `torch.no_grad()` with the model in `eval()`; a fetch in a training loop that happens to be in eval mode with gradients on still counts. So a high `data_wait` is time the training loop itself waited for training batches. One limit: an unmarked evaluation's time is still in the next step's `step_time`, since nothing on the host marks it; wrap evaluation in `session.phase("eval")` to keep it out.
- **What is reported.**
  - `memory_growth`: allocated memory rose at six readings in a row, by at least 5% and 64 MiB.
  - `memory_pressure`: reserved memory at 95% or more of the device total.
  - `allocator_retries`: allocator retries or caught OOMs.
  - `hardware_errors`: uncorrectable ECC or Xid events, as evidence about the node.
  - `gpu_throttled`: thermal or power-brake throttling, an observation; the power cap alone is never reported.
  - `input_starvation`: over 20 steps, the median share of step time spent waiting for data is 0.3 or more, or has risen 0.2 above the first window's.
  - `memory_imbalance`, in `--rank all` only: one rank's peak allocated memory is 1.25× the median and 1 GiB above it.
- **Limits.**
  - Only the session's device is read, so a model spread over several GPUs in one process gets one device's memory.
  - Throttling between flushes is missed.
  - A hung NVML call never makes training wait and never fills the writer's queue, since the writer does not wait for readings. A reading still in the driver after 2 s (10 s for the first, which opens NVML) is found at a later flush, written once as unavailable, and NVML is off for the session.
  - Only PyTorch's `DataLoader` iterator and `time_data` are timed.

## Projects, run names and comparing runs

Built Nov 17, 2026, on CPU (macOS). A run has a project and a name, as in W&B, and two or more runs can be compared on what only TensorQuill records: what was checked and the incidents. Charts of scalars across runs stay with W&B and MLflow.

```python
session = tensorquill.init(model, project="granite", name="baseline", config={"lr": 1e-5})
```

- **The run ID is still the identity.** Every file and every folder in a server's store is named by it, and nothing moves under a project folder. The name is a label and may repeat.
- **Where the labels come from.** `project`: the argument, then `TENSORQUILL_PROJECT`, then W&B's project or `MLFLOW_EXPERIMENT_NAME`, then `uncategorized`. `name`: the argument, then `TENSORQUILL_RUN_NAME`, then the tracker's run name, then the run ID. W&B's rule for a project name applies (at most 128 characters, none of `/ \ # ? % :`): a bad argument raises at `init`, and a bad name from the environment or the tracker is made to fit with a warning. MLflow's experiment is not looked up by its ID, because that is a call to the tracking server during `init`, which could stall or fail a training start. If your experiment is set another way (`mlflow.set_experiment`, or an ID), pass `project=` or set `TENSORQUILL_PROJECT`.
- **The run manifest.** Rank 0 writes `<run_id>.run.json` beside its `.jsonl` file at `init`: project, name, group, tags, start time, world size, the SDK and PyTorch versions, where the run ID came from, and `config`. With `endpoint=` it rides on the first batch of each of rank 0's streams, and the server writes `runs/<run_id>/run.json`. A manifest that cannot be written is warned about and the run goes on. A manifest over 60,000 bytes goes to the server without its `config` (marked `config_left_out`, with a warning at `init`), and the server stores none over 64 KiB. An older server ignores the key, and an older sender still works with a new server.
- **Every evidence file has a `run` block** with the project, the name and the run ID. A run recorded before the manifest existed reads as `uncategorized` with its run ID as its name.

```sh
python -m tensorquill runs tensorquill-out --project granite
python -m tensorquill compare baseline after-the-fix --source tensorquill-out
```

- **`runs <folder or store>`** lists one row a run, by project: name, run ID, run state, how many ranks, last step, incidents by class, the first incident, how many kinds were checked, and the start time. It reads the manifests and the small evidence or report files only. It opens no Parquet part and runs no detector, so a local run whose evidence file was never written is listed with `?` and a note. For a run of several ranks the row is the whole run's, by the all-ranks rules: every rank's report (a store) or evidence file (local files) is read, `ranks_with_incidents` names the ranks that show one, and a kind counts as checked only when every judged rank checked it. A rank without a current report or evidence file makes the run state `unknown`, never clean. How many ranks a local run has is read from the file names, the first and last record of each file, and the manifest's `world_size`; no file is read whole. A `<run_id>.rank<N>.jsonl` file holds rank N alone when no line read names another rank (a file over 1 MB is scanned for the ranks its lines name, not parsed), and is then counted without a manifest; one that holds other ranks too is a file of several ranks, each named, and its count is settled. The count stays not known only where the scan stopped short of the file's end. When every file holds its rank alone and the manifest's `world_size` is above the files, the ranks with no file are counted and unknown, never clean, as a store's are: a run of several ranks captured on rank 0 only reads `unknown`, or `unhealthy` with an incident, never `healthy`. When those cannot settle it (a file of its own name or one whose ends name another rank, and a world size that is not the ranks seen, or no manifest), `rank_count` is null, the table prints the ranks seen with `+`, and `rank_count_not_known` says why. The evidence file beside a file that may hold several ranks (its first and last records name two, or, for a lone file, the manifest's `world_size` is above 1) is one rank's. Where the evidence names the rank it judged (`rank`, with `ranks_in_source`), the row of a lone such file says which; evidence that does not say, and any such file in a run of several files, is given to no rank: its incidents are listed with no rank, its ranks are unknown (the row is `ranks_unknown`), the run state is what the run-state classifier gives (an observation alone does not make it unhealthy), and what was checked is not counted for them. The last step of such a file is its furthest rank's, each rank's read from its last line in the file's last megabyte. `compare` reads every rank of such a file. A run with only the compact evidence file (`--compact`) is read from it. A run kept both as local files and in a store under one folder is one row (`also_in_store`). A rank written to more than one local file is read from all of them (`more_files`). A store run with no judged rank shows `?` for its incidents, not none. `tensorquill.list_runs(source, project=None)` gives the rows.
- **`compare A B [C ...]`** takes each run by ID or name at `--source` (default `tensorquill-out`), or as a path. An exact ID wins, and a name that fits several runs is refused with their IDs. It prints a summary and writes `compare.json`, in four parts:
  1. What differs in the setup: project, group, world size, versions and each `config` key.
  2. What was checked: a kind checked in one run and not configured, unavailable or not yet with enough history in another. This comes before the incidents.
  3. The incidents, by kind and what they name, with each run's first step. For a run that does not show one, the entry says whether that run looked (`absent_from`). The run's own incidents (`job_stalled`, `rank_silent`, `duplicate_batches`, `memory_imbalance`, `collective_hang`, `collective_desync`, `traincheck_violation`) are matched by what stays the same whenever the run is read, since Nov 18, 2026: a stall by how it stopped (a hang, suspected or confirmed, or a lost connection), a stuck collective by the collective and its process group, a TrainCheck violation by the invariants, and the other two by the kind; their times, seconds, severity, steps, byte counts and sequence numbers are left out, and the ranks each run names are in its `where`.
  4. Where two runs part, for two paired runs (the same job run twice, or a run before and after one change): the first step, and the layer or parameter, where a series leaves the runs' own early agreement and stays out. Runs that never agree early (another seed, another model) get "no answer" with the reason, never a step. It reads both runs' step records, so it is not answered for a run given as an evidence file, for three or more runs, or through the MCP tool for a run in a server's store. A `.jsonl` file still being written is read on its whole lines, as parts 2 and 3 read it, and the answer says a line was left out (`unfinished_lines_left_out`).
- **`first_divergence(records_a, records_b, rank=...)` called directly** takes rows as `load_records` returns them or raw (`all_attempts=True`), since Nov 21, 2026: each run's attempts of that rank are resolved first, so rows a resumed job rolled back are not compared, and `runs.a` / `runs.b` say how many were left out (`replaced_records`, present only when some were). Before, raw rows could name a step the replacement attempt never reached. Attempts are resolved only where their step ranges overlap or touch, so that rows `compare` has already resolved are read as they are; raw rows whose first attempt sits wholly above a later one, with no step in common, are left as given.
- **Every rank of each run is read** (Nov 17, 2026; before, rank 0 only). A run of several ranks is compared as a whole, by the rules of the all-ranks view (`--rank all`): its incidents are every judged rank's, grouped across ranks, and an entry's `ranks` names the ranks that show it, so an incident on rank 3 alone is not missed. In part 2 a kind is `checked` for the run only when every judged rank checked it with enough history; `history_not_stated` means some rank does not say, and `ranks` lists which ranks checked it when they differ. A rank that is not judged is named in `incidents.other_ranks_not_compared` and `read_from.unknown_ranks`, with why in `read_from.unknown_why`. One such state is `earlier_attempt`: the server's status shows the rank at another attempt than its report judged, or started again with nothing stored yet. A status entry written before the rank's first batch names no attempt and is not read that way. A local run's ranks are the ranks its records hold, its files are named for and its manifest's `world_size` counts, so a rank that no file holds a record of is not judged; for a run given as one rank's file, the other ranks are said to be not read. `--rank N` reads that one rank of every run, as before. A run of one rank gives the same output as before, with `rank_count` added.
- **Where it is read.** Local files are judged here by the Python detectors with the default thresholds, each rank on its own, and put together by the all-ranks rules (`evidence.combine_rank_evidence`). With no server, cross-rank batch duplicates are not looked for (`not_configured`); memory imbalance is compared across the ranks' memory readings. A run in a store is read through the all-ranks view from each rank's report and the status, and no part is opened. A rank whose report is not current is judged here from its parts by the command line, with the thresholds its last report applied, and the output says which ranks (`read_from.judged_here`); when its parts cannot be read (no `pyarrow`, a torn part) it stays unknown with the reason, also when it is the one rank read (a run of one rank, or `--rank N`): the comparison is still made, with that run's state `unknown` and the rank in `read_from.unknown_why` and `incidents.other_ranks_not_compared`. The MCP tool reads no part: such a rank stays unknown, and a run with no current report on any rank is refused with the reasons.
- **Part 4 with several ranks** compares rank r of one run with rank r of the other, for every rank, with the same rule as for one rank, and gives the earliest divergence with its `rank` (the lowest rank on a tie) and each rank's answer in `by_rank`. `no_divergence` needs every rank to say so; otherwise a rank with no answer makes it `no_answer`, naming the ranks. Runs with different ranks are not compared (`ranks_differ`): with another world size a rank reads another share of the data. Nothing is computed across ranks. A rank whose step records cannot be read is named in `ranks_not_read` and the other ranks are still compared. After a resume a run's `last_step` is the resolved run's, not the highest step of any attempt.
- **`runs` and `compare` are verbs wherever they come first.** A file or folder with one of those names is read as `./runs` or `./compare`. This changes what `python -m tensorquill runs` meant for a folder named `runs`.
- **Checked** in `tests/test_run_manifest.py` (30 tests) and `tests/test_runs_compare.py` (30 tests): two runs of one project told apart from local files and from a real server's store; a two-process run writes one manifest; a healthy run and each seeded run of `examples/seeded_failures.py --toy` compare as one incident in the second only, on the seeded parameter; a router-only run against a full-capture run reports what was checked before any incident; an incident on rank 1 or rank 2 alone appears in `compare` and `runs`, from local files, from a store written by hand and from two ranks streamed to a real server, which agree; a rank whose report is not current is judged from its parts, or named as unknown with why when `pyarrow` is missing, for one rank read alone too, and a command line with `pyarrow` not installed compares such a run; a `.jsonl` file of several ranks is listed with its ranks and never counted as one.
- **Not checked:** a GPU, Linux, a real W&B or MLflow run (the trackers are stand-ins in the tests), S3 or GCS, a real job of more than two ranks through `compare` (three ranks only in a store written by hand), the time and memory of part 4 on a run of many ranks, and a store of more than a few hundred runs.

## Scalars mirrored from W&B and MLflow

Built Nov 24, 2026, on CPU (macOS), against stand-ins of `wandb` and `mlflow` shaped from their sources, and run against the real wandb 0.31.2 (offline and disabled) and mlflow 3.18.0 (a SQLite store) in a separate environment. A script that logs its loss to W&B or MLflow and never calls `session.log` still gets that loss, and its `eval/*` numbers, on TensorQuill's records, beside the incidents and in `compare`. W&B and MLflow stay the place for charts, sweeps and reports: this is a copy of the plain numbers, made in the process, for context.

```python
import wandb                                   # imported before tensorquill.init
session = tensorquill.init(model)              # mirror_scalars=True by default
run = wandb.init(project="granite")            # before or after tensorquill.init
...
wandb.log({"train/loss": loss.item(), "lr": lr})   # also session.log({...}) on the step in progress
```

- **What is wrapped.** `wandb.Run.log` on the class and the module's `wandb.log`, and `mlflow.log_metric` and `mlflow.log_metrics` (on `mlflow` and on `mlflow.tracking.fluent`, which defines them). The W&B wrapper on the class covers a run made after `init` (W&B's `wandb.init()` points `wandb.log` at the new run's `log`), the one on `wandb.log` a run made before it, and a `wandb.finish()` followed by a new `wandb.init()` is covered again. So is a run made with `wandb.init(mode="disabled")` (W&B's `NoopRun`, a subclass of `Run` with a `log` of its own, wrapped too). The Hugging Face `WandbCallback` and `MLflowCallback`, Lightning's `WandbLogger` and Accelerate's W&B and MLflow trackers all log through these names. One call records once, also when `wandb.log` goes through `Run.log` or another wrapper sits between.
- **What is taken.** Python `int` and `float` (not `bool`), NumPy integer and floating scalars, and 0-D tensors already on the CPU, of a real dtype. A tensor on a GPU or on Apple MPS is skipped without being read: no `.item()`, no copy, no sync. Images, tables, histograms, strings, lists, nested dictionaries and `None` are ignored, as are keys that are not non-empty strings. A NaN or an infinity is taken as it is.
- **Which step.** A mirrored value is recorded on the step `session.log()` would give it, through `session.log()` itself. W&B's `step` and `commit` and MLflow's `step` are ignored, and `wandb.run.step` is never read (it waits on W&B's service and raises in shared mode). Several calls in one step add up there (`wandb.log(..., commit=False)` included), and a key logged twice in a step keeps its last value. Inside `session.phase("eval")` that is the newest step still in memory (see `scalars` above), and one with no step in memory is left out, as `session.log` leaves it out; the tracker still gets it.
- **Explicit wins.** A key that the step already holds from `session.log` (your call, or the Lightning, Hugging Face or Accelerate callback's) is not replaced by a mirrored value, whichever came first. On the newest step under `"eval"` too: a key that step held when it ended (its own loss, for example) and one you `session.log` there after it are not replaced by a mirrored value. So the Hugging Face `Trainer`'s averaged `train/loss`, which a W&B logger logs while the callback has set `"eval"` for an evaluation on the same step, does not replace the step's own loss. One limit: if the mirror stored a key first and you then `session.log` the very same small integer object for it (Python shares the objects for -5 to 256), a later mirrored value of that key in the same step can still replace it.
- **The tracker is untouched.** Its call is made with your arguments, returns its own value, and its own error reaches you unchanged; a call it refused records nothing. The mirror reads no API key, makes no network call and calls no tracker server. Nothing it does raises into training or into the tracker's call, also under `python -W error`: a name it cannot wrap is left as it is, and a value it cannot read is not mirrored.
- **Order to respect.** Only a tracker already imported when `tensorquill.init` runs is wrapped, and TensorQuill never imports one: `import wandb` (or `import mlflow`) before `tensorquill.init`. `wandb.init()` itself may come before or after. A function bound to a name of your own before `init` (`from mlflow import log_metric`, `log = wandb.log` taken before `init`) and calls made through `MlflowClient` (Lightning's `MLFlowLogger` logs its metrics with `MlflowClient.log_batch`) are not seen: log those with `session.log` yourself.
- **Several sessions.** The wrappers are shared by every open session that mirrors, and each of them gets the value on its own step. They come off when the last such session closes or stops (`close()`, or a capture that stopped on a sink error), and when an `init` fails part-way. A wrapper someone installed on top of ours after `init` is left in place, with ours under it passing every call through. `mirror_scalars=False` installs nothing.
- **Checked** in `tests/test_lane_ak1_mirror.py` (40 tests), against stand-ins: both orders of `wandb.init()` and `tensorquill.init`, a finished run and a new one, a disabled run, MLflow's two names, every accepted and refused kind of value, an MPS tensor left unread, accumulation and explicit precedence, the tracker's arguments, return value and own exception, broken tracker internals under `python -W error`, no tracker imported, overlapping sessions, removal on `close()`, on a stop and on a failed `init` with a later user wrapper kept, and a run with no tracker writing the same bytes with the mirror on or off. `tests/test_lane_ak1_real_trackers.py` (6 tests) runs both orders, a disabled run, a finished run and a new one, and MLflow's two names against the real packages where they are installed, and skips where they are not (the project's `.venv` and CI).
- **Not checked:** a GPU, `torch.compile` with a tracker call inside a compiled function, and a tracker called from several threads at once.

## For a coding agent: a read-only MCP server

Built Nov 16, 2026. `python -m tensorquill.mcp_server PATH` serves one run's evidence to a coding agent over MCP (stdio). Installed, it is also the `tensorquill-mcp` command, so an agent's MCP configuration can start it with no install step once the package is on PyPI: `uvx --from tensorquill tensorquill-mcp PATH` (not run yet: nothing is published). `PATH` is an `evidence.json`, a `.jsonl` capture, or a run folder in a server's store (`runs/<run_id>`). It needs no package beyond the SDK: the part of the protocol it uses (revision 2025-06-18) is written out in `mcp_server.py`.

It has six tools, and all six only read. Four answer about the run at `PATH`; `list_runs` and `compare_runs` (Nov 17, 2026) read the folder that run is kept in, or the one named with `--runs FOLDER`, and take run IDs and names found there, never a path:

| Tool | Gives |
| --- | --- |
| `list_incidents` | The incidents with their kind, class, first step and what they name, plus the run state and what was not checked |
| `get_incident` | One incident in full |
| `get_series` | One layer's, parameter's, router's or logged scalar's values over a step range |
| `get_all_ranks_status` | For a run folder: which ranks are judged, unknown, clean or showing incidents |
| `list_runs` | The runs kept beside this one, by project: name, run ID, run state, rank count, last step, incidents by class, first incident |
| `compare_runs` | Two or more of those runs by ID or name, every rank of each: what differs in the setup, in what was checked, and in the incidents |

- **It follows a live run.** The path is read again at every call.
- **Answers are bounded.** No reply is longer than 50 KB. A long series is thinned to 200 points with the stride reported, and the minimum, maximum and median are still taken over every recorded step.
- **For a run folder it runs no detector.** The incidents come from the server's own reports, and only `get_series` opens the Parquet parts, which needs `pyarrow`. `compare_runs` keeps to this: a rank whose report is not current is unknown, and a run with no current report on any rank is refused with the reason. On local files it runs the Python detectors, as `list_incidents` does on a capture; it never starts the server binary, whatever is installed.
- **The page to give the agent** is [AGENT_INSTRUCTIONS.md](AGENT_INSTRUCTIONS.md): which tool to call first, how to name the step, the layer or parameter and the kind, what the three classes and "not checked" mean, and that it explains and takes no action on the run.
- **Checked** in `tests/test_mcp_server.py` (36 tests): a scripted client using only the first four tools recovers the kind, the first step and the layer, parameter or module of all seven Gate 1 fixtures; the size cap on a 10,000-step run; a two-rank run folder, by hand and through the real server; every error case.
- **Not checked:** no live agent has used it.

## A score, four measurements and two changed rules

Built Nov 21, 2026 (wave AD), from one page, `DETECTOR_RULES_CONTRACT.md`, and 56 shared cases in [`tests/fixtures/rules/cases.json`](tests/fixtures/rules/cases.json). The Python detectors and the server were each built from the cases alone, and [`tests/test_wave_ad_trial.py`](tests/test_wave_ad_trial.py) holds both to the same evidence through `build_evidence` on the 43 cases that give records.

- **A score beside a ratio.** Wherever an incident records a `ratio` taken against a window of earlier values, it also records a `score`: `(value - median) / (1.4826 × MAD)` over the same earlier values.
  - **How it is read.** The ratio shows the value relative to its baseline. The score shows its distance from the earlier median in units of 1.4826 × MAD.
  - **When there is none.** With fewer than 10 earlier finite values the score is `null` and `score_note` is `short_history`. With a zero MAD nothing is divided: the score is `null` and `score_note` is `no_dispersion`. The summary and the MCP tools say "score 31.2", "no score: fewer than 10 earlier values" or "no score: the earlier values had zero median absolute deviation", and never show a missing score as 0.
  - **Where.** On `grad_spike` (the incident and each of its `parameters`), and on each of the `modules` of `activation_spike`, `activation_drift`, `attention_collapse` and `attention_logit_growth`. The attention kinds have at most 5 earlier probes, so theirs is always `short_history`.
  - **It is a description.** No rule reads it and it changes no incident. On the development captures it separates activation faults from healthy runs by a wide margin, and does not separate the total gradient norm (a healthy Granite step scores 76, two seeded faults 31 and 54).
- **`activation_drift` compares a module with its recent past.** The median of its last 10 records against the median of the 50 records before those, for `std` and for `abs_max / std`, at 3 times up or down, from the module's 110th record on. So the kind needs 110 records where it needed 60.
  - **Why.** Against a module's first 50 records the ratio has no ceiling on a model trained from scratch: the earlier rule fired on 18 of 28 healthy development record sets. This one fires on none of them (largest ratio 1.68), and on the three recorded GPU faults at step 254 as before.
  - **How far that goes.** The rule was fitted to those runs. One fresh run it was not chosen from (nanoMoE in another shape, 900 steps, 4 modules judged on 792 records each) stayed quiet at 1.44 where the earlier rule fired at step 114. That is one seed of a familiar model family.
  - **What it gives up.** A slow drift never fires, however far it goes. A shift inside a module's first records is not seen by this kind (`activation_spike` judges from the 11th record). After a shift `affected_steps` is about 30, since the new level becomes the baseline.
- **`moe_imbalance` on a router that starts unbalanced.** A router flagged from its first sample at step 0 is in the state it started in. That leading run is not reported while it is shorter than 10 samples.
  - **Two steps, kept apart.** Once it reaches 10 samples the incident carries `step` (the first flagged sample), `reportable_step` (the tenth) and `since_start: true`, and a reader says "collapsed since step 0, reportable at step 9". Among several routers the incident is the one that could be reported first. A flagged sample after the leading run has ended, or on a router whose first sample is not at step 0, is reported as before.
  - **A short capture is not clean.** When the records end with a router still in that leading run, the `moe_imbalance` entry of `kind_checks` carries `starting_state` (each router with its sample count) and `enough_history` is false.
  - **Measured.** nanoMoE with its balance loss, flagged at steps 0 and 1 before (one expert at 36.2% against 35% at random initialisation), now raises nothing. Without the balance loss it is reported at step 7. Every seeded collapse on the development runs is reported at the step and router it was before.
  - **What it gives up.** A router collapsed from its first step is reported 10 samples later.
- **`update_spike` carries the learning rate:** `lr` at the flagged step and `lr_before` at the step it was compared with, each only when that record has `lr`. The rule does not read them.
- **`parameters_not_judged`** on the `stalled_weights` entry of `kind_checks` names the parameters whose gradient was not read, from both engines. The all-ranks view carries the union, and `parameters_not_judged_by_rank` when the ranks' lists differ.
- **Four measurements, with no incident and no threshold.** Each is a block in one rank's evidence, present when the records hold what it reads. No rule reads them and they change no run state.

  | Block | What it reads | What it records |
  | --- | --- | --- |
  | `gradient_trend` | The total gradient norm (the pre-clipping norm when the run clips), skipped steps left out | `points`, `first_step`, `last_step`, `first`, `last`, `growth` (last over first), `per_100_steps` |
  | `attention_trends` | Each attention module's largest logit, probe by probe | `statistic`, `modules`, and `listed`: the ten with the largest `growth` |
  | `update_trends` | Each parameter's `update_rms` against the median of its own 50 records before | `parameters`, `judged`, and `lowest`: the ten whose update fell furthest |
  | `weight_jumps` | Each tensor's norm at two consecutive weight checks | `checks`, `parameters`, and `largest`: the ten largest changes |

  - **The trend** is a line through the median of the first third of a series and the median of its last third, at the actual step numbers. A series under six points has none.
  - **What they do not do.** A gradient norm that climbs in three steps and then stays (the re-created missing `zero_grad()` of the TrainCheck page) has a flat trend and is still missed. A healthy run can rise more than a buggy one. `attention_trends` has only hand-written coverage: no recorded capture has the six probes it needs.
  - **In the compact file** both `gradient_trend` and `weight_jumps` are kept. On `tests/test_compact.py`'s fixture the file went from 8,221 to 10,178 bytes (`weight_jumps` 1,746, `gradient_trend` 210), under a ceiling of 12,000; neither block holds a per-step series.
  - **In a live server** the two trends are exact, the same values and the same absences as offline. Measured on one rank with release builds (16 parameters, 12 attention modules, a probe every 100 steps): the two series hold 288,054 bytes at 10,000 steps and 2,295,094 at 100,000; a report takes 0.63 ms at 100,000 steps against 0.05 ms without them; the next acknowledgement on that rank is about 0.6 ms later at 100,000 steps and no later at 10,000. Not measured: more than one rank, or a million steps.
- **Three things a capture now says.**
  - **`layers_not_read`**, once, on a record: the modules the capture cannot read at all, each with why. In evidence it is a `not_checked` entry with `check: "layers"` and a `coverage`. With `partial` the activation kinds stay `checked` and name the others under `modules_not_judged`. With `none` those kinds are `unavailable`: nothing was looked at, so nothing reads as clean. A limit of this version: a module read on some records and not on others is not named, and is judged on the records that hold it.
  - **`moe_source`**, once, for each router: `form` (`scores`, `indices` or `map`: how the routing reached the capture) and `point` (`requested`, `dispatched` or `unknown`: where in the model it was taken). Indices and maps can be made before or after a capacity limit, so the form never says which. A reader says "dispatched assignments" only when `point` is `dispatched`. It reaches a reader from records and from a server's report alike.
  - **The step capture stopped at.** A heartbeat that carries `capture_stopped` also carries `capture_stopped_step`, the last step the session committed, or null when it committed none. The server's status shows it as `step` inside the rank's `capture_stopped`. Step 0, null and no key (an older sender) stay three different things.
- **Steps newer than the last judgment.** Evidence whose judgment does not reach the newest step carries `freshness`: `{"current": false, "judged_to_step", "records_to_step", "why"}`, with `why` one of `records_newer`, `nothing_judged` or `thresholds_changed`. `python -m tensorquill runs` prints "as of step J; records reach step R", and the watchers show the last current result with its step. Evidence that is current has no such key and is as it was.
- **What the MCP tools pass on.** `skipped_updates` and `checkpoint_tensors` (and their `_by_rank` forms for a run folder), `parameters_not_judged`, the replica `coverage`, the no-peer note, each score with its words under `scores`, `since_start` and `reportable_step` with "collapsed since step 0, reportable at step 9", the measurement that bears on an incident (described as numbers with no threshold, not findings), `moe_source` with its words, and `capture_stopped`. Each is there only when the evidence has it.
- **A watcher that keeps what it has judged.** With the Python detectors, a watcher of a `.jsonl` file or of a store's parts now judges only what is new at each look, and gives what a judgment of the whole run gives. That is `--watch --detectors python` on the command line, and the default of `watch()` in Python. The command line's `--watch` judges with the Rust detectors unless it is told so; since Nov 21, 2026 those, too, judge only what was appended when a look is an append ("Watching through Rust").
  - **Measured** as one warm update on the repository's benchmark stream (`examples/benchmark_detectors.py`: 24 routers of 32 experts at top-8, 219 parameters, 10,000 steps, 45 MB, rank 0), on an M1 Pro: a median 16.52 s before and 0.48 s after. The cold first look went from 19.0 to 19.4 s down to 14.5 to 14.8 s. The process's peak memory was 1.87 to 2.00 GB before and 1.37 to 2.12 GB after (4 of 5 runs at 2.10 to 2.12). The watcher still reads every record at every look, so an update still grows with the run, slowly.
  - **A file that changed under it is read again from the start:** one that is shorter than what was read, is another file, or whose first or last 4 KiB read changed, or whose modification time (`st_mtime_ns`) changed while it did not grow since the last read (wave AF; with either engine); for a store, a part that changed or is gone. An append is still read as an append. **Not detected:** a rewrite in place that keeps the same file, at least the same length, both of those 4 KiB stretches and the modification time, or that also grows the file. A `touch` with no change of content reads the file again from the start and writes the same evidence. A file cut to empty still writes nothing.
  - **Checked at every look, not only at the end.** [`tests/test_lane_ad11_costs.py`](tests/test_lane_ad11_costs.py) and `tests/test_wave_ad_trial.py` hold each look to a fresh judgment after a step is appended, a new attempt begins, late rows of an old attempt arrive, an attempt replaces judged steps, and under another threshold; the second file does so with the Rust detectors, and for a long-lived `--rank all` watcher against one that has seen nothing.
  - The Rerun export of evidence went from about 106 s to 5.3 s at 4,000 steps, and takes 13.5 s at 10,000.
- **A batch the server refuses for good** (a key column missing or of another type) is counted once, and the sender does not send it again without end.
  - **How.** Before the `INVALID_ARGUMENT` status the server confirms on the acknowledgement channel the byte range it refused and the column. The sender moves its saved offset for two reasons only: the server stored the bytes, or it named exactly the range the sender sent as refused. Anything else moves nothing. `sender.refused_batches` and `sender.last_refused` say what was refused, and the local file keeps those steps.
  - **Checked** with the real server and the production sender together, starting from a saved offset: the returning sender's question for the store is answered whatever its columns, the refused bytes are crossed and no more, and the batch behind them is stored (`tests/test_wave_ad_trial.py`).
  - **Across a restart of the server itself** the sender was held at the refused bytes in this wave: the restarted server had forgotten the rank's last acknowledged offset and named a range from byte 0. Fixed in the next wave ("A refused batch across a restart of the server", below).
- **Rows that arrive late inside one part are not stored.** The server keeps a row only when its step is above the last step it kept for the attempt, the rule that drops a replayed row. Of 60 distinct steps sent in one part with every fifth three places late, 48 are stored; the live report, the offline Rust detectors and Python agree on those 48. In this wave no count of the 12 reached a reader; the next wave counts them ("Rows that were not newer", below). The SDK's own sender writes steps in order.

## Clipped groups, a resume, two optimizers, late rows and a restarted server

Built Nov 21, 2026 (wave AE), from one page, `WAVE_AE_CONTRACT.md`, and 36 shared cases in [`tests/fixtures/wave_ae/cases.json`](tests/fixtures/wave_ae/cases.json). The Python detectors and the server were each built from the cases alone, and [`tests/test_wave_ae_seams.py`](tests/test_wave_ae_seams.py) holds both to each case's answer and to the same evidence through `build_evidence`. Every new key appears only when its condition holds: a run without the condition gives the records, evidence and status it gave before.

- **Two `clip_grad_norm_` calls in one step (`clip_calls`).** A record carries `clip_calls`, a whole number above 1, when more than one `clip_grad_norm_` call covering the session's parameters ran in the step. `clip_grad_norm` stays the root of the summed squares of what each call returned.
  - **An absent key does not mean one call.** Under `torch.compile` the session knows that clipping happened and not how many times, and a capture written before the key never says. Absent means one call, or a count that is not known.
  - **What the detectors do.** `update_spike` splits the pre-clipping total by parameter only for a pair of records that name different parameters, and that split assumes one call. When either record of such a pair has `clip_calls`, the pair is not compared: nothing is flagged and its change joins no baseline. Every other pair is compared as before.
  - **What the evidence says.** `not_checked` gains one entry, `{"check": "clip_groups", "kinds": ["update_spike"], "comparisons", "compared", "step", "reason"}`: the pairs not compared, the pairs compared, and the step of the first pair left out. The run reads `degraded`, as with any `not_checked` entry. While `compared` is above zero `update_spike` stays `checked`; at zero it reads `unavailable`, and the reason says none of the comparisons was made.
  - **Not built:** an exact split from each call's own norm and parameters.
- **A stalled parameter and a resume.** A process's first weight check compares nothing, so a `stalled_weights` streak used to run through a resume on comparisons that were never made. Now, when a record's attempt differs from that of the record before it, every parameter's streak starts again at zero. A stall raised before the resume stands with its step.
  - **What it gives up.** A parameter stalled right through a resume is reported up to three checks later, 150 steps at the default interval.
- **An optimizer that steps before the one that ends the step (`ends_step=`).** `tensorquill.init(..., ends_step=optimizer)` names the optimizer whose step closes each iteration. Opt-in; without it everything is as before, including the stated limit that an optimizer placed before the lead in the loop has its update written one step early.
  - **With it** a step ends when that optimizer's step returns, and only then. Every other optimizer's step since the last ended step is written on the record of the step that ends next. An iteration in which another optimizer does not step writes nothing of that optimizer.
  - **Refused at `init`, with `ValueError`, never inside a step:** an `ends_step` that is not an optimizer holding at least one of the model's parameters; `ends_step` with `scaler=` (there `scaler.update()` ends the step); `ends_step` with `auto_step=False` (there `session.step()` ends it).
  - **When the named optimizer never steps.** After ten steps of other optimizers on the model's parameters one warning says so, once, and nothing is recorded until it steps. The warning cannot raise into the training loop under `python -W error`.
  - **Adapters.** The Lightning, Hugging Face and Accelerate adapters do not pass `ends_step`.
- **Several optimizers through one scaler (`step_skipped_part`).** When the scaler skipped at least one optimizer and applied at least one in the same step, the record keeps `step_skipped: true` and `step_skipped_by`, and gains `step_skipped_part: {"skipped": n, "of": m}` with 0 < n < m. It is read from the scaler's own verdicts at the flush, with no sync added. Every optimizer skipped, none skipped, or one optimizer: no key.
  - **`loss_scale_trouble`.** Such a step counts once in `recorded_steps`, once in `partial_steps`, not in `skipped_steps`, and ends the streak of fully skipped updates, because an update occurred. Before, it counted toward the ten consecutive skips. An incident carries `partial_steps` only when it is above zero.
  - **The kinds judged parameter by parameter** (`grad_spike`, `update_spike`, `stalled_weights`) read a partial step as a skipped one: the record does not say which optimizer's update was applied. That can miss evidence from the optimizer that stepped, and never invents any.
  - **`skipped_updates`** counts such steps under `partial`, a key present only above zero. In words a reader says "N step(s) on which the scaler skipped some optimizers and applied others".
- **A records file that holds several run IDs** is refused input by input, and the reader says so.
  - **`first_divergence(a, b)`** still compares a clean run with a different clean run. If either input's rows of the rank hold more than one run ID, the answer is `no_answer`, the `reason` names the side and the IDs, and `several_run_ids` maps the side (`"a"`, `"b"`) to its run IDs. Every row is checked, not the first and last.
  - **`runs` and the MCP `list_runs`** give such a file one row with `evidence.state: "several_run_ids"` and the IDs, with no run state and no incident claimed, whatever evidence file lies beside it.
  - **`compare`:** when a named run is not found and a file in the folder holds that ID among several, the error names the file and the IDs it holds.
- **Rows that were not newer (`rows_not_newer`, `late_steps_confirmed`).** For a row at or below the highest stored step the server cannot tell a step that arrived late from a row sent again, so it reports two counts on the rank's entry in `watchdog.json`, each only when above zero. The ordering rule of the store is unchanged, and no late row becomes stored.
  - **`rows_not_newer`:** every row received and not stored because its step was not above the highest step kept for its attempt. A row sent again is counted again, so it is not a number of steps lost.
  - **`late_steps_confirmed`:** distinct steps that were above the watermark when their part began, were not kept, and arrived inside that part, each counted once. It is a lower bound: a late step that crosses a part boundary is not in it, so the same rows can give another number when the parts are cut elsewhere.
  - **Where it is shown.** One rank's evidence (`watchdog.rows_not_newer`, with `rows`, `late_steps_confirmed`, `includes_replays` and a `note`), the all-ranks view, `runs`, `compare` and the MCP tools, wherever dropped rows are said. When every discarded row is a confirmed late step, the sentence about the other rows is left out.
  - **Checked against the real server:** the 60-row part above gives 12 and 12; a stored part sent again adds nothing to `late_steps_confirmed`; a discarded step sent again adds to `rows_not_newer` only.
- **A refused batch across a restart of the server.** Every batch of rows the sender sends now says where it starts (`start_byte_offset` in the batch's metadata). The server confirms the exact range it refused, and the sender advances only when that range matches its own.
  - **When the claim is used.** Only when the stream had accepted nothing, the server had acknowledged nothing for the rank, and the claimed start is not negative and is below the end. Otherwise the range is named from what the server holds, as before.
  - **What a refusal means.** It confirms the range rejected. It does not acknowledge those bytes as stored: `end_byte_offset` at the top of the confirmation is still what the server holds.
  - **Checked** with the production sender and the real server stopped and started again, by SIGTERM and by SIGKILL: the sender crosses the refused bytes and no more, and the batch behind them is stored (`tests/test_wave_ad_trial.py`, no longer an expected failure).
- **How a stream ended, in the server's log.** The line the server writes for each ended `DoPut` stream says `the response was open` or `closed`. That is the state the server saw as it wrote the line. A call whose deadline passed is written either way, since the transport closes the response on its own task: of 200 such calls under load, 120 read open and 80 closed. A clean half-close read open every time.
- **Tests find the server binary.** `tests/conftest.py` sets `TENSORQUILL_SERVER_BIN` to a binary built under `server/target` when the variable is not set, so the tests that judge with the Rust detectors no longer fail on a tree that has a build and no variable.
- **Measured, with no rule changed.** `experiments/rule-selection/THRESHOLDS.md` reads the spike, diversity, starvation and stall thresholds on the development runs. It is a measurement: no threshold was moved.
- **Not run:** Linux, PyTorch 2.6, NCCL, a GPU, CI.

## Records that cannot be placed, every rank's keys, and routers with no tokens

Wave AF, Nov 21, 2026 (`WAVE_AF_CONTRACT.md`).

**A record's identity fields.** `schema_version`, `rank`, `attempt` and `step` say which rank, attempt and step an observation belongs to. One check (`tensorquill.identity.check`) decides whether they are valid, and every reader calls it where records are loaded, before either engine is chosen, so the two engines cannot disagree:

| Field | Absent | Valid when present |
|---|---|---|
| `schema_version` | read as 0, the legacy version | the integer 0 or 1 |
| `rank` | read as before (0, or the reader's default rank) | an integer of 0 or more |
| `attempt` | read as 0 | an integer of 0 or more |
| `step` | not valid | an integer of 0 or more |

A Boolean, a float (also a whole one, `1.0`), text and `null` are not integers. `run_id` is read as before.

**Offline, a record that is not valid refuses the whole input**, and nothing of it is judged: a missing observation never reads as a clean check.

- `build_evidence`, `watch`, `first_divergence` and `compare_runs`, with either engine, raise `tensorquill.identity.MalformedRecordError`, a `ValueError` with `field`, `value`, `where` and `reason`. Its text names the field, the value and the place: the file and its line from 1, a store's part and its row, or the record's place in a list. No evidence file is written, and one an earlier look of `--watch` wrote is left as it was.
- The command line, with `--watch`, `compare` and either engine, prints one line, `tensorquill: error: attempt is 1.0 at run.rank0.jsonl, line 4: tensorquill reads an integer of 0 or more`, and exits with status 2.
- The MCP tools that read records answer with a tool error holding that text, and answer the next call.
- `python -m tensorquill runs` and the MCP `list_runs` do not raise: such a file is listed as a run with no evidence.
- `tensorquill-server detect`, with or without `--run`, exits with status 1 and one line naming the row, the field and the value, for a negative `rank`, `attempt` or `step` and a `schema_version` other than 0 or 1.
- The capture writes a `step=` or `start_step=` below 0 as given; such a file is then refused, so give steps of 0 or more.

**The sender and live ingest.**

- The sender reading its own file does not send a line whose `rank`, `attempt` or `step` is not valid (negative, not an integer, or a missing `step`), nor one whose key the stream cannot hold. It skips the line, counts it in `sender.skipped_lines`, says the first such line once on stderr with its byte offset in the file, its step and the field, and sends the lines after it. The file keeps the line as written. Nothing raises into training.
- A line whose `schema_version` the server does not read is sent. The server drops that row and counts it under `unsupported_schema_version` (`dropped_row_keys` in the status), as it drops a row with a null key and counts it under that key.
- Live ingest refuses a batch holding a negative `attempt` or `step` whole, with `invalid_argument`, and stores and acknowledges nothing of it; the next valid batch is stored. A stream whose descriptor names a negative rank is refused. The SDK's own sender never sends such a batch.
- **The difference that stays.** Offline, a file with such a record is refused whole. Live, the server cannot refuse a run that is still arriving: it drops and counts a row with a null key or an unread `schema_version`, and refuses a batch with a negative `attempt` or `step`.

**Several refused batches in a row.** The server keeps, for each rank, the end of the last refusal it confirmed, and names the next refused batch from there when the batch claims to start at that end and nothing was acknowledged past it. A sender whose batches are refused several times in a row then moves past each, and the valid batch after them is stored. A refusal whose confirmation was lost moves nothing, and a start the server never named is not taken. The kept end is in memory only: after a restart the server takes the sender's claimed start by the restart rule of the section above, so each refusal still names the bytes it was sent for.

**The status after a refusal or a late row.** `watchdog.json` is written at the next watchdog pass when a rank's `refused_batch_keys`, `rows_not_newer` or `late_steps_confirmed` changes, as for its other counts, not at the next periodic write.

**Offline reports and live ones.** The offline reports of `tensorquill-server detect` (with `--samples`, and each rank's with `--run`) carry `attempt_order` (`first_seen`), as a live report does. For the same valid rows the two reports are equal but for `rebuilds`, which counts how often a live server built the rank's detectors from its store and is 0 offline. Two differences stay. Offline, steps out of order within an attempt are put in order and judged, since the whole file is in hand; live, a row whose step is not above one already kept for its attempt is counted under `rows_not_newer` and not judged again. And offline refuses a negative key or an unread version that live ingest drops or refuses, as above.

**Every rank's keys in the all-ranks view.** A key that says what was not observed, or how an observation was made, reaches every view of the check it qualifies, with its ranks:

- `moe_source_by_rank`, `gradient_trend_by_rank`, `attention_trends_by_rank`, `update_trends_by_rank` and `weight_jumps_by_rank`: one entry `{"rank": n, "<block>": ...}` for each judged rank whose evidence or current report has the block, unchanged and not added up. No key when no judged rank has it. In the all-ranks view from local files and from a store, in `--rank all`, and in the MCP tools.
- Each rank's `not_checked`: on the rank's entry of `ranks` in a store's view, and under `not_checked_by_rank` (`{"rank", "not_checked"}`) in a view read from local files. The `--rank all` summary has one line for each, `Not checked on rank N (<check>): <reason>`.
- In the run's `kind_checks`, an activation kind's `modules_not_judged` is the union of the ranks' lists, and the MoE imbalance kind's `starting_state` gives each router once with the fewest samples any rank gives it; `modules_not_judged_by_rank` and `starting_state_by_rank` name each rank's list where the ranks differ.
- `compare`'s divergence answer no longer lists `layers_not_read` and `moe_source` as series that were not compared: they say how a run's records were observed. Where the two runs differ in either, the answer has `provenance_differs` (`{key: {"a": ..., "b": ...}}`, null for a side whose records never said it), and the summary has one line naming it.

**A router recorded with no tokens on every step** was not read. Both engines, offline and live, then list a `not_checked` entry `{"check": "moe_routing", "kinds": ["moe_imbalance", "starved_experts"], "routers": [...], "reason": ...}`, the routers sorted by name. While no router was read the two MoE kinds are `unavailable`, and the run reads `degraded`; with some read they are judged on those, and the entry names the others. A router with tokens on some records and zero counts on others is judged as before. Live, the entry is judged on what has arrived: there while a named router has had only zeros, gone at its first tokens. The entry reaches the all-ranks views with its ranks, and the MCP tools.

**The live report's trends.** A live server finds `gradient_trend` and each module's attention trend again only when its series has a point it did not have at the last report; a series with no new point gives the trend found before. The report is the same as before. Its cost was not measured.

## Things to know

- **What can wait or raise in training.** Once `init` has returned, TensorQuill's own monitoring issues no collective, waits for no other rank and raises nothing into the training loop: the scheduled drift check is each rank's own observation, a failing sender keeps its error, and a failing local sink stops capture with a warning. The two replica checks you call yourself, `tensorquill.distributed.replica_spread(params, group)` and `session.record_replica_spread(group)`, are different: each is a collective. Every rank of the group must call it on the same step; it waits for the others as any collective does, so a rank that never calls leaves the rest waiting until the process group times out (by default 10 minutes on NCCL, where PyTorch then aborts the process, and 30 minutes on other backends); and a gather that fails once issued raises into the caller ("The two explicit calls are collectives", above). `session.close()` waits for the writer, up to 60 seconds if it is behind.
- **A `Trainer.train()` that raises (Nov 21, 2026).** The `Trainer` gives a callback no hook for an exception, so `on_train_end` never comes. The Hugging Face callback now closes its session when the process ends, when `callback.close()` is called, or at the next `train()`, and each of those writes the end marker as raised, naming the exception when its traceback passes through that `train()` and `TrainEndNotReached` when it cannot tell. Measured on CPU with a real `Trainer`: a script that ends with the raise, or with Ctrl-C, now has every step on disk and a marker; before, the newest step was lost and there was no marker.
  - In a process that goes on after the raise (a notebook, a caught `KeyboardInterrupt`) the session stays open until one of those three; call `callback.close()` in a `finally:`.
  - A `close()` made on purpose while `train()` is still running (from another callback, or from another thread) is written as a clean close, `closed` (lane AD6): the callback finds that `train()` still running on one of the process's threads. Where it cannot read that `train()`'s frame, the close is written as raised.
  - The close at exit waits for the writer as any `session.close()` does, up to 60 seconds if it is behind. Run on two CPU ranks under torchrun (lane AD6): every rank interrupted the same way writes every step and its marker. A rank that torchrun stops because another rank failed gets SIGTERM, so it loses its newest step and leaves no marker. Not run: a notebook.
- **SIGTERM.** TensorQuill installs no signal handler, and `tensorquill.init` registers no exit hook (the Hugging Face callback's exit hook, above, does not run under a default SIGTERM either, as no Python exit hook does). A process stopped by SIGTERM with the default handling runs no `close()`: the steps not yet written are lost (those since the last flush, up to `every`, and any still in the writer's queue) and the file reads `not_closed`; what was written is whole lines. A job that turns SIGTERM into an exception (`signal.signal(signal.SIGTERM, lambda *_: sys.exit(143))`) and trains inside `with session:`, or in a `try` whose `finally` calls `session.close()`, keeps every step and leaves a marker whose outcome is `raised`. Under torchrun the agent sends SIGKILL to a worker still alive 30 seconds after its SIGTERM (PyTorch 2.15's `LocalElasticAgent`), and a close can wait up to 60 seconds for a writer that is behind, so a close still waiting then is cut short. Run on CPU, one process, `every=10`: 25 steps and a SIGTERM wrote 20 lines and no marker with the default handling, and 25 lines and a `raised` marker with that handler.
- **Mixed precision.** Pass the run's scaler: `init(..., scaler=scaler)`. `torch.amp.GradScaler` skips `optimizer.step()` when gradients overflow, so the optimizer hooks alone would miss those steps; with `scaler=`, the step ends at `scaler.update()`, which runs every iteration, and each record gets `step_skipped` and `grad_scale` (the loss scale used), read as tensors before `update()` resets them, with no added sync. Gradient spikes and non-finite gradients are not reported on skipped steps, where the scaler expects them, and `loss_scale_trouble` reports 10 or more skips in a row or a loss scale below 1 (first guesses; a few skips in a row at the start, while the scaler halves its initial 65,536, are normal). Without `scaler=`, pass `auto_step=False` and call `session.step(lr=...)` once per iteration.
- **A framework that steps where the hooks cannot see (Nov 20, 2026).** With `auto_step=False`, call `session.step()` once at each optimizer-update boundary, and say with the keyword whether the update happened: `session.step(skipped=False)` for an update that was due and applied, `session.step(skipped=True)` for one that was due and skipped. Pass `skipped` by keyword. It takes only `True`, `False` or nothing. Anything else raises `TypeError` on a live session before any of the step is recorded; on a closed session, or one whose capture has stopped, the call returns without raising, as it does for a wrong `lr`. An accumulation microstep is not a step: make no call there. The gradient norms are read inside `session.step()`, so call it before `optimizer.zero_grad()`, or call `session.record_grads()` before clearing: a loop that clears first records no gradient norm (`grad_norms` empty, `grad_norm` null), and one whose `zero_grad()` leaves some gradients records those alone, with a total over them only and nothing saying so.
  - **What is recorded.** `step_skipped` is true when either the caller or the scaler given to `init` says so, and `step_skipped_by` says who: `"caller"`, `"scaler"` or `"both"`. On a caller's skip that the scaler was seen to apply, the record also carries `scaler_applied: true`. Both keys travel in `extra_json`, so the schema is unchanged. A skipped record without `step_skipped_by` was written before the key and is read as the scaler's.
  - **What the detectors do with a skip.** `grad_spike` and `update_spike` do not judge it. It cannot advance a `stalled_weights` streak, and a streak carries across it; this holds for a scaler's skips in an older capture too, so a stall whose streak ran through skipped steps counts fewer steps than it did. Only a skip the scaler confirmed counts toward `loss_scale_trouble`, whose streak is "10 consecutive scaler-confirmed skips among observations judged by this rule". A caller's skip with the scaler's outcome unknown leaves the streak and both counts as they are; one the scaler was seen to apply ends the streak and counts as one recorded step. A loss scale below 1 on a caller's skip still raises, with reason `scale`. A gradient that is not finite on a skip the caller reported raises nothing by itself and is kept in the evidence under `skipped_updates` (`skipped_updates_by_rank` in the all-ranks view); a layer statistic that is not finite still raises `non_finite`.
  - **When `scaler.update()` comes after `session.step()`.** The scaler's verdict is taken at `scaler.update()`. If the loop calls `session.step()` first, the scaler's outcome for that update is unknown when the step ends: a caller's skip gets no `scaler_applied`, so it neither adds to the scaler's streak nor ends it. The scaler's own `step_skipped` and `grad_scale` then land on the next record, one step late, as they did before this argument existed. Call `scaler.update()` before `session.step()` to have both on the step they belong to.
  - **Adapters.** Megatron-LM: `session.step(skipped=not update_successful)`. That is the caller's report even when Megatron's own loss scaler caused the skip, so it never raises `loss_scale_trouble`; only a scaler given to `init` does. DeepSpeed: `was_step_applied()` is also false at an ordinary accumulation microstep, so decide from your own count of microsteps whether an update was due, and only then call `session.step`. accelerate: `optimizer_step_was_skipped` is true when any tracked optimizer skipped; with one optimizer it is the answer, and with several it cannot say that every one skipped, so do not pass it as `skipped`.
  - **Limits.** The scaler's verdict is read from `GradScaler`'s private per-optimizer state, as `scaler=` already did, and this was run on PyTorch 2.15 only. With two `update()` calls in one step the last verdict wins, and with several optimizers one overflow makes the step `"both"`; neither was established beyond that. A step on which the scaler skipped some optimizers and applied others carries `step_skipped_part` and is counted as a partial step (wave AE).
- **Resuming.** Pass `start_step=` the step you resume from. Otherwise step numbers start at 0 again, and the evidence reports them as repeated steps. When you resume from a checkpoint earlier than the last recorded step, the new attempt's records replace what earlier attempts recorded from that step on, in the evidence and in every reader; the file and the server's store keep both, and `load_records(..., all_attempts=True)` returns both.
- **Clipping.** Gradient norms are read just before `optimizer.step()`, which is after clipping. The spike detector therefore uses the pre-clipping `clip_grad_norm` for the whole run whenever the run clips, so a spike that clipping flattened is still found; a NaN or Inf `clip_grad_norm` is reported as non-finite. Call `session.record_grads()` before you clip to record the unclipped norms. A step with more than one `clip_grad_norm_` call says so in `clip_calls` ("Clipped groups, a resume, two optimizers, late rows and a restarted server", above).
- **Gradient accumulation.** A hook runs on every forward pass; the record keeps the last one before the optimizer step.
- **Non-finite values** are written as the strings `"nan"`, `"inf"` and `"-inf"`, so the file stays standard JSON.
- **Several optimizers on one model** (for example Muon for matrices and AdamW for the rest) count as one step per training iteration: the first optimizer that ever steps leads, its steps end TensorQuill steps, and gradient norms are read before it steps, so they cover every optimizer's parameters. The others' steps add no step. This holds however each optimizer clears its gradients, but assumes the lead steps once every iteration; when it does not, pass `auto_step=False` and call `session.step()` at the iteration boundary. Lightning's `global_step` counts every optimizer step instead; to match it, pass `auto_step=False` and call `session.step(step=trainer.global_step)`. Optimizers that subclass another and call `super().step()` fire PyTorch's step hooks twice, nested; only the outer call counts, and a step that raised does not stop later ones from counting. An optimizer that sits before the lead in the loop has its update written one step early unless `init(..., ends_step=optimizer)` names the optimizer whose step closes the iteration.
- **`optimizer.step(closure)`**, as Lightning steps, runs forward and backward inside the step, so gradient norms are read after the step instead of before it.
- **Activation checkpointing** recomputes forward passes during backward; the capture hooks skip those recomputations, so router counts and activation statistics count each token once.
- **The cross-GPU drift check is a screening check.** A parameter's float64 norm and sum miss changes that keep both, such as two elements swapping places. The seeded projection added Nov 15, 2026 catches that swap, but it is still a screen: a change that keeps all three values is possible, just far less likely. Megatron's `check_param_hashes_across_dp_replicas` compares hashes for exact equality; each observation also records an exact signature (`fold64-v1`), and signatures that differ prove the bits differ, but for now they are evidence only and raise nothing, since whether healthy replicas are bit-identical has not been checked on a multi-GPU run. Equal signatures do not prove equal bits. A NaN or Inf weight on any replica is reported as drift with `non_finite`.
- **Tensor parallelism.** By default the drift check compares every trainable parameter across `replica_group`, which is right for data parallelism. Under tensor parallelism each rank holds a different shard of most weights, so pass `replica_params=`: a `(name, param) -> bool` filter, or the parameters or their names. With Megatron, which marks sharded weights with `tensor_model_parallel`, use `replica_params=lambda name, p: not getattr(p, "tensor_model_parallel", False)`.
- **The probe is off on a sharded model (since Nov 24, 2026).** Under FSDP1 (`FullyShardedDataParallel`, nested wrappers included) and FSDP2 (`fully_shard`) a forward is a collective: each sharded unit gathers its parameters from every rank. A probe is an extra forward, so a rank that skipped it (a session that stopped because its sink failed) or left it part-way (a probe that raised) left its peers' collectives to meet its next training ones. On two Gloo ranks on the CPU, one rank's process aborted and the other waited (PyTorch 2.15; not run over NCCL).
  - **What `init` does:** it looks at the model's module types and parameter types on this rank only (no collective), turns the probe off, says so once in a `RuntimeWarning` (logged instead under `python -W error`, never raised), and captures everything else as usual. `init` does not fail and no other capture is turned off. The probe's callback is never called.
  - **What is written:** `"probe": {"not_run": "<why>"}` on the first step's record, and the probe's checks reported as unavailable with that reason.
  - **Sharding must already be in place when `init` runs.** The check is made once, at `init`. A model wrapped or sharded afterwards is not seen and keeps its probe, with the hazard above: call `init` after wrapping, as Lightning's FSDP strategy does.
  - **Seen:** an FSDP1 wrapper anywhere in the model; a module inside an FSDP1 wrapper passed without it (PyTorch marks the modules a wrapper manages; this is what Lightning's FSDP strategy gives with no wrap policy); an FSDP2 module; and any parameter that is a DTensor with a `Shard` placement.
  - **The last of these includes tensor-parallel models.** A model whose parameters are sharded DTensors has its probe turned off whether the sharding is FSDP2's or a tensor-parallel layout's: `init` cannot tell from the parameter whether that model's forward is a collective, so the probe is off for both. The rest of the capture is unchanged.
  - **Tested** with two real Gloo ranks on the CPU, for both FSDP versions and for FSDP1 with the wrapper outside the module given to `init`, with one rank's sink failing mid-run: both ranks finish and the healthy rank's capture is whole. **Not yet run on a GPU over NCCL.** The two-L40S run of Nov 24, 2026 (Lightning's FSDP strategy, FSDP1, PyTorch 2.11) had no probe configured, so it is evidence for FSDP capture with the probe off, not for this check.
- **Full sharding alone gives the drift check nothing to compare.** Under FSDP full shard or ZeRO stage 3 no parameter is held twice, so there is no replica. With hybrid sharding the check applies across the replicated dimension only.
- **The drift check cannot see a fault that every rank shares.** A gradient corrupted before or during the reduction reaches every replica alike, and so does a reduction done in too low a precision: one team found a BF16 all-reduce of the LM head's gradient across tensor-parallel ranks became the main source of numerical error as its logits grew, with no hardware fault (Laguna report, p. 9).
- **The scheduled drift check is not a collective.** Each rank observes on its own where `(step + 1) % replica_every == 0`, from the step number, and a reader pairs the ranks' observations by run, launch, group and step, so the ranks must still agree on step numbers (the same `start_step`, or the same `step=` passed to `session.step`) for their observations to be compared; a rank that disagrees leaves the steps `insufficient`, and no rank waits. The explicit calls are collectives ("The two explicit calls are collectives", above).
- **A restarted job can carry an earlier start's launch.** Restart keys under a torchrun launch with several agents (nodes) are not supported in v1: there a restarted rank can take the earlier start's run ID and launch. torchrun keeps one store across a restart of its workers. Where every worker comes from one torchrun agent (`GROUP_WORLD_SIZE` 1: one node, `--standalone` or `--nnodes 1`), each restart after the first start puts the run ID and the launch under keys of its own, scoped by `TORCHELASTIC_RESTART_COUNT`, which that agent raises by one at each restart after a failure, so a restarted rank that is back before its rank 0 waits for the new entry and never takes the earlier start's (shown on a real TCPStore kept across starts, with each rank a process of its own; a whole restarted torchrun job has not completed on this Mac, where its second start hangs in Gloo's `init_process_group`, with or without TensorQuill). The first start keeps today's keys, and rank 0 also writes today's keys in every start, so a rank on an older TensorQuill still reads it; a new rank finds an older rank 0's entry by the mark it lacks and takes it, as before. With several agents (nodes) the count is not trusted: each agent counts its own restarts, a restart for a membership change counts none, and an agent that joins starts at 0, so the ranks of one start can hold different counts. There, after a membership-change restart that ends with one agent again, or with a rendezvous store that outlives torchrun, the keys are the same in every start, and a restarted rank can read the earlier start's launch before the new rank 0 has set its own. Each rank other than 0 reads the launch a second time, on a thread of its own started at the end of its first step (one `check`, then one `get`); neither the training thread nor the writer ever waits for it. Until that read returns, the rank's records carry `launch: null` (unknown), never the launch `init` read, so a record never carries a launch the second read would have replaced: a store that hangs leaves every record's launch null, one that fails leaves it null, and one that answers late gives null until it answers and its answer after. A reader reads a null launch as `not_established`. A reader also allows a rank only one attempt under a launch. Where the keys are the same in every start, a rank whose second read is still early, or a store left on disk by a crashed job, can still pair with the earlier start (contract, section 9), and the run ID, exchanged the same way, has the same exposure (bug list, L25).
- **With several optimizers, the drift check can miss what the second one does.** The observation is taken after the lead optimizer steps and before the second optimizer steps, so on every rank it reads the second optimizer's parameters as they were before that step's update. With the default interval of 50 steps (`replica_every=`), drift the second optimizer introduces right after an observation is seen at the next one only if it is still there. If the run ends first, or the replicas agree again before then, it goes undetected. A second observation after the second optimizer steps would cost a second reading of the parameters and a second record (SDK-06, open).
- **The writer queue is bounded** at about 400 steps: `max(2, ceil(400 / every))` blocks of `every` steps, 8 at the default `every=50`. Training never waits for the writer. If the sink raises, or the writer falls a full queue behind (a stalled network filesystem, say), capture stops for the rest of the session with one `RuntimeWarning`, sent so that `python -W error` cannot turn it into an exception. The steps already handed to the writer are written and no later step is; `session.writer_error` holds the cause; the file gets no `.end.json`, so it reads as cut off, not as closed. `close()` waits at most 60 s for the writer, and after `close()` or a stop the session's `step`, `flush` and `log` return at once and do nothing. On a streaming run the heartbeat then says so on every beat (`capture_stopped`, with the reason: `sink_error`, `writer_behind` or `close_timeout`), with one last bounded beat at `close()`. The server shows the rank as `capture_stopped`, with no severity and no progress incident, and keeps that through a restart and after a clean close; the run's summary is `capture_stopped` when every rank is stopped or finished, and a run with such a rank never reads healthy. One limit: if every stop notice is lost and the stream then closes cleanly, the run reads `finished`. A server from before this state reads such a run as it always did, and a reader from before it says `unknown`.
- **Under `torch.compile`, a tensor subclass is not read.** A router's output or a watched block's output whose type is neither `torch.Tensor` nor `nn.Parameter` is refused in compiled code, the router by name in `moe_refused` and the block left out of the layer statistics, because an op that raises there fails the trace before any `except` can catch it. Eager mode reads them as before. Subclasses that were counted correctly under `aot_eager` and inductor are refused too, since the type alone does not tell them apart. A DTensor block output is unwrapped first; a DTensor router output is refused with its own reason. Run on the `eager` and `aot_eager` backends, not inductor.
- **Register your own forward hooks before `tensorquill.init`.** On PyTorch 2.10 with a Hugging Face Llama, a hook registered with `prepend=True` on a block TensorQuill also hooks crashes `torch.compile` while it builds guards (`IndexError: tuple index out of range`), with or without `skip_nnmodule_hook_guards`. The same hook registered normally, or prepended on a block TensorQuill does not hook, works. Not checked on PyTorch 2.14.
- **Hooks stay on the model after `close()`**, because removing a hook from a compiled module triggers a recompile.
- **Full-capture cost.** Each watched module adds a few small kernels per step. Granite's measured ~6% for activation capture was with every leaf module (171); blocks are the default now (`--layers all` in the benchmark for the old selection). Full capture with defaults measured +4.15% against capture off on the RTX PRO 6000 (Stage 3 above).
- **A fault that goes away under full capture is not gone.** Instrumentation changes timing and load: in published cases error rates on faulty GPUs fell under instrumentation, a checksum's overhead lowered the corruption rate, and a synchronising tracer made 4 of 20 bugs stop reproducing (Zheng et al., Ma et al., OpGuard).

## Develop

Use PyTorch 2.14.1 in the local development environment. From the repository root:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install 'torch==2.14.1' -e './sdk[dev,rerun]'
```

The `rerun` extra installs Rerun 0.43.2, whose `rerun` command and viewer send anonymous usage analytics unless you run `rerun analytics disable` once, as each user on each machine that opens a recording; TensorQuill sends none (see [No telemetry](#no-telemetry)).

Until `tensorquill-server` is on PyPI, pip cannot resolve the SDK's dependency on it, so `-e './sdk[...]'` here and in the commands below fails: install with `pip install -r <(python sdk/packaging/requirements.py dev rerun)` and then `pip install --no-deps -e sdk`, as CI does.

That environment skips the Lightning, Hugging Face, Accelerate and streaming tests. Before committing a change to an adapter or to streaming, run the tests with every extra installed and the server built, as CI does: `pip install -e './sdk[dev,lightning,huggingface,rerun,flight]'` and `cargo build --manifest-path server/Cargo.toml`. A change once passed locally and failed there because only the project environment was used.

For CUDA dogfooding, use the training job's PyTorch build and CUDA environment.

```sh
cd sdk
../.venv/bin/python -m pytest
../.venv/bin/python examples/toy_moe.py --rerun
```

The ingest server needs a Rust toolchain. `test_flight.py` needs only `pyarrow` (`pip install -e './sdk[flight]'`); `test_flight_e2e.py` runs against the server binary and is skipped until it is built (or set `TENSORQUILL_SERVER_BIN`):

```sh
cargo test --manifest-path server/Cargo.toml
```

CI ([ci.yml](../.github/workflows/ci.yml)) runs the tests on every push and pull request, on Python 3.11 and 3.12 with PyTorch 2.6, 2.10, 2.14 and 2.15, and on Python 3.13 and 3.14 with PyTorch 2.15 (CPU builds), and once more with the Lightning, Hugging Face and Rerun extras installed. It also runs `gpu_check.py --skip-overhead`, which on CPU uses the `aot_eager` backend. The real GPU gate is a separate job, started by hand from the Actions tab with `gpu` ticked; it needs a self-hosted runner with a CUDA build of PyTorch, and none is registered yet.

The `Trainer` callback has its own acceptance check, a dense model fine-tuned through `transformers.Trainer` with `torch_compile=True`, clipping and fp16, with the same seeded fault as `dense_outlier_check.py` (`--fault`, default `massive`). It exits non-zero unless every step, loss and clipping norm is recorded and agrees with what `Trainer` logs, the detector finds the outlier, and nothing recompiles:

```sh
pip install -e 'sdk[huggingface,flight]'
python examples/trainer_check.py --out runs/trainer-check
```

It passes with `--toy --backend aot_eager` on CPU. On a GPU (Colab, A100-SXM4-80GB, PyTorch 2.14.1+cu130, SmolLM2-360M, Inductor, fp16, clip 1; Nov 15, 2026) the first run trained 400 steps in 139 s and then crashed in the compile check, which counted Dynamo's backward-graph metrics as frames (fixed in `2ef2da4`). The rerun passed nine of ten checks: every step recorded and numbered as `Trainer` numbers them, loss and clipping norm on every step and equal to `Trainer`'s logged values, `grad_scale` on every step (4 steps skipped), 4 probe passes, 0 graph breaks, 1 compiled frame never recompiled. It **failed the detection check**: no `activation_spike` was found at step 250 in `model.layers.16`.

The cause is the seed, not a missed reading. The block's output had `abs_max` about 20,000 and `std` 31 to 37 at every step before the seed (the model's own massive activations, about 640 times the `std`), and scaling two channels of 960 by 100 moved the block's `std` by 1.07 to 1.14 times and its `abs_max` by 0.95 to 1.07 times, against a threshold of 5. The seed was real: the loss went from about 2.3 to 6.9 on step 250, and the `GradScaler` skipped steps 250 to 253 (scale 65,536 down to 8,192), so the gradient-norm detector first flagged step 254. The block summary (`std`, `abs_max`, `mean`, `zero_frac` of the whole output) cannot see growth confined to a few ordinary channels once the output holds large activations; it would see growth in the massive ones or a block-wide change. The toy Llama has 64 channels, so the same seed was a 13 to 42 times change there. Decided and changed the same day: the check now seeds the channels with the largest outputs by default (`--fault massive`), or the whole block (`--fault block`); `--fault channels` keeps the old seed, and a test builds this situation in miniature and runs the detector on it. The three faults pass on the CPU toy. Rerun on the A100 (same setup as above, commit `d987509`) with `--fault massive` (channels 87 and 398) and `--fault block`: **all ten checks passed in both**. The loss went from 2.32 to 8.46 with 0 steps skipped (`massive`), and to 13.27 with steps 250 to 252 skipped (`block`). The activation spike is at step 250 and the drift at step 254, each covering blocks 16 to 31, and the first gradient spike is at step 250 (`massive`) or 253 (`block`), first in `model.norm.weight`. On this run the spike listed modules by ratio, so it led with block 31, not the seeded 16; fixed the same day (it now leads with block 16 and names block 31 as the largest). The check still only requires the seeded block to be among the listed modules. `--fault channels` was not rerun on a GPU. On an RTX PRO 6000 (commit `2b56eac`, with the check tightened to require the spike to lead with the seeded block) both passed again with the same losses (8.46 with 0 steps skipped, and 13.27 with 3 skipped); each led with block 16 and named block 31 as the largest (722× and 720×).

## No telemetry

The SDK sends no usage statistics, update checks or crash reports. Its only network traffic is the opt-in Arrow Flight sender, which is off unless you set `endpoint=` or `TENSORQUILL_ENDPOINT`, and which connects only to that address (checked with an audit hook that raises on any non-loopback socket use, on a clean install of the wheel running `toy_moe.py`). `tensorquill-server` listens on the address you give it and writes to the store you configure (local disk, or S3 or GCS if you choose one); a reading of its source and its dependency list found no analytics or crash-reporting code, but it has not been run under a network trace. TensorQuill itself sends nothing, with or without the `rerun` extra: `export_rerun` and `--rerun` only write an `.rrd` file. Rerun's own programs are another matter. As read in the source of Rerun 0.43.2, the version the extra pins: the `rerun` command, and the native viewer it opens (`rerun file.rrd`), send anonymous usage analytics to Rerun by default, with a random ID kept on the machine, from the first time either runs. To turn them off, run `rerun analytics disable` once, as each user and on each machine that opens a recording; it writes `analytics_enabled: false` to Rerun's config file, which `rerun analytics config` prints. The command is itself a `rerun` command, and Rerun records each command before running it, so on a machine where analytics are on, that one call is recorded before the setting changes (whether it is then sent was not traced). `FORCE_RERUN_ANALYTICS` turns them back on even after that, so leave it unset. Rerun also keeps them off where the `CI` variable is set. The Python SDK alone, writing an `.rrd` file without opening the viewer, does not turn them on: in 0.43.2 only the command's entry point and the viewer's start do, which is a reading of the source, not a network trace. The web viewer is built with analytics too; its analytics config is kept in the browser's local storage, holds no on-or-off setting, and is not reached by `rerun analytics disable` (`rerun --web-viewer` serves it, as [Run TensorQuill on your own job](RUN_ON_YOUR_JOB.md) suggests on a cluster).
